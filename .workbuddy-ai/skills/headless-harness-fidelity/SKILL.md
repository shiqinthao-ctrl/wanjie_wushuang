# 无头 harness 保真审计

`apps/mobile-next/src/core/*.test.ts` 里的 harness 都是**纯规则驱动**（无 DOM、无时钟），
它们通过 `GameCore.snapshot()` 读状态、用 `core.choose/move/action/advance` 驱动。
**它们很容易在某个动作上悄悄比浏览器机器人弱**，然后给出一个看似精确的错数字。

这个 skill 是「先证明仪器，再读数字」的固定流程。本项目已被同类缺陷咬过三次。

## 第 0 步：先核实「这条规则是否已经存在」——**而且要翻遗留 oracle**

`TASK.md` / 队列里的「做法」是**散文**，它可能描述一个**已经实现**的规则。R1g-8 就整片栽在这里：
立项是「把宝箱候选池从随机改成排序」，实测 `TimedChests.claim()` **从来没有抽取过**——
它先 push 全部合格融合、再 push 进化、再补 filler，然后 `slice(0, 3)`，
所以合格融合**恒在 `options[0]`**，而 `random` 只被 `pick()` 里的 `generateGear` 使用。

**核实顺序（缺一不可）**：

1. **读那段代码**，别读描述。一句话就能看出有没有 `random()` 参与候选构造。
2. **翻遗留 oracle**：`tasks/mobile-modernization/baseline/*-oracle.json` 记录的是 V3.1.3
   **真实行为**，比任何散文都硬。R1g-8 的答案就在 `chests-oracle.json` 的最后一个 selection
   用例里 —— 它自己就要求「六条已进化 ⇒ 三条融合、**零条进化**」。
3. **看谁在守它**：`timedChests.test.ts` 的 `matches config priority case N` 一直在跑那些用例，
   说明这条规则不是「碰巧如此」，是**被迁移钉住的契约**。
4. **别把「默认分支」的行为安到某个具名分支头上**。R2-F04 的 `TASK.md` 说
   「`phoenix` 的必杀扫全周并**留下一个跟随火域**」，而 `EvolutionCombat.ts:94` 是
   `else if (v.heroId === 'H010') for (...) projectile(...)`、`:95` 才是
   `else { arc(...); field(..., follow: true) }`。同一个 `else if` 链上的**相邻两行**，
   `:94` 先命中 ⇒ **`:95` 那个跟随火域永远到不了 phoenix**。判据：**在 `else if` 链上，
   一条具名分支的主张必须读它自己那一行**，不要把「同一链上后面那条」的行为算进来；
   链越长、`heroId` 复用越多（H010 同时是 `phoenix` 与 `legion` 的 hero）越容易错。
5. **「已有断言」可能是假覆盖 —— 看它能不能被别的分支满足**。`evolutionCombat.test.ts:29` 对
   `phoenix` 断言 `render.projectiles.length >= 5`，但**同一个测试体**在断言之前已经
   `player.ult = 100; action('ultimate')` 射了 **16 道** ⇒ 普攻**一道都不射**也通过。
   **核实前提时不能只看「断言存在」，要读它之前那个测试体已经做了什么。**
   （R2-F05 撞到同一类：`evolutionCombat.test.ts:27` 对 `legion` 断言 `summons.length > 0`，
   而那个测试体**先 `action('skill')`、再 `action('ultimate')`** ⇒ 必杀一个分身都不召也通过，
   而且它没钉数量 / id / `life` / 节奏中的任何一项。）
6. **`if` 与 `else if` 要逐行确认前一条是哪种 —— 同一链的相邻两行既能「吞掉」也能「放行」。**
   R2-F04 的教训是**吞掉**（`:94` 的 `else if (heroId === 'H010')` 抢在 `:95` 的 `else` 之前，
   于是 `phoenix` 永远到不了那个跟随火域）。R2-F05 是**同一个链的反面**：
   `EvolutionCombat.ts:85` 是**独立的 `if`**（`if (v.heroId === 'H012' || v.formId === 'legion') this.summon(…)`），
   `:94` 是**另一条链**上的 `else if (v.heroId === 'H010') for (i<16) projectile(…)`，
   而 `legion` 的 `heroId` 就是 H010 ⇒ **两条都命中**，必杀 = 4/5 个分身 **加** 16 道火羽。
   实测：必杀后 `summons` 长度 4/5 **且** `projectiles.filter(id === 'H010_R')` = 16。
   **判据**：读到一个「必杀是 X 或 Y」的转述时，先看那两行的缩进与关键字 ——
   `if` 是并行、`else if` 是互斥；**一个 `if` 后面跟一串 `else if`，是最容易把两件事读成一件的形状**。
   R2-F07 是**第三次**（`void` 的 `heroId` 也是 H012 ⇒ `:85` 的分身包 **加** `:93` 的跟随风暴），
   而且多出一个新变体：**同一个施放里一半 rank-blind、一半不 blind** ——
   `:93` 的风暴 `r/dmg/life` 全是字面量（两阶逐位相同），`:85` 的分身数 4 → 5。
   ⇒ 「这个必杀读不读 `v.rank`」**没有单一答案，必须分半回答**；写「必杀不读 rank」是错的。
   **H012 被四个形态共用**（`void`/`reaper`/`beastlord`/`windwarden`）——
   **heroId 复用越多，越要按 `heroId` 而不是按 `formId` 去读那几行。**

前提为假 ⇒ **零生产改动**。交付改成三件事：**把规则钉成永久断言**（防下一个人再立一次项）、
**把验收测成数字**、**把真正的瓶颈写回队列**。不要为了「让切片看起来有产出」去实现一个已存在的规则。

## 第 1 步：列全「浏览器机器人会做、harness 可能没做」的动作

逐个 harness 对照 `tests/settlement.spec.ts`，检查这五类：

| 动作 | 陷阱 |
| --- | --- |
| 升级选择 | `first` 驱动必须取 `options[0]`（= 浏览器）；取「第一个 active」是**更强的玩家**，不是同一个 |
| 事件弹窗 | `resolveEvent(token, 'skip', { affordable: true, gold: 6000 })` |
| 宝箱 | **`status` 变成 `'chest'` 不是自动的**：必须先 `core.claimChest(index)`（要求 `status === 'running'`）。只响应 `status === 'chest'` 的 harness **一局都不开宝箱** |
| Boss 战利品 | `pickBossLoot(uid)` / `pickChapterLoot()` |
| 地图互动 | 浏览器**每步都按 `f`** → `core.interact()` → `FirstStageMap.useNearest()`。`MAP_BARREL` 是 `atk×7.5`（165px）+ `atk×9.5`（Boss）、`MAP_MECHANISM` 是 `atk×2.1`×10 + `atk×4`（Boss），`heal` 回 35% 生命、`altar` 永久 +22% 攻击。**三个 harness 一次都没调用过** |
| 移动与按键 | 追击时停在 65px。**按键节奏是「每步一次」，不是「每秒一次」也不是「每帧」**：一步在 Boss 阶段 180ms、其余最多 1000ms。两种既有 harness 各取一端（`bossBudget` 每秒、`growthPacing` 每帧），**都在夹逼而不是复刻** |
| 闪避 | 浏览器**会闪避**（`settlement.spec.ts:139-143`）：在渲染出来的 `首领招式` 变化且新值命中 `BOSS_CUES`（`:99` = `['离开红圈','横向闪避','绕至侧后']`）时点「闪避」/ 按 `Space`，且只在 `win && bossPresent` 时。**是反应式的一次按键，不是周期性按键**。`formPressure.test.ts` 的 `run()` 从来没按过（R2-F08）。⇒ 补它之前**先确认场景里有没有 cue**：没有 cue 的开关是死的（§6q） |

地图互动的正确门控是 `state.map.target?.canUse`（= 未使用物件在 74px 内），因为
`interact()` 在范围外本来就是空操作，所以「无条件按 `f`」等价于「`canUse` 时按」。

**症状**：改造前只差 2.8s TTK，改造后（宝箱真的产出进化）差 **22.3s**，胜负率假性掉到 86.4%
（开宝箱实为 95.5%）。⇒ 保真缺口会被内容改动放大，不是常数。

**同一类缺口对份额与对胜率的作用可以完全相反**：地图互动对手动伤害份额只值 **0.02pp**，
却让 classic cell 的胜率从 24/33 变 **31/33** —— 因为 `MAP_BARREL` 的量在总伤害里很小，
但它落在 Boss 阶段，而 `heal`/`altar` 根本不是伤害。**不要因为「份额没变」就判定缺口无关。**

## 第 2 步：量化缺口，别靠推理

同驱动、同种子，**只切换那一个动作**（开/不开宝箱），比较两组：

```
const opened = SEEDS.map(seed => run(driver, seed, viewport, true));
const closed = SEEDS.map(seed => run(driver, seed, viewport, false));
```

若两路**都能赢够多局**，比 TTK 中位；若弱的那一路赢不下来，比**胜局数**（更强的陈述）。

## 第 3 步：证据按切片隔离

**会写文件的 harness 必须在构造函数/模块顶层按切片取输出目录**，且每次进入新切片就换目录：

```ts
const EVIDENCE = resolve(process.cwd(), '../../tasks/game-remediation/evidence/R1g-5');
```

否则它会**每次运行都覆写**上一片的报告。本项目已有两次实例：
`threatModel.test.ts` 硬编码 R1g-3、`growthPacing.test.ts` 硬编码 R1g-4，
两个文件从落地起就在漂移，内容早已不代表自己的切片。
报告里的 `slice` / `base` 字段必须与目录一致，否则文件会**自称是上一片**。

**`slice` 表示「谁拥有这个问题」，不表示数字的年份**。一个 harness 只要还在跑，
它的报告就一直是**当前树**的数字。`evidence/R1g-5/growth-report.json` 写着 `slice: "R1g-5"`，
但内容早已是 R1g-7/8 时代的 —— R1g-8 差点把它当成 R1g-5 的数据照抄。
读任何 `evidence/<旧切片>/*.json` 之前先看它的目录时间和 `IMPLEMENTATION.md` 正文；
如果这个 harness 没被当前切片改过、只是**又跑了一遍**，那就把它的 `slice` 标注成
`<切片> (rolling)` 并补一个 `note` 字段说明它是滚动工件。

**推论（R1g-7 补）**：报告是**对当时的代码**跑出来的，所以它天然是**滚动工件**，不是历史快照。
改完生产再跑一次，旧切片的目录里就躺着新切片的数据（R1g-7 把 R1g-5 和 R1g-6 的报告都污染过一次）。
正确做法不是「保留旧文件」，而是：

1. 把报告的 `EVIDENCE` 指向**当前切片**，`slice` / `base` 同步改；
2. 把旧目录里的 JSON **移走**（它是错的标签 + 新的数据）；
3. 在旧切片的 `IMPLEMENTATION.md` 里留一行「滚动工件说明」，指明新位置，
   并声明**旧切片的数字以该文件正文为准**。

两个配套陷阱：

- **报告字段的值取决于测试执行顺序**。填充模块级状态（`let counterfactual` / `let dashIsolation`）
  的测试必须排在 `writes the evidence report` **之前**，否则 JSON 里是**空数组**
  （R1g-7 的 `dashIsolation` 曾为空，因为它的测试被放在报告测试之后）。
- **`all()` 池化可能把同一个 cell 算两遍**。`CELLS` 里有一个 `focus` 驱动在 evolution 局
  解析成与 `first` 完全相同的机器人 ⇒ 五 cell 池化在**最强的 cell 上重复计权**。
  报「池化值」时**同时报一个去重后的值**，并断言两个都过线，否则结论建立在一个被重复计权的 cell 上。

**R1g-12/13 补（两个新陷阱）**：

- **「移走」这一步必须真的执行，而且要复核**。R1g-12 给七个旧目录写了「本目录的副本已删」的
  指向说明，但**删除这一步漏了** —— 说明与状态不符，下一位会以为目录干净。写完说明后 `ls` 一遍
  目录，确认里面只剩 `IMPLEMENTATION.md` / `RESULTS.md`（`R1g-2/threat-report.json` 这类
  **真历史快照**要留，判据是它的 mtime 属于该切片、且不在任何 harness 的输出列表里）。
- **零生产改动的切片不要重指输出目录**。harness 是**树的确定性函数**（固定种子）：树没变 ⇒
  重跑只复现同一批数字，重指目录只把同一批数字复制一遍，还制造「这一片有自己的读数」的错觉。
  判据：**只有本片改了生产值或新增了仪器才换目录** —— R1g-8 / R1g-9 各自新建了仪器，所以需要；
  R1g-13 零改动，所以 `evidence/R1g-12/` 仍是当前读数（同片的全量套件就是这条确认）。

**R2-F05 补：报告 schema 变了时，「旧报告逐位不变」要用「去掉新键后重建 md5」来证。**
`formPressure.test.ts` 是**跨形态共享**的仪器，每个形态写自己的报告。给 `Outcome` 加读数
（R2-F05 加了 `summonsPeak` / `summonKinds`）之后，四份旧报告的**字节必然不同** ⇒
直接比 md5 会得到一个**假红**（而且你还不能用 `git diff`，因为 `evidence/` 全是 untracked）。
由于写入是确定性的 `JSON.stringify(report, null, 2)`、且新键只在**原位**插入、没有重排字段，
旧字节可以从新文件**精确重建**：

```bash
grep -v '"summonsPeak":\|"summonKinds":' evidence/R2-F01/form-pressure.json | md5sum
# = 601bdaa5085a7b3fa8e06223f4f02e6a，与 R2-F01/IMPLEMENTATION.md 记录的逐位相同
```

四条判据：① 新键必须是**追加且 opt-in**（缺省路径不变）；② 报告写入必须是**确定性**的
（无时间戳、无 `Map` 迭代序、无浮点格式化漂移），否则重建不成立；③ 重建出的 md5 要与
**旧切片自己 `IMPLEMENTATION.md` 里记下的 md5** 比，不是与「你以为的旧值」比；
④ 这条「重建 md5」要写进仪器文件头，供后续加读数的切片沿用。

**推论**：**新增读数 = 新的回归义务**。任何一个「加一个形态」的切片，只要动了 `Outcome` 的
schema，它的验收就多一条 —— 四份旧报告的重建 md5 必须逐位不变。把这条写进 TASK 的 Constraints。

## 第 4 步：红断言先归因，再决定改什么

### 4a. 单一开关反事实

本项目所有 `threat-v2` / `paced` 行为都由一个开关决定（历史上是 `GameCore.ts:63`，
把 `'paced'` 换回 `'legacy'`）。改这一行跑一次：

- 受影响的 cell 变了、**无关 cell 逐位相同** ⇒ 受控实验，是这次改动引起的，不是 RNG。
- 无关 cell 也变了 ⇒ 你的归因是错的。

### 4b. 三类红的正确处置（**不要为绿灯放宽断言**）

1. **仪器缺陷** ⇒ 修仪器，然后**重标数值**。仪器保真与重标定通常是**一枚硬币**，必须同片落地。
2. **口径错误** ⇒ 修口径，并说清历史口径是什么。常见两种：
   - **粒度**：同一主张在两个 harness 里一个按聚合、一个按逐 cell。**先查这个主张的历史总体**——
     本项目 `≥.9` 一直是聚合口径（per-cell 本就在 81.8%–100% 波动），写成逐 journey 是**比历史更严**。
   - **总体**：把**故意弱**的驱动（`unlock`）和**出货**驱动（`first`）混在一个门槛下。
     断言的作用域必须对齐它自己的名字。
   - **自相矛盾**：注释写「是分布不是逐种子约束」，代码却逐种子。
3. **真设计信号** ⇒ 不改断言也不硬调数值，**写进证据并升级为设计决策**，同时把实测数字照实写进报告。

### 4c. 加守卫，不要只放宽

若某 cell 的真实数字低于门槛（例：classic 84.8% vs evolution 97.0% 的**反转**），
**不要**降低聚合门槛了事：聚合会掩盖方向相反的 cell。
做法是**保留**原聚合断言，**另加**一条逐 cell 守卫，并把逐 cell 数字写进报告。

### 4d. 归因条件必须**逐字抄**生产代码，边界要写清包含还是排除

R1g-8 想证明「前提成立 ⇒ 候选必然出现」，两版断言都错在**我自己的复述**上：

| 版本 | 我写的条件 | 生产代码 | 实测 |
| --- | --- | --- | --- |
| 1 | 两个父件都已进化 | `!this.forms.fused[id] && evolved[a] && evolved[b]` | **凭空 9 个违规** —— 把「本局已经拿到融合」的局判成「前提成立却没候选」 |
| 2 | `recipeReadyAt > 240` | 需要**严格早于**倒数第二次宝箱 | 11/13；有两局恰好 **240.0**（闸门在那次宝箱**之后**才满足）⇒ 改 `>= 240` 才 13/13 |

两条可复用判据：

1. **把生产代码那一行抄进断言**，别用自己的话复述。漏一个子句就会造出一批**假违规**，
   而假违规比假通过更危险 —— 它会让你去修一个不存在的 bug。
2. **边界判据写清 `>` 还是 `>=`**，并用实测数据验证：恰好在边界上的样本（这里 2 局）
   就是判定包含还是排除的证据。`240.0` 这种「看起来该包含、实际是排除」的样本最容易漏。

### 4e. 验收不可达时，交付「测量 + 归因 + 写回队列」

目标值在**当前 Scope 内**不可达时，不要硬凑，也不要只写一句「做不到」。R1g-8 的交付模板：

1. **逐条列出候选杠杆与它们的禁区**（闸门 / 宝箱时刻 / `xpNeed` 被 Scope 禁止，
   `activeSkills` / 数据表 / UI 被 Out of scope 禁止），说明**范围内无杠杆**，而不是「没找到办法」。
2. **把瓶颈测成数字并归因到具体机制**：13 个 miss → 9 个是第二个父件没升到 Lv.5
   （自然策略下其中位等级是 **0**）、4 个是在倒数第二次宝箱之后。这样下一片拿到的是
   **问题陈述**，不是「还差 40pp」。
3. **把断言钉在真实现状上**：`expect(rate).toBeLessThan(1)` 明确记录缺口，而不是删掉断言或放宽它。
4. **把「已经是对的那一侧」判满分**：本片最强的断言是**等式**而非比率 ——
   77 局 / 308 宝箱 / 24 个满足前提 / **0 例外**。区分「规则错了」与「前提太罕见」，
   是这类切片最有价值的产出。
5. 把实现选择**交回设计层**：在 `DECISIONS.md` 里给出 A/B 两条路与各自代价，别替设计层拍板。

## 第 5 步：单种子不可用，且**任何数字都要带仪器声明**

整局结局量是混沌的：刷怪半径 524.2→524（**0.2px**）就让 Boss 生成时 HP 从 478 变 710。

- 一切断言用**多种子取中位**，种子集固定且**包含已知最差种子**，失败种子写进证据。
- **n=11 的中位数不足以区分真分歧与分位噪声**（视口一致性在 n=11 读 17.8%、n=33 通过）。
  **不要用 11 种子的中位数去动平衡数值。**
- **n=33 也不足以把「仪器差异」当信号**：同一个 classic cell 在四种都站得住的仪器下读到
  **24 / 28 / 30 / 31**（33 种子），跨度 **21pp** —— 比某片曾据以立论的「反转幅度」12.2pp 还大。
  ⇒ 报任何胜率/份额时**必须同时写清是哪台仪器**（按键策略 + 是否按 `f` + 视口 + 种子集），
  否则下一个切片会拿着旧仪器的数字去推翻新仪器的数字。**「更忠实」不等于「更高」**。

## 第 6 步：份额类指标与代价曲线

### 6a. 份额直接从 `damageBy` 的 source 字符串分类，且划分必须完备

`CombatSimulation.damageBy` 以规则传给 `hit`/`hitBoss` 的 source 字符串为键，**那就是战报遥测**
（`GameCore.captureFinal` 写进 run report）。不要新建采集通道 —— 给它分类即可。

关键是把划分做成**完备**的：未知关键字返回 `undefined`，并**断言 `unclassified` 为空**。
否则新出现的伤害来源会悄悄并进「自动」桶，把份额类指标压下去而无人察觉。

```ts
const unknown = [...new Set(runs.flatMap(r => Object.keys(r.damageBy).filter(s => !bucketOf(s))))].sort();
expect(unknown).toEqual([]);
```

分类的判据要**先核实前提**：本项目 `cast()` 的生产调用者**只有**自动循环（`updateOuter`），
所以在 `action()` 调用栈内包装 `cast`，就能直接测「手动按钮是否触达过某个术式」——
比从份额反推或读源码推断都硬：

```ts
let depth = 0;
const action = sim.action.bind(sim);
sim.action = a => { depth++; try { return action(a); } finally { depth--; } };
const cast = sim.cast.bind(sim);
sim.cast = id => { if (depth > 0) manualCasts.push(id); else autoCasts[id] = (autoCasts[id] ?? 0) + 1; return cast(id); };
```

**包装 `hurt`/`hit` 时，兜底分类会把无关来源吞进目标桶（R1g-9）。** 第一版 `sim.hurt` 包装把
**所有**来源都推进 `hits`，再让 `SKILL_SHAPE[source] ?? 'contact'` 兜底 ⇒ 小怪的
`hostile-projectile` 全被算成 Boss 的**体接触**：接触次数从 **35/局** 变 **220/局**，
占比中位被 `Math.max(1, mitigated)` 的地板钉死在 **1/763** —— 凭空造出一批 7 倍的假数据，
而且它**看起来完全合理**（数字不大、方向也对）。正确写法是**先筛前缀再分类，
且桶内未识别的必须断言为空**：

```ts
if (!source.startsWith('B001')) { lostToOther += lost; return; }   // 不属于本桶的来源直接出栈
const shape = source === 'B001-contact' ? 'contact' : SKILL_SHAPE[source.slice(5)];
if (!shape) unclassified.add(source);                              // 桶内未识别 ⇒ 报告断言为空
```

**前缀判据本身也会错：它吞掉共享前缀的兄弟键（R1g-10）。** `'B001-contact'.startsWith('B001-')`
为真，所以「用 `B001-` 前缀选技能」会把体接触一起选进来。R1g-10 第一版就这么写，于是
体接触也被乘了 14.31 ⇒ **施放/局 0、Boss 承伤/局 573**（玩家在 Boss 第一次施放前就被
82 HP / 1.1s 打死），而报告里每个数字都「看起来合理」。写法是显式排除：

```ts
const isSkill = source.startsWith('B001-') && source !== 'B001-contact';
```

定位手法：写一个**临时** `tmp-*.test.ts` 打逐来源直方图（`B001-contact: n=35` 才是真的），
或临时打印一次样例的 `source` 原文 —— 看见 `hostile-projectile` 就定案了。跑完即删。

**分母不是常数。** `FirstStageMap.useNearest` 的 `altar` 分支是 `p.maxHp *= .90; p.atk *= 1.22`，
而机器人**每步都按 `f`** ⇒ 同一组种子会跑出 `maxHpObserved = [687, 763]`。
所以：观测集合断言在区间内且**至少两个值**（这本身就是「那笔交易真的发生过」的证据），
设计分母用 `calculateStartup(structuredClone(fresh)).player.maxHp`，实测占比用**命中自己的**
`maxHp`。硬编码 `763` 会在第 28 号种子上红。报告里同时记 `maxHpStartup` 与 `maxHpObserved`。

### 6b. 代价曲线用**测试内**线性缩放，零生产改动

要回答「把某条轨道调到 X 会怎样」，**不要**改生产代码再回滚 —— 在 harness 里包装
`hit`/`hitBoss` 缩放 `base` 即可。所有伤害路径都经过它们，且 `enemyHit` 对 `base` 线性，
所以这是忠实的反事实，且**不可能忘记还原**：

```ts
const hit = sim.hit.bind(sim), hitBoss = sim.hitBoss.bind(sim);
const scale = (source: string) => bucketOf(source) === 'autoSkill' ? k : 1;
sim.hit = (e, base, source, crit, skill) => hit(e, base * scale(source), source, crit, skill);
sim.hitBoss = (base, source, skill) => hitBoss(base * scale(source), source, skill);
```

产出「份额 × TTK × 胜率 × 局时长」的代价表。**若越过目标值的那一行胜率为 0，结论就是
「这个目标买不到」**，这比任何定性判断有用。

**但测试内缩放只适合「测」，一旦这个杠杆准备「落」，就要把它做成生产字段（R1g-10）。**
R1g-10 第一版在 harness 里用「逐帧分类 `castCd` 是否被新赋值」缩放节奏，落地时改成
`threatV2.bossCastCooldown`，两者读数不同：

| | harness 近似 | 生产字段 |
| --- | --- | --- |
| 相位切换帧的 cooldown | `(1.2 − dt) × k`，**多算 `(k−1)·dt ≈ 0.22s`** | `1.2 × k − dt` |
| k=14.31 时 dodge 臂 hpMin 中位 | 0.222 | **0.272** |
| 能否被浏览器套件复用 | 否 | 是 |

三条理由，按重要性排：

1. **混沌会把「位置」的微小差别放大。** 0.22s 的时间位移本身无关紧要，但在
   **一局只有 2 次施放**的配置下，它决定了那两招落在哪一帧 ⇒ 血线中位差 **5pp**。
   这与「单种子/小样本不可用」同源：结局量是混沌的，**幅度**的小差别无所谓，**时刻**的小差别会变号。
2. **近似无法被浏览器套件复用**，而落地恰恰要在浏览器套件上验。做成生产字段之后，
   同一个开关同时服务无头仪器与 Playwright，两边不可能漂移。
3. **缺省值让「零改动」可证。** 三个新字段全部缺省 `1`，于是既有的逐字节契约测试
   （legacy 路径、G3 窗口、伤害链）可以**原样通过**，拆分本身被证明是行为中性的。
   落地数值与拆分成两片，**先证中性再证效果**。

### 6c. 只断言已测到的，其余记录

反复出现的自伤：**给断言猜一个界**。本项目在 R1g-6 连撞三次 —— 猜「顶层来源 > 35%」（实为
33.8%）、猜「按键越多份额越高」的单调夹逼（实为 0.64pp 带宽内无序）、猜「去掉 `f` 键胜率不变」
（实为 11→9）。做法：

- **只断言已测到的方向**；没测过的写进报告字段，不写进断言。
- 需要「记录但不钉方向」时，用 `expect(x).toBeLessThanOrEqual(y)` 这类**弱形式**，或只断言
  「不变量」（全距、非空、和等于总数）。
- 断言之前先把数据赋给报告变量，**断言失败时报告仍带数据**，否则你会为了拿数字多跑一轮。

### 6d. 施放时刻定格的参数，不能用结算时刻的状态去验证

R1g-9 要验证「每次命中的伤害都能被 `13 + phase*4` 解释」，第一版拿**结算时刻**的
`sim.boss.phase` 去比对 ⇒ 3301 条里 **69 条**不符，看起来像链条错了。真因是
`FirstBoss.updateAI` 在**施放时刻**就把相位烘进了 `warning.damage`，而预警完全可能在
Boss 越过 70%/35% **之后**才结算（实测 `browser` 臂 **2.09%**、`dodge` 臂 0.56%–0.82% 的命中如此）。

正确做法是**从 `raw` 反解**那个被定格的参数，而不是读当下的状态：

```ts
const phaseOfRaw = (shape, raw, diffDmg, bossDamage) =>
  shape === 'contact' ? (raw / (diffDmg * bossDamage) - 11) / 3
                      : (raw / (SHAPE_FACTOR[shape] * diffDmg * bossDamage) - 13) / 4;
```

两条配套判据：

1. **反解结果是浮点**（`raw / scale` 不精确等于整数）⇒ 计数器必须比较**取整后**的值。
   第一版 `if (phaseFromRaw !== phaseAtHit)` 把 **69 条报成 807 条**（12 倍假红）。
   同时断言误差 `< 1e-9` 且值落在合法相位区间内 —— 那才构成「链条逐位可复现」的证据。
2. **跨相位结算要单独计数，不要当成违规。** 它是规则的真实行为，写进报告字段
   （`crossedPhaseHits`）而不是断言里；断言只要求「跨相位结算条数 > 0」，
   即证明这条路径确实被测到过。**「这条路径被测到过」本身要断言**，否则你无法区分
   「没违规」与「没测到」。

推广：**任何「在事件 A 时刻计算、在事件 B 时刻结算」的量，都不能用 B 时刻的状态验证。**
先问一句「这个数字是什么时候算出来的」，再决定从哪个量反解。

### 6e. 结局要看 `losses` 的**分解**，不能只看血线中位数

「惩罚变弱了」还是「惩罚消失了」，**血线中位数答不了**。R1g-12 把杂兵表降 20% 后，不闪避那一臂的
血线从 **0** 升到 **0.202** —— 只看这一个数，结论是「惩罚没了」。把同一批 66 局的 `losses` 拆开
才是真相：

| 臂 | 血线中位 | 胜率 | **战死** | 超时 |
|---|---|---|---|---|
| 会躲（`hud`） | 0.449 | 87.88% | **8/66 = 12.1%** | 0 |
| 不躲（`browser`） | **0.202** | 71.21% | **18/66 = 27.3%** | 1 |

**不躲让战死率翻 2.25 倍** —— 惩罚只是从**悬崖**变成了**斜坡**，而斜坡往往是更好的设计
（悬崖让「一次没躲到」= 「这局白打」；R1g-11 实测过：落地前认真读预警的玩家 **64/66 超时**，
最优解反而是站桩硬吃 ⇒ 悬崖把「躲」变成负收益）。

**做法**：臂报告里的 `losses` 必须按 `defeat` / `timeout` 分开记（本项目的臂对象已有 `losses`），
判定设计强度时**先看战死率，再看血线** —— 超时与战死是两种完全不同的失败，池化会把它们抹平。
同理，「不躲的代价」这类命题要给出**两条臂的差**（血线 −24.7pp、胜率 −16.7pp、战死率 ×2.25），
不要只给一条臂的绝对值。

### 6f. 遥测字段记的是**它自己的定义**，不是你关心的量

R2-F01 第一版把「远程线有没有开火」读成 `damageTakenBy`（即 `hurt` 的 `lost`）。一路读 **0**，
于是写成断言「弹丸没命中」，还准备去查 AI 为什么不开枪。真因在**被调用函数的写入条件**上：

```ts
hurt(damage, source) { const before = hp; Object.assign(player, incomingHit(...));
  const lost = before - hp; if (lost > 0) damageTakenBy[source] += lost; }   // 只记 HP 损失
incomingHit(...) { if (shield > 0) { ...blocked = min(shield, damage); damage -= blocked;
  if (damage <= 0) return { hp: player.hp, shield, inv }; } }                // 护盾吃满 ⇒ 提前 return
```

**护盾吸收的一切都不进 `damageTakenBy`。** 血条没掉 ⇒ 遥测全 0 ⇒ 把「护盾全吃下了」误判成
「没打到」。弹丸其实**每一发都命中**（`shield` 122.1 → 61.6 → 1.1，技能每 6s 补满）。

**写法**：要测「打到了没有」，就在**同一个调用**里读你想测的那个量 —— 包装 `hurt` 时同时读护盾：

```ts
const hurt = sim.hurt.bind(sim);
sim.hurt = (dmg, src = 'unknown') => { const shield = max(0, sim.player.shield); hurt(dmg, src);
  const eaten = shield - max(0, sim.player.shield);
  if (eaten > 0) { absorbed += eaten; absorbedBy[src] = (absorbedBy[src] || 0) + eaten; } };
```

**先读写入条件，再决定读哪个字段。** 一个字段「全是 0」有两种含义 —— 事件没发生，
或**发生了但没被记**。区分它们的方法永远是打开那个函数看 `if`。

**顺带一条规则发现**（这类误读的副产品往往比原命题值钱）：`incomingHit` 用**减伤之前**的
`damage` 扣护盾（第 136 行），却用软上限减伤**之后**的值扣血条（第 144 行）。同一批 24 发弹丸：

| | 护盾消耗 | 血条损失 |
|---|---|---|
| 有护盾 | **241.92** | 0 |
| 无护盾 | 0 | **164.95** |

⇒ **1 点护盾 ≈ 0.68 点生命**，`maxHp × .16` 实际只值血线的 10.9%。`legacy` 支
（`damage - baseDef * .08`）形状相同 ⇒ **冻结的遗留行为，只测量、不改**，写回队列。
**「读一个字段」和「理解一个字段」之间差着一整条规则。**

### 6g. 一个「什么都没发生」的格，必须配单一开关对照才能写因果

R2-F01 的敌群格（12 只贴脸）读 `absorbed + taken = 0`，看起来是形态 kit 的功劳。关掉技能再跑：

| 敌群 12×EN001 @120px | 造成伤害 | 首命中 | 有没有碰到玩家 |
|---|---|---|---|
| 按技能（有火域） | 1821.77（全 `H001_E`） | **0.00s** | 没有 |
| **关技能**（只有普攻） | 4736.59（全 `H001_BASIC`） | **1.05s** | **还是没有** |

**原归因被证伪**：杂兵被任意一件工具一击必杀，而从 120px 合围到接触比 1.05s 更久 ⇒
**这一格不具判别力**，火域唯一可测的贡献是「提前 1.05s 清场」。按**负结果**记录，不包装成胜利。
同一批对照里，远程格则**有**判别力：有盾血条不动，无盾 10s 掉 **164.95 = 血线 21.6%**。

判据：

1. **零结果先问「如果拿掉这个件，会不会还是零」**。会 ⇒ 这个格测不出该件的价值，如实写。
2. **「有判别力」本身要断言**（`control.absorbed + control.taken > 0`），否则下一片无法区分
   「kit 承重」与「场景本来没威胁」。
3. 对照组的 `casts` 要断言为 **0**（证明技能真的没被按），否则对照本身失效。
4. 反过来，**承重的格要把「值多少」算出来**：`absorbed`（护盾花掉）vs `control.taken`（血条会掉多少），
   两者口径不同时要在注释里说清为什么不同（见 6f 的 0.68）。

### 6h. 按一次技能键可能是**两件事**：先读那个按钮的**全部**副作用

R2-F03 需要拥有技能才能开羁绊，于是撞上了 F01/F02 从没见过的东西：

```ts
// CombatSimulation.ts:266-273
if (this.journeyCombat && action !== 'dodge') {
  const done = this.journeyCombat.action(action);        // ← 形态 kit
  if (done && action === 'skill') this.releaseManual();  // ← R1g-7 手动术式，×6 攻击，键名带 `_E`
  return done;
}
```

`releaseManual()` → `progression.manualSkill()` → **`build.active` 里等级最高的已拥有主动技**
（`A003, A011, A021, ... G2_FROST`，取**第一个严格更高**的等级）。F01/F02 没撞上，只因它们
**不拥有任何技能** ⇒ `manualSkill()` 返回 `undefined` ⇒ 提前 return。

**后果**：如果两臂拥有的技能不同，「单一开关」其实是两个开关 —— 搭车的那一招换了技能、
换了元素、换了位置。实测：`{G2_FROST:1}` → 搭车 `G2_FROST`（一次霜爆 983.08，把精英直接打死）；
`{A011:1, G2_FROST:1}` → 搭车 `A011`。

**写法**：让两臂解析到**同一个 id**。`A011` 在 `build.active` 里排第二、`G2_FROST` 排最后，
同等级时先命中 `A011` ⇒ `{A011:1, G2_FROST:1}` 与 `{A011:1}` 都解析成 `A011`，
手动轨道逐位一致，羁绊成为唯一差别。另外把自动轨道的 `cool` 钉死：

```ts
function silenceAutoCast(sim) { for (const id of Object.keys(sim.state().skills)) sim.cool[id] = 1e9; }
```

（`cool` 只挡自动施放，所以对不拥有技能的形态是 no-op —— 因此可以放进共用 `run()` 而不动旧读数。
注意 `releaseManual` 会自己写 `cool[id] = 0`，所以**手动那一发**是钉不住的，只能靠对齐。）

**通用判据**：**要断言「只有一个变量在动」之前，先枚举这个动作会碰到的每一个共享状态**
（拥有的技能、`manualSkill()` 的解析结果、`cool`、`manualCast`、宠物、导演刷怪）。
少枚举一个，对照就悄悄变成两个变量。

### 6i. 双通道形态：把「只乘一条通道」写成**可证伪**的断言

R2-F03 的 `frostflame` 同时跑冰与火，GDD 把它卖成「组合冰火羁绊」（`thermalshock` 给
**被减速敌人身上的火焰伤害 ×1.3**）。「有羁绊比没羁绊多」是散文；可证伪的形式是**两条通道分开读**：

| 格（rank 1，两臂都拥有 `A011`） | 火通道 | 霜通道 | `kitDealt` |
|---|---|---|---|
| 精英（羁绊开） | **118.41** | 109.23 | 227.65 |
| 精英（羁绊关） | **91.09** | 109.23 | 200.32 |
| 首领（羁绊开） | 3643.53 | 1119.62 | 4763.16 |
| 首领（羁绊关） | 3643.53 | 1119.62 | **4763.16** |

- **火通道 118.41 / 91.09 = 1.300000**（`toBeCloseTo(1.3, 3)`）；
- **霜通道用 `toBe` 而不是 `toBeCloseTo`** —— 「只乘火」这句话的全部内容就是**另一条通道逐位不变**；
- **首领格两臂逐位相同**：`hitBoss()` **不调用** `incomingEnemyDamage` ⇒ 首领对羁绊也免疫。
  这是「开关打开、什么都没动」的读数形式，比断言「首领没有 `chilledUntil`」有力得多。

**判据**：多通道 / 多来源的增益类效果，**必须同时给出「该动的动了」和「不该动的没动」**。
只给前者时，一个「其实乘了全部通道」的实现也会绿。同一批里还顺手测了**静止 vs 跟随**：
`field()` 把 `point.x/y` 拷进结构，传不传 `follow` 决定它跟不跟 —— 行为断言是**移动玩家后读坐标**，
不是读调用参数。

### 6j. 单一开关的**判别量**选错，会把正结果读成负结果

R2-F04 的 `phoenix` 敌群格（12 只 @120px）是本系列**第一个「kit 承重」的正结果**：
它的普攻是 **±0.23 rad 的扇形**，盖不住一个环。撤掉技能（`kit: false`）：

| 敌群 12×EN001 @120px | `killed` | HP 承伤 | `hpMin` | 首次命中 |
|---|---|---|---|---|
| 按技能 | **12/12** | **0** | **1.000** | **0.00s** |
| **关技能**（只有扇形普攻） | **12/12** | **84.06** | **0.836** | 1.05s |

**击杀两臂完全一样** —— 扇形只是慢，10 秒内照样清空。若沿用 R2-F01 的
`expect(control.killed).toBeLessThan(control.of)`，这一格会被判成「不具判别力」，**正结果就丢了**。

**判据**：选判据之前先问 **「这个 kit 的代价记在哪个字段上」** —— 承伤 / 血线 / 时间 / 击杀 /
份额。不同的 kit 记在不同的字段上（护盾记在 `absorbed`、减速记在 `chilledSeconds`、
召唤记在 `summons`、扇形清场记在 `taken`）。**一个字段上读不出差别，不等于这个格不具判别力**，
只等于**这个字段不是它的账本**。写对照时至少同时看 `killed` / `taken` / `hpMin` / 首命中时间。

### 6k. 聚合字段在**负结果格**里会骗人 —— 先拆 `dealtBy` 再下结论

R2-F04 的远程格 `kitDealt` 两臂**逐位相同（1088.52）**，看起来像「kit 参与了但没差别」。
拆开 `dealtBy` 才发现里面**只有 `H010_BASIC`** —— `H010_E` / `H010_R` 连 0 都没有：

| 远程 6×EN002 @520px | `kitDealt` | `dealtBy` | 承伤 |
|---|---|---|---|
| 按技能 | 1088.52 | `{H010_BASIC: 1088.52}` | 81.73 |
| 关技能 | 1088.52 | `{H010_BASIC: 1088.52}` | 98.08 |

⇒ **这一格量的是普攻的 880px 射程，不是 kit。** kit 唯一的贡献是突进的 2 × 0.25s 无敌帧
（98.08 → 81.73）。`kitDealt` 这个**聚合字段名**在负结果格里是**误导性的**。

**判据**：凡写「这个格量的是 X」之前，先把聚合拆成 `dealtBy` 的**逐源份额**看一眼，
并断言**不该出现的那一路确实没有键**（`expect(o.dealtBy['H010_E'] ?? 0).toBe(0)`）。
负结果要写成负结果，**并写明它实际量的是什么**（R2-F01 的敌群格、R2-F02 的清减速对照、
R2-F04 的远程格，三次同形）。

### 6l. 窗口本身决定了你能看到 kit 的哪一部分 —— 先把「够不到的那一半」显式打开

R2-F05 的 `legion` 有**一半伤害在必杀上**（敌群格 6067.98 里的 **5573.21 = 91.8%**、
首领格 22807.65 里的 **14110.70 = 61.9%**），而必杀**只在击杀时充能**：

```ts
// CombatSimulation.ts:240
this.player.ult = Math.min(100, this.ult + (enemy.elite ? 8 : 1.4));   // 无任何时间充能
// EvolutionCombat.ts:83
if (p.ult < 100) return false; p.ult = 0;
```

十秒窗口能摆出的敌人上限是敌群格的 **12 只** ⇒ 最多 **16.8 点**，**赚不到一次必杀**。
实测：不加干预时**八格 `ults` 全为 0** ⇒ 这个 harness 结构上**测不到 kit 的一半**，
而报告里的每个数字都「看起来合理」。

**修法**：给 `RunOpts` 加一个 **opt-in 的 `ult?: boolean`**（`t=0` 给一次充能），
并**让它缺省 false**，于是前四片报告不受影响（§3 的重建 md5 就是这条的证明）。
浏览器机器人玩几分钟自然到得了必杀，所以这不是「给玩家作弊」，是**把驱动对齐到真实玩家**。

三条判据：

1. **先问「这个窗口能到得了 kit 的哪些部分」**：充能 / 冷却 / 层数 / 相位这类**由局内事件驱动**
   的资源，在短窗口里可能**结构性到不了**。看到「某条通道读数全 0」时，先算一遍它需要多少次事件，
   再比窗口内的事件上限。
2. **到不了的部分要显式打开，而不是放弃**：一个 `ult: false` 缺省的开关，既让新形态测到全貌，
   又让旧形态逐位不变。**不要为了测必杀去改 `ult` 的充能速率** —— 那会改生产、也会改旧读数。
3. **这条与「弱驱动不是保守，是另一个玩家」是同一类账**：不是仪器算错了，是**仪器看到的玩法**
   和真实玩家不同。**窗口的长度、按键的节奏、有没有按 `f`，都是仪器声明的一部分。**

### 6m. 新形态不一定要新键 —— 但一定要先问「它的伤害落在哪个容器里」

R2-F05（`legion`）引入了 `summonsPeak` 这个**新读数**，于是很容易形成一个惯性：
「每加一个形态就往共享骨架里加一个键」。R2-F06（`thunderlord`）证明这条惯性是错的。

`thunderlord` 是**首个「立即结算连链」形态**：普攻 / 技能 / 必杀全部在**施放那一帧**结算，
没有弹道、没有场、没有召唤。于是：

- `fieldR`（R2-F01 引入）恒为 **0** —— 它落在 `vortices` 之外；
- `summonsPeak`（R2-F05 引入）恒为 **0** —— 它不召唤；
- 唯一能证明「这个 kit 真的打出去了」的量，就是 **`kitDealt` / `dealtBy[...]` 本身**。

**所以本片零新键**：八格 `fieldR`/`summonsPeak` 全 0 不是缺陷，是**这个形态的真实形状**，
可达性直接用「技能 / 必杀各自的 `dealtBy > 0`」表达。因为 schema 没变，
§3 的逐位 diff 用的是**直接 md5**（R2-F05 用了「去掉新键后重建 md5」，两片各自正确）。

三条判据：

1. **先读 kit 落在哪个容器里，再决定读什么**：`fields` / `vortices` / `summons` / `projectiles`
   是四个不同的容器。一个形态的伤害只会在其中一两个里出现，**沿用上一个形态的读数会得到 0，
   而 0 会被误读成「没生效」**。开写之前先 grep 一遍 `EvolutionCombat` 里这个形态的每个
   `this.<method>(...)`，看它们往哪个数组 push。
2. **容器决定可达性，不是能力决定可达性**：R2-F07 的 `void` 又把伤害放进 `vortices` ——
   于是 `fieldR` 与 `summonsPeak` **又是双 0**，可达性必须换成 vortex 自己的读数。
   这不是「仪器缺一个键」，是**你要为每个形态选对那个键**。
3. **不要为了「流程统一」而无谓加键**：加键会让 schema 变、让 §3 的重建 md5 变成必需。
   只有当**现有键没有一个能表达这个形态的可达性**时才加。R2-F06 的结论就是「不用加」。

### 6n. 「行为验证」的正结果与负结果要**成对**出现

R2-F06 有六条身份断言，其中最有价值的不是「能打中」，而是**反证**：

- 贪心目标反证：A=(100,0)、B=(280,0)、C=(95,−215) ⇒ `[true,true,false]`，
  C **一次都没被碰过** —— 证明链是「按距离排序后 `shift()`」而不是「打所有在范围内的」。
- 远程格负结果：撤掉 kit 后 `taken` **逐位相同**、仍 **6/6** ⇒ 说明 `thunderlord`
  对**分散的远程单位**几乎无解（必杀 `dealtBy['G2_LIGHTNING_R'] === 0`，因为半径内没有敌人）。

**一个只报「能打中」的身份测试是弱断言**：它同时被「正确实现」和「一个碰巧也能打中的错误实现」
满足。**能区分两者的，永远是那条「本不该发生却没发生」的负结果**。
写身份测试时，先设计一条**正结果**（证明存在），再设计一条**必须失败的负结果**（证明边界）。

### 6o. 旧读数可能**活着但看不见你关心的那一半** —— 别把「非 0」当成「够用」

R2-F05 因为 `fieldR` 归零而引入 `summonsPeak`。于是很容易以为「有读数就行」。
R2-F07（`void`）给出反例：`fieldR` 是 0，**而 `summonsPeak` 不是 0** ——
必杀里 `:85` 那条独立 `if` 会为 H012 召 4/5 个分身，所以旧读数**每一格都活着**。
但技能落在 **`vortices`**（一个新容器），`summonsPeak` 对它**一无所知**。

危险之处在于：如果只断言 `summonsPeak > 0` 就宣布「可达性已覆盖」，**八格会全绿**，
而技能风暴的伤害在其中**四格恰好是 0**（一阶半径 110 < 敌群环 120）。

三条判据：

1. **一个读数「非 0」只证明那个容器被用过，不证明你关心的通道被用过。**
   R2-F07 的八格 `vortexPeak` 全 = 2（技能风暴与必杀风暴同时在世），
   而 `dealtBy['H012_E']` 在敌群 r1 / 远程 / 精英 r1 都是 **0**。
   **可达性断言与伤害断言是两回事，两个都要写，而且不能互相代替。**
2. **换容器时要同时断言「新读数 > 0」与「旧读数为什么不够」。** 本片写成
   「`summonsPeak > 0`（必杀的分身那一半）**且** `vortexPeak > 0`（技能真正的容器）」，
   于是「旧读数活着但盲」这件事本身进了记录，而不是被静默绕过。
3. **`killed` / `hpMin` 这类结局量会掩盖通道级的 0。** 远程格 `killed` 是 6/6、
   `hpMin` 0.87，看起来一切正常 —— 拆开 `dealtBy` 才发现**普攻贡献恰好为 0**
   （`fan` 的 `.115 rad` 在 520px 处张开 60px）。**先拆逐源，再看结局。**

### 6p. 测「牵引 / 击退」这类空间效果：用**半径夹层**把位移与伤害分开

R2-F07 的文案写「牵引风暴」，而 `updateVortices` 里牵引半径是 `r * 1.5`、伤害半径是 `r`。
这给了一个干净的实验设计：

- **`r` 与 `1.5r` 之间的夹层里放一个身体** ⇒ 它会被**拖动**但**不会受伤**。
  于是「它动了」这件事**只可能**是牵引造成的 —— 不需要关掉脉冲、不需要改生产。
  实测 `1.49r` 的 `x` 增大且 `hp === maxHp`。
- **`1.5r` 之外放一个** ⇒ 一动不动。**对照臂**（不施放）里两个身体都一动不动 ⇒
  「每帧推进本身不会移动一个 `speed = 0` 的身体」被证明，位移的归因才成立。
- **想测边界时，把身体放在垂直于漂移方向的那一侧**：风暴沿 `heroAim()` 漂移，
  放在正前方的话「漂移」与「牵引」同向，位移读数会**互相抵消**
  （两者都是 85 px/s ⇒ 距离恒定，看起来像「没有牵引」）。
  垂直放置时漂移只会让距离**变大**，于是 `1.49r` 进、`1.51r` 不进，边界干净。

推论：**要测一个「顺带」的效果（牵引、减速、击退），先找生产代码里两条不同半径/阈值，
夹层就是天然的隔离带**，比包装函数或改常量都便宜。

### 6q. 「开关存在」≠「开关能触发」—— opt-in 开关也可能是**结构性死的**

R2-F08 补上了 harness 的第五个同构缺口（机器人会闪避、`run()` 没按过），加了一个忠于机器人的
`RunOpts.dodge`。然后发现**它在四个场景里一次都不会触发**：

- 机器人的闪避是**反应式**的 —— 只在 `首领招式` 变化时按一次。
- 而场景 Boss 是 `sim.time = 270` 时**当场新生**的，所以它第一次出手要等一整个 `castCd`：
  `1.7 × bossCastCooldown = 1.7 × 14.31 = 24.33s`。
- 四个场景**都是 10s** ⇒ `boss.next` 永不变成 cue、`bossCasts` 实测 **0**。

⇒ 三件事必须同时做，缺一就不算诚实：

1. **把开关做成忠于机器人的规则**（cue 驱动），而不是「每帧按一次」的方便版本；
2. **断言它在现有窗口里恒为 0**，把「够不着」写进证据，而不是留成一个缺席的断言 ——
   否则读者无法区分「这个 kit 没有那一半」和「这一半没被量到」；
3. **另开一个显式声明的窗口**去真正量它（这里是 30s），并在测试名/注释里写明
   **只有窗口长度不是机器人的规则**。

推论：**加一个 opt-in 开关时，先证明它在默认窗口里能触发**。一个永远为 0 的开关比没有开关更糟 ——
它看起来像覆盖，实际是沉默。

**同族的第八个例子**（同一个 `bossCasts`）：八片形态的首领格 `bossCasts` **全是 0** ⇒
首领格一直在测一个**10 秒内不出手的 Boss**，只量到体接触或零。**一个共享场景的窗口长度
会同时决定它能看到多少个形态的哪些行为**；八片对齐之后才看得出这是仪器性质而不是形态性质。

### 6r. 容器有**生产上限**时，`> 0` 不是可达性断言 —— 要断言**上限数字**与**构成**

R2-F09 的 `beastlord` 是第一个「kit 全靠召唤物」的形态，也是第一个撞上 `cap(summons, 8)` 的：
技能 3/4 近卫 + 必杀 6 分身 = **9 / 10 > 8**，`cap` 用 `splice(0, …)` 丢**最旧的**（= 技能的近卫）。
结果**两阶场上都只剩 2 个近卫**，而且留下的是**开火最晚**的那两个。

⇒ 三条必做：

1. **先查这个容器有没有生产上限**（`cap(...)` / `applyCaps()` / `cap(this.X, n)`），再决定怎么断言。
2. **有上限就断言数字**（这里是 `summonsPeak === 8`），不是 `> 0` —— **后者在「咬了」和「没咬」
   两种情况下读出来完全一样**，会把本片唯一的发现藏起来。
3. **断言构成**（`guards` / `clones` 各几个），因为总数相同并不代表内容相同：本片二阶留下的
   近卫 tick 是 `.24/.36` 而不是 `.12/.24` ⇒ **觉醒不但没多出近卫，还把第一波推后了 0.12s**。

推论：**「代码里存在」≠「场上存在」。** `:71` 真的写了 `rank === 2 ? 4 : 3`，但第四个近卫从来没
上过场。凡是「觉醒/加成加了 N 个单位」这类主张，都要在**场上**数一遍，不能在调用点读一遍就写结论。
目录文案也可能因此变成**「在调用点为真、在场上为假」**的句子（本片 `四名近卫`）—— 那是规则与文案
的张力，不是文案漂移，别按漂移去改。

再推论：**净增量会掩盖反向的分量。** 首领格 `kitDealt` 是 **+3.19%**，拆开是 `H012_CLONE`
**+750.53** 与 `H012_R_CLONE` **−187.63** ⇒ 觉醒实际是**把伤害从一个容器挪到另一个容器**。
**凡是「觉醒值多少」的问题，先拆 `dealtBy` 再看总量。**

### 6s. 「设计字面量」不等于「测到的值」；装饰调用可能借 kit 自己的遥测 id

两件 R2-F09 撞到的事，都属于「读代码得到的数不是场上那个数」：

1. **范围参数常被 `skillModifier(...).range` 乘过。** `EvolutionCombat:212` 写的是
   `125 * skillModifier(...).range`，本 build 面积加成把它乘到 **156.8（×1.2544）**。
   **直接断言 125 会红，而且看起来像 kit 的 bug。** 做法：**先从生产事件里探针读回真值**
   （这里读 `takeEvents()` 的 `ring` 事件 `radius`），再用读到的值放边界假人，并**同时写清
   「字面量是多少 / 实测是多少」**——与「同一个量在两个基准下有两个值」是同一类账。
2. **装饰性调用可能借 kit 自己的 id。** `:92` 是 `s.ring(p, 180, 'H012_R_CLONE')` —— 纯事件，
   但它用了分身包**自己的** source 字符串。分开两者的办法：**在施放帧读 `damageBy`**
   （那一帧分身还没开火 ⇒ 必须是 `undefined`），并用「环**罩住的**假人没掉血」做第二重证明。
   同理，**共享的英雄前缀键（`H012_BASIC`）在四个形态下形状各不相同**，别把上一个形态的
   普攻断言沿用过来。
3. **遥测后缀可能与 id 撞名（R2-F10）。** 手动释放的标记是 `_E`（`CombatSimulation:218`），而
   **每个形态的技能 id 也以 `_E` 结尾**（`EvolutionCombat:61`：`G4_WIND_E` / `G5_FROST_E` /
   `H001_E`…）。R2-F09 写下的「no manual release fired」用的是裸 `endsWith('_E')`，在 beastlord
   上恰好对，只因为那一片的 kit 是唯一**不含 `_E` 结尾 id** 的形状；到 `windwarden` 第一次跑就红
   （`expected [ 'G4_WIND_E' ] to deeply equal []`）。**这不是「有手动释放」，是同一个字符串被读了
   两种意思。** 做法：过滤器排除 kit 自己的 id（`!(spec.kit as readonly string[]).includes(k)`），
   并写清「这个断言只在 kit 不含该后缀时成立」。

### 6t. 两个容器可能**互相遮蔽** —— 净增量相同不代表机制相同

R2-F10 的 `windwarden` 是第一个**同时抬起 `vortices` 与 `summons`** 的 kit，也是第一个撞上
**同源遮蔽**的：`:68`（技能）与 `:89`（必杀）都调 `fixedVortex`，**同一帧、同一个 `nearestFrom`
⇒ 落在同一个点**；必杀的 200px 盘**严格包含**技能的 120/160px 盘；而 `updateVortices`
（`CombatSimulation:489`）**倒序遍历**数组 ⇒ **必杀先结算**。于是只要必杀一跳致死，技能
**一点伤害都打不出**（敌群格 `G4_WIND_E` 连键都不存在，两阶 `kitDealt` **逐位相同**）。

三条可复用判据：

1. **同一个函数被两个调用点使用时，先问「它们会不会落在同一个位置」。** 都取
   `nearestFrom(p)` / `heroAim()` 的两个效果，只要同帧施放就**同心**；半径大者**包含**半径小者。
2. **结算顺序是隐含的规则。** 数组的遍历方向（`for (i = len-1; i >= 0; i--)`）决定谁先扣血，
   而先扣血者可以**杀死**后来者的目标。这不是数值问题，**换顺序就换结果** ——
   所以「觉醒让技能变强」这类主张，必须在**两个效果同时在场**的格子里读。
3. **逐位相同是强证据，不是巧合。** 两阶 `kitDealt` 精确相等 ⇒ 觉醒在那一格**结构性无效**。
   拆 `dealtBy` 会发现**缺一个键**（不是变小），这比「差了 0.3%」有力得多。
   ⇒ 遇到 `r1 === r2`，先找**遮蔽 / 上限 / 提前结束**这三种结构性原因，不要归到噪声。

推论：**「A 变强了」和「A 的伤害变多了」是两件事。** 本片觉醒确实把技能半径 120→160、时长
4→6（规则层为真），但它在敌群/精英两格**换不来任何东西**。⇒ 文案没错，是**规则与场地的错配**；
改法是动**几何/顺序**（已入队 R2-F-SHADOW）。**R2-F-SHADOW 的结论是：三条修法全部被实测否掉，
零生产改动，而根因不是遮蔽 —— 见 §6v。**

再推论：**同一个 kit 的觉醒符号可以在四格里分裂。** 本片敌群 ×1.0000 / 精英 ×1.0000 /
远程 ×1.0780 / 首领 ×1.1445 ⇒ **聚合一个中位数会把三个方向不同的格糊成一个数**（R1g-11 的同类错）。

### 6u. 一个格读 **0**，先问「事件发生了吗」—— 窗口可能比事件还短

R2-F-INST 是全系列的**仪器片**：`formPressure.test.ts` 的四个压力场景共用一个 `FRAMES = 600`
（10 秒），而**首领格**要看到的事件是 Boss 出手。Boss 的首次施放闸在
`FirstBoss.ts:41` `castCd = 1.7 * castCdScale`，而 `castCdScale = threat.bossCastCooldown = 14.31`
（`threatV2.json:14`）⇒ **首跳在 `1.7 × 14.31 = 24.33s`**。于是**十片**的首领格全都记着
`bossCasts = 0`、`takenBy = {}` —— 那个 `0` 被读成了「Boss 打不出伤害」，真相是
**Boss 从没被问过**。同一片里 `bulwark` 的首领格在换窗口后 `bossHpLost` 6710 → **30606**、
`phoenix` 的 `hpMin` 0.9363 → **0**（88.92s 战死）。

四条可复用判据：

1. **一个 `0` 有三种来源，必须区分**：①**事件没发生**（窗口太短 / 闸门没到）；②事件发生了但**无效**；
   ③事件发生了但**没被记录**。第 ③ 种看被调函数的 `if`（§6f），第 ① 种看**窗口与事件时序的对比**。
   R2-F-INST 是 ① —— 而在修掉之前，它**长得和 ② 一模一样**。
2. **窗口长度是仪器声明的一部分，且应当从配置读**。`BOSS_FRAMES = (firstStage.duration − firstStage.bossAt) / DT`
   = `(360 − 270) × 60 = 5400`（90s）—— 读的是**这场遭遇自己的长度**，不是拍脑袋的数。
   硬编码 `5400` 会在 `bossAt` 一改就静默失效。
3. **覆写必须按场景**。`run(sim, scenario, spec, frames)` 的 `frames` 是**全局**的；把首领格拉长成
   `WINDOWS = { horde: FRAMES, ranged: FRAMES, elite: FRAMES, boss: BOSS_FRAMES }` 之后，
   另外三格才逐位不变（十份报告里只有首领格变了，顶层只多 `windows` / `bossDodged` 两个键）。
4. **旧窗口的负结果要留成断言，不要删**。新加的测试里显式跑一次 10s 窗口并断言
   `short.bossCasts === 0`、`short.takenBy` 为空 —— 这条**证明仪器确实曾经瞎**，
   比「现在读到了 2」更能防止将来有人把窗口调回去。

**推论：拉长窗口会把「快照」变成「持续交换」，读数含义随之改变。** Scope 4 逐格复核了另外三格：
`elite` 十片在 600/5400 下**答案相同**、`horde` 九片相同（`legion` 例外），但 **`ranged` 六片不同** ——
因为远程格是**持续交换**（敌人不断重生），`taken` 在那格里是**10 秒采样**而不是总量。
⇒ **改窗口前先问：这一格量的是「一次事件」还是「一段流量」**；后者会被窗口长度直接缩放。

再推论：**仪器一变，依赖它的门槛与标定全部作废**。本片把 Boss 从「不出手」改成「出手两次」，
于是 G2/G3/G4 的标定全部重开 —— 已入队 **R2-F-CADENCE**（Boss 一场只出手两次，`skillIndex`
走 0→1→2 ⇒ 玩家**永远看不到 `震地斩`**，闪避键每场只有 2 次机会）。**把作废的账写进队列，
否则它会在几片之后以「某个 harness 突然红了」的形式重新出现。**

## 第 7 步：生产改动也要先过单一开关反事实 —— 并且要准备回退

R1g-7 的教训：**本片自己新增的两处机制，都是被自己的实测打回的。**

| 新增机制 | 它想修的症状 | 单一开关实测 | 结论 |
| --- | --- | --- | --- |
| `dashLength` 夹紧到 `min(150, 距离-65)` | 「按键越多血线越低」 | 血线 **−25pp**、evolution 少赢 **10 局**，份额只值 +0.9pp | 回退 |
| Boss 相位 dwell + `holdHp` | 「三阶段各至少一次」 | 让 Boss 相位切换后 **6s 内不可杀**，打破 **9 个**合法一击必杀测试 | 回退 |

三条可复用判据：

1. **机制在站位/阈值处可能退化成空操作。** 机器人停在 65px，所以
   `min(150, 65-65) = 0` —— 那个「夹紧」不是缩短突进，而是**删掉**突进；
   而突进是**脱离手段**（`inv` 与位移无关地照给），所以血线塌了。
   **上线前先算一遍机制在实测参数下的取值**，不要只看公式的形状。
2. **「不可见规则」的代价是测试，不是数值。** 让 Boss 在相位切换后 6s 不可杀，
   在遥测里看不出来，但它会让**任何合法的一击必杀失效** —— 一次跑出 9 个红。
   给规则加例外之前，先问「有没有合法操作会被这条例外挡住」。
3. **症状跟着数值走，就用数值解决。** 这两处机制都在针对一个**只在特定数值下出现**的相位/血线
   症状；把数值（`bossHp`）重标之后症状就消失了。用机制去锁一个数值产物，等于把一次性
   补丁永久焊进规则。

做法与第 2 步同构：给新机制留一个**测试内开关**（`tune?: { dashClamp?: boolean }`），
同种子跑开/关两组，把代价写进报告。回退后**保留那个开关**并把代价钉成一条永久断言 ——
将来谁再加同样的机制，就得在同一处再付一次代价。

> 顺带：改生产前先记下**基线**。R1g-7 是「先落地 → 发现 G2 破了 → 才去隔离」，
> 多花了整整一轮 4 分钟的 harness 运行；如果上线前就跑一次开关对照，第一轮就能发现。

### 6v. 两个读数**同生同灭** ⇒ 同一个事实的两面 —— 出路是**换场地**，不是换数值

R2-F-SHADOW 把 §6t 的遮蔽追到根上，结论是**零生产改动**，因为三条修法**全部**被实测否掉。
四条可复用判据：

1. **队列/TASK 里写的理由，本身就是待核实的前提。** 本片的 ① 被队列写成「技能改 `heroAim()`
   （偏离最近目标，不再同心）」—— 而 `heroAim()`（`CombatSimulation:174`，= `boss || nearest()`）
   与 `nearestFrom(p)`（`EvolutionCombat:115`，**含** Boss）**只在「有 Boss 且 有更近小怪、且
   不同轴」时分离**。探针在六种配置上实测，**四格 × 两阶里一个字节都不动**。
   ⇒ **照队列的理由直接落地，就会交付一个「声称修好了、但一个字节都没动」的改动。**
   这是「前提核实」的第 N 次，而这次的前提是**队列自己**写的。
2. **「有效」不等于「修好了」—— 要问净额的符号。** ③（降必杀一跳到不致死）确实把
   `G4_WIND_E` 送进 `damageBy`（0 → **277.09 / 387.93**），但**净额是负的**：觉醒的敌群
   `kitDealt` 1845.76 → 1643.25（**×0.8903**），玩家从**零伤**变 `taken = 18.68`。
   ⇒ **凡「X 出现了 / X 上升了」的句子，都要用同一份账本再问一次「整体是变好还是变差」。**
   （§6k 是它的正向版本：先拆 `dealtBy`；这条是反向版本：先看净额。）
3. **扫掠下的同步翻转是结构性信号。** 把必杀系数从 `.65` 扫到 `.30`（六个取值），
   **`hpMin === 1` ⟺ 两阶逐位相同**，无一例外，而且**在边界值 `.397` 就已经破** ⇒ 不是调参问题。
   机制可逐条读出来：200px 盘在第 0 帧只覆盖环上 **7/12**，盘外 5 具**自己走进来**；
   致死时**一跳即死**（`deathFrames = [0×7, 16,17,17,17,17]`），不致死时要 **2–3 跳**
   （`[0×5, 9,17,21,31,34,34,34]`）⇒ 撑到 frame 30+ ⇒ **挨打**。
   ⇒ **两个读数同步翻转时，它们多半是同一个事实的两面；修一面必破另一面。**
4. **出路是换场地，不是找那个不存在的交点。** 敌群格**同时**要求「kit 无伤清线」
   （`hpMin === 1`，8 个形态都断言）和「看得见觉醒」，对持续场类觉醒这两件事**互斥**。
   正确动作是**补一格能扛过必杀一跳的敌群**（显式入队），不是在数值上继续扫。

**附带：规律要用全量数据检验，别用 n=4。** 本片一度想把上面的反相关写成**系列规律**，于是在
**十份压力报告、40 个格**上全量检验 —— **28/40，被证伪**。两个方向都有反例：
`phoenix` / `thunderlord` / `void` 的敌群格**无伤却可分**（它们的觉醒动的是**第 0 帧的离散量**：
链跳数 5→7、半径 110→145 **跨过** 120px 环），而 8 个形态的 `ranged` 格**有伤却相同**。
**而且 7/10 形态的敌群格本来就是「无伤 + 两阶相同」** ⇒ 这是**常态不是缺陷**。
⇒ **「这个 kit 的四个格如此」与「系列如此」是两句话；写第二句之前先跑第一句的全量版本。**

**附带二：觉醒要「看得见」，就得动第 0 帧的离散量。** 本片根因**不是遮蔽**（遮蔽只把读数从
277.09 变成 0）：岚影的觉醒动的是「半径 120→160 + 时长 4→6」，**两项在 30° 离散环上都是第 0 帧
中性**的（`240·sin 45° = 169.7 > 160` ⇒ 160px 盘**一具都不多**）。而能看见觉醒的三个形态
（`phoenix` / `thunderlord` / `void`）都动了**跳数**或**跨环半径**。
⇒ **判定「这个格能不能看见觉醒」时，先算觉醒改了哪个第 0 帧的离散量。**



### 6w. 同一个后缀标两种东西 —— 分类器可能在分类**后缀**，而 GDD 的门槛读的是**字面键**

R2-F-SUFFIX 追的是 `_E` 后缀：生产（`CombatSimulation:218`）用 `${source}_E` 标记「手动释放」，
而**每个形态技能 id 本身就以 `_E` 结尾**（`EvolutionCombat:61` 造 ``${heroId}_E``）。六条判据：

1. **先测「这个后缀到底在标什么」，别读注释。** 树上探针把四个键形各跑一遍：`X_E` 对**任何** `X`
   都落 `manualSkill`（连 `PET001_E` / `F004_E` / `MAP_*_E` 这些**永不生产**的键也落）⇒ 分类器
   **在分类后缀，不在分类 id**。且 `X_R_E`（手动**必杀**释放）**也**落 `manualSkill`，因为 `/_E$/`
   **先于** `/_R$/`（`:117` vs `:118`）⇒ 桶名承诺的「手动必杀」机制**根本不存在**。
   ⇒ **任何「按后缀分桶」的分类器，都要先枚举它自己的分支顺序。**
2. **TASK 的待测前提本身可能是假的，而且假得很具体。** 本片 TASK 假设「自动施放的形态技能会落进
   `manualSkill`」。实测：`action('skill')` **只由玩家输入到达**（生产侧仅 `controls.ts:16` /
   `BattleView.vue:91` / `GameCore.ts:91`），自动施放只走 `updateOuter` 的 `cast(id)`，而 `id` 取自
   `build.active`（`A0xx`/`S001`/`G2_FROST`），**无一以 `_E` 结尾** ⇒ 前提为假。
   ⇒ **核实前提要追到「这个 id 从哪个数组来」，不是追到「有没有这个函数」。**
3. **「注释声称的读数」与「代码实际算的量」是两件事 —— 分开量。** harness 注释写「The GDD's own §11.1
   test reads only these two keys」，而 GDD 原文读的是**两个字面 `damageBy` 键**求和。两个读数
   **差 2.74×**（0.1365 vs 0.3739），**GDD 的字面读数未达它自己写的 35% 门槛**（差 21.4pp）；而 harness
   的断言 `expect(core).toBeLessThanOrEqual(headline)` 因 `MANUAL_CORE ⊂ MANUAL` **恒真** ⇒ 「过」是**假绿**。
   ⇒ **门槛类断言必须把「GDD 写的键集」与「harness 用的键集」对齐，对齐不了就两个都报、两个都断言。**
4. **「靠构造回避」要留断言。** `G2_FROST_E` 是唯一**同形两义**的键（霜君签名场 **+** `G2_FROST` 的
   释放键）。两套 harness 都靠**构造**回避（一个保留 `A011` 让 `manualSkill()` 解析到 `A011`、
   另一个只把驱动跑到 `dragon`），**没有一处断言**。⇒ **碰巧没撞上 ≠ 没问题**；把「没撞上」写成断言
   （`truth['G2_FROST_E'].auto === 0`），或入队补测。
5. **修分类器 vs 修生产：判据是「生产那个后缀的用途声明是否被实测满足」。** 本片被满足
   （`A003` auto 7,161,671 与 `A003_E` release 13,447,659 **可分**）⇒ **别动生产**：改后缀会改写
   **每一个已落盘账本的键名**，却买不到分类器买不到的东西。落地只改仪器三处。
6. **误标的修法是「写准标签 + 补测」，不是搬动别人依赖的数字。** `manualCoreShare` 保持 0.3739
   （`evidence/R1g-11`/`R1g-12` 与落盘报告引用的记录值），另加一个 `gddSnippetShare` 说清真读数。

> **「这个开关存在」与「这个开关承诺的东西存在」是两回事。** 本片 `manualUltimate` 桶**100% 非手动**
> —— `releaseManual()` 只在 skill 分支被调用 ⇒ 桶名承诺的机制在生产里不存在。**桶名也是断言。**



### 6x. 队列里的「互斥 / 不可能」是**先验**，不是测量 —— 先把那个集合数一遍

TASK 写「敌群格同时要求无伤清线与可见觉醒，对持续场二者互斥」，并把范围说成「八个形态」。
实测**两处都不成立**：`hpMin === 1` 只被断言 **7 处**（F04..F10；F01/F02/F03 的敌群格只断言
`killed === of` / `absorbed + taken === 0` / `chilledEver`）；而 **「clean ⟺ blind」不是规律** ——
十形态读的 **40 格**里 **17** clean+blind / **4** clean 但**可分** / **8** dirty+相同 / **11** dirty+可分
⇒ **12 个反例，两个方向都有**；敌群列本身 **10/10 clean、其中 3 个可分**（`void` 也是持续场、也分得开），
而且**敌群格还不是最弱的格**（盲的个数 `elite` 9 > `ranged` 8 > `horde` 7）。

**做法**：把「互斥」当成一条**待测假设** —— 先 `grep` 出那个集合的全部成员、数一遍，再对每个成员跑一遍；
**「谁扛着这条验收」要用同口径的计数回答**（本片：`hpMin === 1` 是**成本**断言，七个形态里
**六个只有首领格分得开**，只有 `thunderlord` 靠敌群格）。照前提去「修互斥」会去改一个不存在的规律。

> **可破 ≠ 随便挑个数。** 半径带（8 半径 × 10 形态 × 2 阶 = 160 局）实测 `clean` 是
> `[T,T,F,T,F,T,T,T]` —— **对半径非单调**（180 与 240 变脏）。**互斥可破，但只在孤立档位上可破**：
> 单调的修复可以钉一个数，**非单调的必须连同那张表一起交付**，否则下一个人换个数值就复现缺陷。
> 另：两条「看起来更对」的候选（`EN006@120` 更硬、`EN002@120` 远程）**都被实测否证** ——
> 候选格要先跑再评。

### 6y. 会被**行号**引用的文件里加仪器：一律追加到文件末尾，并用断言钉住等价

`manualDamage.test.ts:131/498/546/550` 用**行号**引用 `formPressure.test.ts:2895/2572/195/1009-1047`。
在文件中间插一个常量会整体下移若干行 ⇒ 那些引用**静默**指到别处（编译器不会报错）。

**做法**：新 `describe` + 新常量**追加到文件末尾**；用一条 `it` 断言「新常量 == 旧构造」
（本片走**生产路径**建环再逐具比对半径 / 角步长 / `maxHp`），**不要**让两边共享同一个字面量 ——
共享字面量只证明「两处写的一样」，不证明「构造没变」。改完 `grep` 复核被引用的那几行**内容未变**。

### 6z. 「核对该目录下全部 X」要写成**可执行清单**，不能手抄

「本片零生产改动」的最强证明是「报告逐位不变」，而 `R1g-12/` 目录里有**六份**滚动报告，
早先两片只核了**四份** ⇒ 一份不符（`R1g-12/manual-report.json`）被漏了整整两片。
**漏掉的项不会报错，只会沉默。**

**做法**：用一条命令列出 X（`ls` / `find`）再逐份核，并把**清单本身**落盘（而不是只落结论）。

### 7a. 全局规则改动：用**证据树全量 md5** 找出所有被改写的报告

只要改动**不是**局限在一个 kit 里 —— 一个上限、一个共享函数、一个共享常数 —— 就必须回答
「它改写了哪些**旧报告**」。逐份猜是不行的，因为受害者往往是**别的形态的格**或**整跑格**。

做法（R2-F-CAP 实测，248 份 JSON / 8 个仪器）：

1. **在开关的两个取值下各跑一遍全部会写报告的仪器**，每次跑完对 `evidence/**/*.json` 做一次
   全量 md5 排序落盘：
   `find . -name "*.json" -not -path "*test-results*" -not -path "*/.baseline/*" -print0 | xargs -0 md5sum | sort -k2 > capN.txt`
   —— 用 `xargs -0`，**不要**用 `find | while read` 循环（几千个文件会被超时杀掉，快照只写一半，
   而半份快照看起来跟完整的一样）。
2. `diff` 两份快照 ⇒ **被改写的报告就是全部答案**，而且是逐位级的，不是「数值接近」。
   本例 248 份里只有 **4** 份不同。
3. **把基线那一侧重跑一次**，确认被改写的报告**逐位复现**原来的 md5。
   没有这一步，`diff` 只能证明「有 4 份不同」，不能证明「这 4 份的不同都是这个开关造成的」。
   复现成功之后，「开关是唯一变量」才从假设变成证据。
4. **全量套件跑完后再 md5 一次**，与第 1 步的快照逐位比对。相同 ⇒ 仪器确定性 + 磁盘证据与交付一致；
   不同 ⇒ 有报告依赖**测试执行顺序**（那是另一个坑）。
5. **基线报告必须在第一次覆写之前复制出来**。报告会被下一次运行覆盖，而 **git 不一定救得了你** ——
   新建的切片目录常常整体是未跟踪的（`git status` 里是 `??`），`git show HEAD:…` 取不到，
   `git diff` 也是空的。落盘位置：当前切片目录 + 两份 md5 清单。

> **反事实的强度来自「逐位」，不是来自「方向一致」。** 一个只在 4 份报告里动、且其中 3 份动的
> 是同一格（`evolution/unlock`）的结果，比一堆「+0.3% / −0.5% 看起来合理」的数字有力得多。

### 6aa. 「没有格包含它」可能是**断言**，不是遗漏 —— 动 `scenarios.*` 前先 `grep` 断言

队列说「首领格不撒任何小怪，所以修法 ① 的生效配置没有格包含」，听起来像仪器缺了一格、补上就行。
实测：`scenarios.boss` **主动 `return []`**，而另一片（`R2-F-INST:3040`）把
`nothing but the Boss lands here` 写成了**十形态共用**的断言 ⇒ 候选「往首领格塞小怪」
**必然打红 ×10**，它不是「补一格」而是**「改一条验收」**。

**做法**：在动任何 `scenarios.<name>` 之前，先把**整套 harness 里针对那个场景的断言** `grep` 一遍
（`grep -n "scenarios\.<name>\|'<name>'"`，并顺带看 `NAMES` / `WINDOWS` 这类**与 `scenarios` 平行的
独立清单**）。**一个「看起来只是数据」的构造，很可能已经被另一片钉住了**；改动成本要按
「这条断言扛着谁的验收」来估，不是按「加几行」来估。

> 同一个动作的两种账单差一个数量级：候选 A（塞进既有格）= 打红 10 条断言；候选 C（**新开一格**，
> 不动 `scenarios.boss`）= 零报告改动。**先量账单，再选候选。**

### 6ab. 「几何理由」要写成**可判定的不等式**，并**逐格对账**

队列的理由是「偏离最近目标」—— 无法证伪，也无法验算。本片把它化成一条可判定的式子：

```
Boss 落在技能涡旋之外  ⟺  d < standoff  且  standoff + min(reach, d) > r + bossR
```

其中 `r`（120/160）与 `reach`（180）来自生产，**`bossR = 42` 是测量出来的**（不是抄来的）。

**做法**：扫一张**二维表**（本片 23 摆位 × 2 阶 = 46 格），把**模型预测**与**实测是否动读数**
逐格比对，**46/46 全中才算结论**。对不上的那几格才是真正要看的地方。

两条容易漏的：
- **先枚举「可分离集合」再下结论**。出货站位 90px 下要 rank 2 可分离需要 `90 + d > 202` **且**
  `d < 90` —— 把 `d = 1..89` **全枚举一遍**，得到**空集**。一句「大约不行」和一个空集，
  在设计裁定里的分量完全不同。
- **挡住路的变量可能不是你以为的那个**。队列以为要调**半径**，实际卡死的是**站位**
  （rank 1 只在 `d ∈ (72, 90)` 可分离）⇒ 最小格的构造是 **standoff 102 / d 101**，与半径无关。

### 6ac. 离散量上的增益是**常数** ⇒ 别去找中间档，直接问**占比**

① 买到的伤害恒为 **+831.28（rank 1）/ +1219.21（rank 2）**，= **跳数 × 单跳伤害**（+15 / +22 跳 × 55.42）
⇒ **一格要么全盲要么全开，没有中间档**。

**做法**：当改动作用在**跳数 / 环上命中数 / 分身数 / 命中具数**这类**离散**量上时，
先扫整个区间确认增益是不是常数。是常数就**别调中间值**，直接问
「这个常数占目标预算的多少」—— 本片是 **0.18% / 0.27%**，于是结论自然是
**「可验证但不值得落地」**（O4），而不是「再找个更好的数值」。

> 与 6x（非单调 ⇒ 连同表一起交付）配对：**连续量看单调性，离散量看是不是常数。**
> 两条都指向同一件事 —— **先扫区间，再决定要不要调那个数**。

### 6ad. 「两个读数不同」要问到「是不是**子集**」

队列说「设计文档的断言与 harness 不是同一个读数」—— 到此为止只知道「不一样」，不足以裁定。
把它推到**严格子集**：文档的字面两个键 = 12,098,521.36 **完全包含在** harness 的两个桶
= 33,139,229.20 里，差量 21,040,707.85。

**子集关系比「不同」强得多**，因为它直接点名**哪一半被漏掉**：漏掉的正是生产自己的 `manual`
旗标判为 `true` 的那一半（19,654,845.33）—— 也就是**这个指标存在的理由**（那次修复落地的手动释放，
`A003_E` = 13,447,659）。

**做法**：遇到「两个读数不一致」，下一步永远是问「**谁包含谁**」，而不是「哪个更保守」。
把两侧的键集都列出来做集合运算，并**用生产自己的旗标/字段**（不是自己再写一个分类器）
确认被漏掉的那一半是什么。

### 6ae. 一个键名可能有**两个发射点** —— 先枚举发射点，再解释它

`H001_E` 同时由 `CombatSimulation:292`（classic 路线，`arc(135, atk×2.2)`）和
`EvolutionCombat:79`（形态 switch 的**最后一个 `else`**，只在英雄**尚未进化**时触发，
`arc(150, atk×2.2)`）发出 —— **两条路径互斥，但共用一个遥测键名**。按路线拆开数：
`H001_E` 有 **74.8%**、`H001_R` 有 **64.7%** 来自进化路线。

**做法**：解释一个遥测键之前先 `grep` 它有几个发射点（`grep -rn "'<KEY>'" src/`，
**注意拼在模板串里的形式** `` `${id}_E` `` 也要算）。**只有一个发射点的键**才能用
「它属于哪条路径」来解释；有两个以上的，先按路径拆开报，再谈它是什么。

### 6af. 判「哪个口径才对」用**方向**；设计文档里的断言没人执行 ⇒ 最易烂

最直觉的裁定是「字面口径更保守，所以更安全」。实测否掉了它。在唯一有「有/无进展」混合的 cell 上
（33 局，20/13 分裂）逐局相关：

| 相关对 | r |
| --- | --- |
| `r(进展, 文档字面读数)` | **−0.3172** |
| `r(进展, 桶读数)` | **+0.3447** |
| `r(进展, 真·手动量)` | **+0.3657** |
| `r(进展, 总伤害)` | +0.2144（⇒ 不是分母效应） |

**两个读数朝相反方向动 ⇒ 它们测的是两件不同的事，不是「一个更保守」。**
**一个随玩家变强而下降的「贡献」读数，测的不是贡献。**

**做法**：裁定按**意图**（文档自己写的指标名 + 现状问题 + 建议做法），不按「哪个数能过」；
同时把**保守界记进账**（收紧口径后的读数，以及它是否过线），因为「哪个口径」这件事
**不能在两种读法之间来回挑**。

**顺带一条文档卫生**：设计文档里的断言**没有任何测试或脚本执行它**（`grep` 全库：只有注释在引用它的
行号）⇒ 它可以错整整两片而无人发现。**改它是「免费的文档半边」** —— 先确认门禁
（`archive-verify` 的必需清单 / 活跃上下文包 / `doc-budget`）**不包含**它，再落。

### 6ag. 「同形两义」要问**谁减掉谁** —— 枚举那个集合，别靠「名字像」

一个字符串有两个用途时（`G2_FROST_E` = 签名场 **和** 某技能的释放键），
**「有共同的字符串」不是判据**：另一个形态的 core 也是 `G2_FROST`，
但它自己的 kit 用的是 `G5_*` ⇒ **同一个释放键不在它的 kit 里** ⇒ 那个过滤器**能抓到它**。

**判据要写成可枚举的不等式**：`chapterCoreSkills[form] + '_E' ∈ SPECS[form].kit` ——
十个形态**恰好一个**成立。**撞车 = 「那个字符串落在会被减掉的那一半里」**，
所以「同一个 core 技能的另一个形态」**不是**同案。

**通用形状**：任何「把某个前缀/后缀从读数里减掉」的守卫，盲区都只在
**被减掉的那一半里恰好装着它本该看的东西**时出现。**先把那个集合数一遍，再看谁落在里面。**

### 6ah. 「守卫盲」要问**它盲成什么** —— 丢了 vs 合并了，两种红完全不同

不要把「盲」直接读成「数据没了」。**同一个键**在两条臂上读 **152.92 → 1136.01**
（**7.43×**），而 `dealtBy` 的**键集完全不变**：释放**并进了签名场自己的键**。

| | 丢了 | 合并了 |
| --- | --- | --- |
| 键集 | 少一个键 | **不变** |
| `filter(...).toEqual([])` | **红** | **绿（静默）** |
| 其它断言（`casts>0` / `fieldR>0` / `r2>r1`） | 可能红 | **全部绿** |

**合并比丢了更坏**：所有守卫都绿，而一个「释放发生了」的事实会被读成「场变强了」。
**报红前先问「是丢了还是合并了」；两条臂只差一个变量（释放哪个技能）就能回答。**

### 6ai. 「靠构造回避」**只写在散文里 = 没有断言**

两套 harness 都在避开同一个碰撞，而其中一套**唯一**把机制讲清楚的注释
（`formPressure.test.ts:1041-1052`，写得非常详细）**没有任何断言**。
⇒ 下一次编辑只要动一行装配，盲区就回来了，而**没有任何东西会响**。

**把回避写成断言**：把**每一个**会改变解析结果的装配各断言一次
（`{}` / `{A011:1}` / `{A011:1,G2_FROST:1}` / `{G2_FROST:1}` / **`{A011:1,G2_FROST:3}`**），
其中**「等级压过」的那一格必须写**（平局靠表序，等级差靠大小 —— 两条路径都会撞）。

### 6aj. `filter(x > 0)` 让**零命中静默消失** —— 取极值前先问**被滤掉的是什么**

G4 的实测行集在 `bossThreat.test.ts:1338` 被 `perShape.filter(shape => shape.hits > 0)` 过一遍，
结果直接喂 `:1363-1364` 的 `cheapestMove` / `heaviestMove`。发货臂上**三招里两招命中为 0**
（`circle` 0 / `cone` 0，只有 `line` 落 2–3 次）⇒ 过滤后**只剩 1 行** ⇒ 两个读数
**是同一个数**（`0.2206`），「有的招看得见、有的看不见」这个**分散度主张塌缩成单值**，
**而行里没有任何字段说丢了一行**。

**两条规矩**：

1. **零命中的占位 `0` 不是读数**。把不过滤的集合直接喂 `min` 会造出**假区间 `[0, 0.2206]`**
   （那个 `0` 是「没观测到」不是「这一招只花 0」）⇒ 显式可见的正解是
   **保留行 + 报 `hits: 0`**，或**保留过滤器但断言它移除了哪几行**（哪个形状、命中数是多少）。
2. **反解出来的量不是「遭遇的性质」**。同块的兄弟三元 `:1370`
   （`g4: phase1.length ? … : null`）在这棵树上取值域 = **`{null}`**：
   `phaseOfRaw`（`:79-82`）把相位**从伤害数额反解**，实测**每个非 `contact` 命中都反解出 phase 3**
   ⇒ `phase1` 恒空 ⇒ `true` / `false` **都不可达**。查证时**先分清是「没测到」还是「测到且不合格」**
   （这里两者同值）；而 `contact` 命中**确实**能到 phase 1 ⇒ 盲区是**形状行专有**的，
   「全程没有 phase 1」是错的叙述。**一个被判定字段可能没有读者**：
   `report.g4` 全库只有 `:1764` 读 `.required`，判定的那个字段本身空转。

**重块的 `it` 必须带显式超时**（漏写 = 默认 5s；33 局冷跑必超），且
**两个 `it` 各自冷跑同一批 = 双倍开销** ⇒ 合并 + 记忆化派生函数（本片 36.1s 跑完）。

### 6ak. 「重块」的判据不是「它慢」而是「它的墙钟依赖邻居」—— 以及三条配套规矩

`formPressure.test.ts:3294` 的 `it` 跑 `scan()` + `sweep()` + `radiusSweep()` = **270 次 `run()`**，
是**该文件唯一**一个三位数 `run()` 的块，而它**没写显式超时**：

- **单独跑 3.11s 绿**；全量（43 文件 / 11 worker，同批还有 30 分钟量级的 `bossThreat.test.ts`）
  ⇒ `Test timed out in 5000ms`。
- ⇒ **只报一次、复跑即绿的红，先量单独耗时再决定加余量还是查断言**。这里的答案是
  **并行争抢，不是断言错**。
- **同文件已有超时惯例就照抄**（`R2-F-BOSS-ADDS:3567` 就是 `}, 300_000);`），
  而**同一个坑上一片刚在 `bossThreat.test.ts` 踩过**（G4ROWS）⇒ 写重块的第一件事是**抄本文件惯例**。

**三条配套规矩**：

1. **读回的字段要先确认它是什么**。`castLog` 记的是 `event.shape`（**形状键** `'cone'`）
   **不是**招式名（`'旋风断军'`）；混用会让反事实算出 **61/61** —— 一个看起来很有力、实际是假的读数。
   **修法不是改数，是把「返回键」与「返回名」拆成两个函数**（名用于表与断言，键用于与生产比较）。
   **凡是「拿生产字段和期望值比」的地方，先把那个字段打印出来看一眼。**
2. **反事实要钉实测值，不要钉阈值**。断言 `[61, 58]` 与 `[59, 59]`（**跑出来的**），
   不是 `moved > 0.9 * total`。**阈值只证明「有变化」，实测值证明「变化是多少」** ——
   规则被改动时，后者会指出**移动了哪一格**，前者只会说「还是红的」。
3. **注释声称的机制 ≠ 代码实际依赖的机制**。`bossThreat.test.ts:249-250` 声称「后缀永不连续重复」
   靠 `(skillIndex + phase - 1) % 3`，实际只靠 `+1 % 3`。**解释一条性质前先找出它的最小充分条件**；
   多出来的那一项**必须有它自己的防守对象**，否则就是**把一个旋钮渗进了正交维度**
   （相位是难度旋钮，合法用途是缩放伤害/预警/速度/冷却；把它加进招式下标 ⇒ 顺序成了 DPS 的函数）。

### 6al. 「读数是一个连续量」是**最贵的默认假设** —— 先问**最小增量**

HORDE-BAND 要在「环半径」这个参数上找**中间档**（`120 → 150` 缓解 6 个形态，
`150 → 180` 再缓解几个 ⇒ 一档一价）。第一次写断言就把 `taken` 当成**连续伤害**，
于是「120 与 150 都干净」被读成「这两档等价」。

**实测**：`320/320` 个 `taken` 全部落在同一个格点上
`q = enemyDamage.EN001 × (1 − def/(def+softCap)) = 11.52 × 60/74 = 9.34054054054054`
（`combatMath.ts:146`，**bit-equal**），并且 `sim.player.incoming === 1`。
⇒ **`taken` 不是伤害总量，是「命中次数 × 单次接触伤害」** —— 一个**离散量**。

**三条规矩**：

1. **先问「这个读数的最小增量是多少」**。算法：拿两个相邻样本相减，问那个差是不是
   **某个可命名的量子**（这里是「一次接触」）。若是 ⇒ **它没有中间档**，
   参数的每一格要么全开要么全盲；此时**不该找「最佳值」，该报「占比」**
   （本片两候选的增益 = Boss 预算的 **0.18% / 0.27%** ⇒ 「可验证但不值得落地」）。
2. **浮点量子必须在派生处取整，不能靠断言容忍**。`taken / CONTACT_DAMAGE` 留下
   `23.99999999999998` ⇒ 断言处 `toEqual([24,…])` 必红（3 处）。**修法是把 `Math.round`
   放进派生函数**，而不是改成 `toBeCloseTo` —— 后者会把「差一次命中」也放过。
3. **「扫描床上恒定」是必须测量的断言，不是背景**。控制臂上 `reaper` 的 `ctrlClean` 是
   `[false,true,true,true,false,true,true,true]`（`DDCCCDCC`）—— **非连续集**。
   **它不是在说「数据脏」，而是在证明「这里不存在距离阈值」**：
   120 与 240 同为 3 次接触却分了干净/脏，**同一个读数在两格取同值 ⇒ 差异来自竞态，
   不是来自半径**。看到「同值不同果」先怀疑**另一个变量**，别急着调这个参数。

### 6am. 「既有仪器已经覆盖它」要**分臂各数一遍**

队列说「环半径这条带上没有对应物」—— **一半是假的**：
`radiusSweep()` 早在 `:3195` 就存在（十形态 × `RADII`），`:3307` 的块**已经断言**
「`120` 唯一」。真正缺的只有**控制臂**（`kit:false`）。

**两条规矩**：

1. **「缺仪器」的主张要分臂数**：本片 `SPECS` 的构造点有 **9 个**
   （`R2-F03 frostflame` 缺席），而 `control.horde` 被引用 **43 处、其中 34 处在 `expect` 里** ——
   「数一遍」不是修辞，是「`grep -c` 一下」。
2. **「既有断言」也要分清它断的是哪一臂**：kit 臂有带 ⇒ 不要重造；
   **控制臂没有 ⇒ 补的那把尺子只量控制臂**（不然两边混在一张表里，
   读出的「差异」其实一半是自己叠出来的）。
