## D1（§10.4）G8 的目标值是否可动 —— **保留 35%，允许手动轨道新增伤害**

**决定**：35% 不动。走 GDD P2-2 的「双轨制」，且允许它**抬高一局的总伤害上限**
（即 R1g-6 §8 说的「手动轨道必须新增伤害，不能靠重新分配」）。

**依据**：
- 35% 是设计意图的数值化 ——「玩家操作要对输出有实质贡献」。整改的起因就是
  「这局自己在玩」，把门槛降到 20% 等于把这个抱怨追认为设计目标，自相矛盾。
- `ROADMAP.md` 的冻结范围已经承诺「自动普攻，**手动移动、闪避、主动技、必杀**」。
  手动主动技**本来就在范围内**，只是没实现（G9 = 0，手动按钮从未触达任何术式）。
- R1g-6 §8 的代价曲线证明「重新分配」这条路走不通：只砍自动轨 ×0.6 →
  份额 18.75% 且胜率 100%→**18.18%**；越过 35% 的设置**一局不赢**。

**代价与配套**：新增伤害会让一局总 DPS 上升 ⇒ TTK 缩短 ⇒ **G3（60–90s）会破**。
所以本片必须**同时**重标定 `threatV2.bossHp`，两者是一枚硬币（同 R1g-5 的做法）。

## D2（§10.6）手动技能的 `dash(150)` 是否保留 —— **保留；且**不做**夹紧（原决定已由实测推翻）**

**原决定（R1g-7 动手前）**：保留位移，但夹到 `min(150, 到目标距离 - 65)`，不允许穿到 Boss 身后。

**实测（R1g-7 落地后，单一开关反事实：同种子、只切夹紧）**：

| journey | 夹紧（D2） | 不夹紧（现状） |
| --- | --- | --- |
| classic/`first` | 血线 **0.159**、30/33 胜、份额 39.07% | 血线 **0.408**、29/33 胜、份额 36.37% |
| evolution/`first` | 血线 **0.185**、**22/33** 胜、份额 41.02% | 血线 **0.447**、**33/33** 胜、份额 40.96% |

**结论：原决定被推翻，夹紧已回退。**

**为什么原假设错了**：
- 机器人的站位就是 65px，所以 `min(150, 65 - 65) = 0` —— 夹紧不是「缩短突进」而是
  **删掉突进**。而突进是**脱离手段**：`EvolutionCombat.dash` 的无敌帧（`p.inv`）
  与位移**无关地**照给，所以玩家丢的是那 150px 的**距离**，不是无敌。
- 于是 R1g-6 §7.2 的因果假设（「是 dash 造成了血线问题」）被**证伪**：
  把 dash 拿掉**才是**血线问题的成因。
- 夹紧对 G8 几乎无贡献（classic +2.7pp、evolution −0.06pp），代价却是
  evolution 少赢 **11 局**、两条 journey 的血线各掉 **25pp 左右**。
- G2（hpMin 25–60%）在回退后**恢复达标**（0.332 / 0.417，见下），
  它缩短的 TTK 由 `bossHp` 买回来（classic 15→**17.5**、evolution 34.5→**47.5**）。

**保留物**：`dashLength(length)` 仍是两条 journey 唯一的位移入口（生产实现 = 原样返回），
`manualDamage.test.ts` 里保留一个 test-local 开关可以随时复现 D2 的夹紧，
把这笔代价钉在测试里 —— 将来谁再加夹紧，就得在同一处付出同样的代价。

## D3（§10.5）G10 是否按 journey 分别计分 —— **是，分别计分**

**决定**：`evolution ≥ 6`；`classic ≥ 3`（形态 0 + 觉醒 0，它的转折点应来自
**路线 + 羁绊 + 宝箱 + Boss 战利品**）。

**依据**：
- classic 结构上拿不到形态与觉醒（`RunEvolution` 只在 evolution 局创建，
  `GameCore.ts:67`），所以拿同一个 6 去卡 classic 是拿一个**不可达**的门槛在扣分。
- 但 GDD §4 的本意是「每局都要有足够多的决策节点」，classic 不该被免检 ——
  所以不是「不计分」，而是**换一组它够得着的来源**。
- R1g-6 实测 classic 转折点 = **0**（33 局里 2 局拿到 1 个进化，中位 0），
  这本身是设计信号，按 D3 记为该 journey 的缺口。

**R1g-7 实测复核（重要，本决策的两条门槛都**未**达到）**：

| cell | 转折点中位 | 全距 | 构成 |
| --- | --- | --- | --- |
| evolution/`first` | **4** | 4–6 | 形态 1 + 觉醒 1 + 进化 2（尾部 3）+ 融合（5/33 局） |
| evolution/`unlock` | **2** | 0–4 | 形态 + 觉醒，进化几乎拿不到 |
| classic/`first` | **0** | 0–1 | 33 局里 4 局拿到 1 个进化 |
| classic/`unlock` | **0** | 0 | 拿不到任何转折点 |

- evolution 的中位从 R1g-6 的 5 掉到 **4**（进化从 3 条变 2 条）——手动轨道改变击杀分布，
  闸门被动来得更晚。**但最大值从 5 升到 6**：第 6 点第一次在尾部出现，说明它是
  **节奏问题而不是结构问题**。
- classic 的天花板实测是 **1**，D3 给它定的 3 需要「路线 + 羁绊 + 宝箱 + Boss 战利品」
  这四类来源 —— 它们目前**只存在于 evolution 路径**。所以 classic ≥ 3 是
  **R2 的工作项**，不是本片能兑现的；本片只把它记成缺口。
- **结论**：D3 作为**计分规则**成立（classic 不再被结构性地判零），
  但两条门槛的**达成**都还没发生，两者都写进 `STATE.md` 的未决风险。

## D4（§10.3）G7 的缺口在等级预算 —— **不改门槛，改宝箱候选池的排序**

**决定**：G7 的目标改为「单局内融合候选**必然**出现 ≥1 次」（可达性契约，100% 种子），
达成率单独报。实现方式是让第 4 次宝箱（R1g-5 已加，240/300s）**优先给融合候选**。

**依据**：
- R1g-5 §9.2 与 R1g-4 §3 已经排除「门槛」这条杠杆：三种 gate 策略下**没有任何一种**
  给出过融合候选，而 4/44 局在结束时手里握着完整父对 ⇒ 缺的是**宝箱次数**，不是门槛。
- 现状 2/44 = 4.5%，是抽奖。加门槛只会更抽奖。

**归口**：本决策的**实现**属 R2-D（200 种子构筑报告）的范畴，本片只记录，不改代码。

**R1g-8 实测复核（重要，本决策的前提被证伪了一半）**：

| 前提 | 判定 | 依据 |
| --- | --- | --- |
| 宝箱候选池是**均匀抽取** | **假** | `TimedChests.claim()` 先 push 全部合格融合、再 push 进化、再补 filler，`slice(0,3)`。**无随机数参与**，且这是 `chests-oracle.json` 最后一例**早已钉死**的遗留行为 |
| 一局能带两个父件走到第 4 次宝箱 | **真** | 77 局里 **24** 局在某个宝箱上同时握着两个父件 |
| 可达融合只有 `F001`/`F004` 两行 | **部分为假** | **结构可达 4 行**：`F001` `F002` `F004` `F026` |

**验收（Scope 3 的 100%）未达成**：刻意策略 **20/33 = 60.6%**、自然策略 **3/33 = 9.1%**、
`growthPacing` 的 `focus` 策略 **1/11 = 9.1%**。

**缺口被重新归因**（本决策的实质修正）：

> 「融合是一次抽奖」这句话是对的，但**抽奖发生在升级候选池，不在宝箱候选池**。
> `Progression.validOptions()` 把 10 个主动技洗牌后 `slice(0, 3)`，
> 配方的第二个父件（`A054`，未拥有）要和另外 8 个未拥有主动技抢 3 个槽。
> 13 个 miss 里 **9 个**是 `A054` 根本没升到 Lv.5（自然策略下其中位等级是 **0**），
> **4 个**是升到了但在倒数第二次宝箱之后。

宝箱侧的规则本身是**满分**：308 个宝箱、24 个满足前提、**0 例外**。

**因此 D4 的实现方案（R2-D）从「改候选池排序」改为下面两条之一**（都需要设计决策，故不在 R1g-8 动）：

- **A. 让配方可达**：在升级候选池里给「本局已拥有主动技的配对」加权，
  或在 `validOptions` 层面保证「已拥有的技能」优先出现。
  代价：改变**每一次升级**玩家看到的候选，是全局 UX 改动。
- **B. 让配方可见**：图鉴 / 升级界面上标出「这个技能与 X 组合可融合」。
  代价：属 Out of scope 的「any UI」，且需要 R3-P01 图鉴先落地。

**不在 R1g-8 动的原因**：Scope 2 明令禁止改闸门 / 宝箱时刻 / `xpNeed`，
Out of scope 明令禁止 `activeSkills` / 融合表 / UI，而剩下的两条路都是**全局玩家可见**的改动。
按 R1g-7 的教训（「症状跟着数值走就用数值解决，不要用机制去锁一个数值产物」），
本片只做**测量与归因**，把选择权交回设计层。

## D7（G4）Boss 招式威胁度能否用 `threatV2.bossDamage` 达成 —— **不能；可达上限是目标的 27%，真杠杆是施放频率**

**决定**：G4 的「单招命中 ≥ 15% 生命」**不由 `bossDamage` 承担**。本片不动任何生产数值。
G4 的实现改为**结构问题**：把一局 31 次施放压到约 6 次、单招提到 15%（同样的总量、更少更大的招），
或把 G4 读成聚合口径 + 修单招可读性。两条都需要自己的切片。

**依据**（`bossThreat.test.ts`，374 局，`evidence/R1g-9/boss-threat-report.json`）：

1. **今天的单招代价是 1.05%–1.64% 生命**，不是 GDD §4 的「全招式合计 4.2%」。
   那个 4.2% 测于**遗留路径**（`incoming 0.44` + `def × .08` + 全局 0.28s 无敌帧）。
   在 `threat-v2` 下 Boss 单局造成 **432/763 = 56.6%** 生命、占全部承伤 **34.6%**，
   已是最大**一组**来源。所以「Boss 不构成威胁」在**总量**上早已不成立，
   不成立的是**单招可读性**——1.1% 的血条变化看不见，31 次累加成 57%。
2. **需要 14.31×**（最弱招 蛮王冲锋 相位 1）**或 9.17×**（最强招 旋风断军 相位 3）。
   而 G2 的 25% 地板把每一条臂都夹死：
   `browser` 臂只在 **0.6×** 上守住（0.363），**1.0× 就跌破**（0.127）；
   `dodge` 臂只在 **0.6× / 1.5×** 上守住（0.659 / 0.326），**2.0× 归零**。
   ⇒ **可达的单招代价上限 ≈ 4.09%，是 G4 目标的 27%。**
3. **G3 不是约束。** 1.5×–2.0× 的 dodge 臂 TTK 是 72.7s / 73.6s，仍在 60–90s 内；
   把臂打穿的是 G2（2.0× 时 33 次 `defeat` 对 5 次 `timeout`）。
4. **`bossDamage` 不是纯招式旋钮。** `FirstBoss.damageScale` 同时乘体接触，
   14.31× 下 contact 占 Boss 自身伤害 **71.5%**、每 1.1s 打掉 **18%** 生命。
   即使 100% 躲开三招，贴身仍会被打死。
5. **算术上的根因**：31 次施放 × 15% = **465% 的生命**。回避率 74%（`dodge` 臂，移动-only 的下限）
   ⇒ 约 8 次命中 × 15% = **120%**，仍必死。要守住 25% 地板需要约 **84%** 的回避率。
   **G4 与 G2 在「每 2.2 秒放一次招」这个频率下互斥，与仪器无关。**

**仪器侧的关键事实**：`tests/settlement.spec.ts` 全文没有 telegraph 引用（grep 核实），
`browser` 臂的 `core.move` 实参只有 `(0,0)` 或指向 Boss——**它没有任何读预警的代码路径**。
它的回避率 **21.1%** 全部是副作用：Boss 冲锋 776px 后走回来，玩家以 240px/s 追击，
追击期间脚下的红圈被甩在身后（逃掉时中位移动 121.8px，命中时 **0.0px**）。
`dodge` 臂（同一玩家，只加了「离开包含自己的预警」）读 **74.0%**。
⇒ 那 53pp 就是「仪器在玩」与「仪器在读预警」的差距。

**三条候选杠杆与代价**：

| 路 | 内容 | 代价 |
| --- | --- | --- |
| **A（推荐）** | `castCd` 2.62/2.24/1.86s → 约 11s，31 次 → 约 6 次，单招 15% | 战斗质感变化；「三招连中即死」变成真正可能——**正是 GDD 的意图** |
| B | GDD §5 P0-4 的 maxHp 比例（0.18/0.22/0.26） | 大了一个量级：74% 回避下约 8 次 × 22% = **176%** 生命，仍必死。必须与 A 一起降频 |
| C | 把 G4 读成聚合 + 修可读性（硬直/击退/读数/叠层易伤） | 叠层易伤是新机制 ⇒ R2-F / R3-M03 |

**为什么不在本片动手**：`TASK.md` Scope 1 的条件是「若 step 0 说可达」，step 0 说不可达；
A 与 C 都要改 `castCd` / 新增机制或表现，都不在 Scope 1 命名的 `threatV2.bossDamage` 上。
按 R1g-7 的教训——**症状跟着数值走就用数值解决，不要用机制去锁一个数值产物**——
这里的症状**不**跟着单个数值走（G4 与 G2 在 31 次施放下算术互斥），
所以需要的是**结构改动**，应当有自己的切片与自己的证据。

**若后续要走 A，前置条件是仪器先修**：`settlement.spec.ts` 的机器人必须先学会读预警，
否则 Playwright 的自然胜利用例会红，而红的原因是仪器而不是游戏。

## D8（G4 / D7 路径 A）拆开共享旋钮 + 加节奏轴之后，15% 是否可达 —— **可达，落地数值已给出；但被仪器保真阻塞**

**决定**：**D7 的「不可达」结论只在「只用 `bossDamage`」这一个前提下成立，本片把它推翻。**
`threatV2` 新增 `bossSkillDamage` / `bossContactDamage` / `bossCastCooldown`（缺省 1，逐字节不变），
落地数值定为 `bossSkillDamage = bossCastCooldown = 14.31`、`bossHp` = **19.25 / 52.25**（现值 ×1.1）。
**本片不落这三个数值**，因为 TASK 的 Scope 3（仪器保真）是它自己的前置条件；
数值与证据交给 **R1g-11**，与仪器修复同片落地。

**依据**（`bossThreat.test.ts`，814 局，`evidence/R1g-10/boss-cadence-report.json`）：

1. **拆旋钮是实测必需，不是整洁度。** 本片第一版用 `startsWith('B001-')` 选技能源，而
   `'B001-contact'` 也满足该前缀 ⇒ 体接触被乘 14.31 ⇒ **玩家在 Boss 第一次施放前就被打死**
   （施放/局 **0**、Boss 承伤/局 **573**、82 HP / 1.1s）。D7 依据 4 说的「`bossDamage` 同时乘体接触」
   不是理论顾虑，是**能不能跑起来**的问题。
2. **对角线把单招推到 15%**：设计值 1.048% × 14.31 = **15.00%**（`g4Met = true`），
   施放/局 35 → **2**，观测单招中位 1.6% → **24.0%**。
3. **诚实的那条臂上 G2 与 G3 都能守住，但要 `bossHp` 补一刀**：
   `bossHp` ×1.0 → hpMin **0.272** ✓ / TTK **55.1** ✗；**×1.1 → 0.276 ✓ / 60.2 ✓ / 胜率 77.3%**；
   ×1.2 → 0.143 ✗ / 67.2 ✓。**×1.1 是这一区间里唯一的解，而且比现值更宽松。**
4. **设计总量守恒，玩家实际承受量不守恒。** dodge 臂的招式承伤/局从 **94.7 HP 单调降到 0**，
   因为施放稀疏 ⇒ 玩家在 65px 站定而不是追 776px 冲锋 ⇒ 预警出口变短 ⇒ 回避率 74.0% → 99.0%。
   **「更可读」同时意味着「更轻松」**，所以落地必须用 `bossHp` 把时间买回来（第 3 条）。
5. **杠杆的两半不可互换**（k=14.31 各关一半，dodge 臂）：只加伤 = **0% 胜率、血线归零**（R1g-9 的死胡同）；
   只降频 = 一局 1 招且 100% 被躲开（不是威胁）；只有成对使用才是战斗。
6. **体接触成为剩下唯一的 Boss 威胁**：176 HP/局 = 23% 生命条，占 Boss 伤害约 2/3。
   它不随 `bossSkillDamage` 缩放，所以 ×1.2 时战斗拉长、血线反而塌到 0.143。

**为什么本片不落数值**：`browser` 臂在 G4 数值下是 hpMin **0.062**、胜率 **51.5%**，
`g4Breaks.browser = ["G2 floor","G3 window"]`。`tests/settlement.spec.ts` 的

本片完成了 (b) 的**声明**部分（报告与 `IMPLEMENTATION.md` §0），(a) 与数值一起给 R1g-11。

**R1g-11 的硬顺序**：① 修仪器（(a) 或把读数迁走并改 `settlement.spec.ts` 的期望）；
② 落 `bossCastCooldown = bossSkillDamage = 14.31`、`bossHp = 19.25 / 52.25`；

**与 D7 的关系**：D7 的路径 A 成立；D7 的「可达上限是目标的 27%」应读作
「**`bossDamage` 单独**的可达上限是 27%」。D7 的路径 B（GDD §5 P0-4 的 maxHp 比例）与
路径 C（聚合口径 + 可读性）仍然有效，但 B 必须与 A 一起降频，C 需要新机制（R2-F / R3-M03）。

## 附：R1g-7 落地后由实测推翻的**第二处实现**（相位驻留 + `holdHp`）

这一条不在 D1–D6 里，因为它不是「待决问题」而是**实现手段**；它和 D2 一样被自己的实测推翻。

**原手段**：`FirstBoss` 加「相位最短驻留 6s + 一次只升一阶」，并在 `CombatSimulation.hitBoss`
里把 HP 托在 1（`holdHp`），使 G3 的「三阶段各至少一次」成为**规则属性**而不是数值属性。

**为什么被推翻**：

1. 它针对的 **1.7s 第二阶段**是在 **D2 夹紧的世界**里测出来的。夹紧回退、`bossHp`
   重标到 17.5/47.5 之后，六个 cell 的相位中位全部 ≥ 20s，**不需要托底**。
2. 它引入一条**玩家不可见的规则**：Boss 在相位切换后最长 6s 内**不可被杀**。
   实测代价 = **9 个测试**跨 `bossLifecycle.test.ts` / `firstBoss.test.ts` /
   `settlementFlow.test.ts` 被打破（它们的合法「一击必杀」失效）。
3. 相位预算本来由 `bossHp` 承担（R1g-3 的设计），再加第二套机制是**重复保险**，
   而重复保险的代价是给规则引入一条没人看得见的例外。

**结论**：`holdHp` 与 dwell **全部移除**，相位结构回到「按 HP 比例推进 + 一次只升一阶」。
`bossBudget.test.ts` 的 `gives every phase a turn` 在移除后仍然通过。

**两条回退的共同教训**：本片两次试图用**新机制**去修一个**只在特定数值下出现**的症状，
两次都被单一开关反事实打回。症状跟着数值走，就应该用数值解决（`bossHp`），
不要用机制去锁一个数值产物。

## D10（G2 / R1g-12）杂兵接触表：K 是唯一自由度吗，该降到多少 —— **K = 1.44；两条路线都清线；代价是「不躲必死」降级为「不躲拿不到 G2」**

### 前提（Scope 0 核实，三条全部成立）

1. **`enemyDamage` 是杂兵唯一旋钮**，且在**两处**被消费：`CombatSimulation.ts:318` 的远程弹丸
   （`dmg: enemy.damage`）与 `:323` 的接触（`this.hurt(enemy.damage, enemy.id)`）。没有第三条路径。
2. **表只有一个自由度 K**：`threatV2.enemyDamage[id] === firstStage.enemies[id].damage × K`，
   20 个键**全部逐位成立**，实测 K ≡ **1.8**。所以「扫一个倍率」不是简化，是这张表的实际结构。
3. **`firstStage.rule.incoming = 0.44` 在 threat-v2 下不被读**（`spawnRules.ts:74`
   `enemy.damage *= threat ? 1 : firstStage.dmg`，模型内 `incoming: 1`）⇒ 改它既不在范围内，
   也不会影响模型。

`createEnemy`（`spawnRules.ts:48`）每次生成都读 `threat?.enemyDamage[id] ?? cfg.damage`，
所以**改 live 表 = 改发货规则**，一次扫描就是发货读数。

### 决策

**G2 是双侧目标**（血线中位必须落在 **[0.25, 0.60]** 带内），而扫描曲线单调 —— 两半分别卡住窗口两端：
**classic 被 0.60 天花板卡住**（K ≥ 1.62 才进带），**evolution 被 0.25 地板卡住**（K ≤ 1.44 才进带）。
窗口 = **K ∈ [1.44, 1.62]**，取**最小改动** **K = 1.44**。

| K | classic 血线 / 25分位 / 胜 | evolution 血线 / 25分位 / 胜 | 静止玩家死亡 |
|---|---|---|---|
| 1.80 | 0.280 / 0.095 / 28 | **0.147** ✗ / 0.000 / 20 | 38.5s / 34s |
| 1.62 | 0.421 / 0.281 / 31 | **0.170** ✗ / 0.000 / 22 | 40.7s / 36.3s |
| **1.44** | **0.455** / 0.303 / 30 | **0.364** / 0.191 / 28 | 43.8s / 37.9s |
| 1.26 | 0.582 / 0.464 / 26 | 0.478 / 0.285 / 29 | 48s / 40.1s |
| 1.08 | **0.609** ✗ / 0.433 / 30 | 0.492 / 0.155 / 27 | 55.1s / 41.9s |
| 0.90 | 0.637 / 0.517 / 32 | 0.599 / 0.413 / 31 | 74.2s / 47.1s |

K = 1.80 那一行**复现 R1g-11**（0.280 / 0.147），这是扫描读的是发货规则的证明。冻结在
`evidence/R1g-12/sweep.json`。

### 为什么不是别的旋钮

- **Boss 旋钮全部 Out of scope**（R1g-12 的 TASK 明确封了 `bossHp` / `bossDamage` / `bossSkillDamage`
  / `bossContactDamage` / `bossCastCooldown`），而且 R1g-11 的单一开关反事实已经证明**够不着**：
  归零 `enemyDamage` 把 evolution 抬到 0.839 / 33 胜 33，而 Boss 只占 137–175 HP/局。
- **`spawnRadius` / `bossContactInterval` / `incoming`** 同样被封，且都不是杂兵伤害的旋钮。

### 代价（本片真正的设计后果，→ **R1g-13**）

R1g-9 记录的设计事实是「**一个不读预警、不按闪避的玩家必死**」（`browser` 臂 hpMin **0**、约 41% 胜）。
把杂兵表降 20% 之后，同一臂读到 **0.202**（G4 行 **0.165**）—— **仍低于 G2 的 0.25，但不再归零**。
也就是说：**「必须躲」从绝对约束降级成了分档惩罚**。

本片**不修**这一点，因为修它只能动 Boss 旋钮（全部 Out of scope），或者改 G4 的措辞。
按本项目的规矩（「不要用新机制去修一个只在特定数值下出现的症状」，R1g-7 两次被单一开关反事实打回），
这里既不回退 K（那会让 evolution 重新掉破 G2），也不动 Boss；而是**入队 R1g-13**，把

## D11（G4 / R1g-13）不躲的代价要不要重新挂钩到 Boss 招式 —— **不要；(b) 分档惩罚是正确设计，措辞从「不躲必死」改为「不躲的死亡率 12.1% → 27.3%」**

Base: R1g-12。输入：`evidence/R1g-12/boss-hud-arms.json` 与 `IMPLEMENTATION.md` §3 / §6。
本片**零生产改动**。

### 前提（Scope 0 核实，三条全部成立）

1. **「不躲」的代价里四分之三来自杂兵，不是 Boss。** `browser` 臂（不读预警、不按闪避）单局承伤：
   Boss **319** HP（招式 150 + 体接触 162）vs 杂兵 **996** HP ⇒ Boss 份额 **25.25%**
   （`bossShareMedian 0.2525`）。
2. **招式侧没有向上空间。** G4 的定义是「**最弱招** ≥ 15% 生命」，`bossSkillDamage = 14.31` 正好把它
   钉在 15.00%，且 `TASK.md` 明说 G4 的定义不许动 ⇒ **可躲的那部分伤害是常数**。
3. **体接触不可读、也不靠读预警躲。** 它由 `bossContactInterval`（1.1s）驱动，站得近就吃；
   唯一的自由旋钮是 `bossDamage 0.6 × bossContactDamage 0.8`。

### 决策：**(b)** —— 分档惩罚是正确设计；不动任何数值

R1g-9 的原话是「一个不读预警、不按闪避的玩家**必死**」。这句话在 R1g-12 的表上**不再成立，
但它降级后的版本仍然成立，而且更健康**。按 `boss-hud-arms.json` 的 `losses` 分解（66 局/臂）：

| 臂 | 血线中位 | 胜率 | **败北（战死）** | 超时 |
|---|---|---|---|---|
| `hud`（读预警 + 按闪避） | **0.449** | 87.88% | **8/66 = 12.1%** | 0 |
| `browser`（不读预警、不躲） | **0.202** | **71.21%** | **18/66 = 27.3%** | 1 |

**不躲让战死率从 12.1% 涨到 27.3%（2.25×），血线掉 24.7pp，胜率掉 16.7pp，并跌破 G2 下沿。**
这不是「惩罚消失了」，是「惩罚从悬崖变成了斜坡」。而斜坡是**更**好的设计：

- 悬崖（必死）让「一次没躲到」等于「这局白打」，玩家学到的是**放弃**；
- 斜坡让「躲得好」有正收益（战死率减半）而「不躲」仍然可玩（71% 胜）——梯度可感知、可选择；
- R1g-11 已经实测过悬崖的代价：落地前一个**认真读预警**的玩家 **66 局里 64 局超时**，
  血线 0.761 却打不死 Boss ⇒ **「读懂了会输」，最优解是站桩硬吃**。悬崖把「躲」变成了负收益。

### 为什么 (a) 不可行（算术 + 设计两条）

**算术**：要把 `browser` 从 0.202 推到归零，需要再扣 ≈20% 生命 ≈ **152 HP/局**。招式侧被 G4 钉死，
只能全压在体接触上 ⇒ `bossContactDamage` 0.8 → **≈1.55**（×1.94）。

## D15（仪器 / R2-F-BOSSPHASE）招式下标该不该含相位项 —— **钉住，不改生产；修法留作 O2/O3/O4 供设计裁定**

**问题**：`FirstBoss.ts:106` 用 `config.mechanics.skills[(boss.skillIndex + boss.phase - 1) % 3]` 选招，
而 `boss.phase`（`:70`，`ratio <= .35 ? 3 : ratio <= .70 ? 2 : 1`，`ratio = hp / maxHp`）
随 **Boss 剩余血量**推进，也就是随**玩家已经打出的伤害**推进。`boss.skillIndex` 本身
（`:105`，`(skillIndex + 1) % 3`）是一条干净、可学的三步循环；**加上相位项之后，同一个施放序号
会解析成不同的招式**，取决于这一局的血量轨迹。

**现场（逐字引）**

1. `:105` `boss.skillIndex = (boss.skillIndex + 1) % 3;`
2. `:106` `const [type, name] = config.mechanics.skills[(boss.skillIndex + boss.phase - 1) % 3]!;`
3. `:70` `const ratio = boss.hp / Math.max(1, boss.maxHp), phase = ratio <= .35 ? 3 : ratio <= .70 ? 2 : 1;`
4. 表（`firstBoss.json.mechanics.skills`，常量）：槽 0 `circle` 震地斩 / 槽 1 `line` 蛮王冲锋 /
   槽 2 `cone` 旋风断军；相位名 `巨斧压境 / 蛮王狂怒 / 震岳绝境`。

**相位有两个角色，只有一个是非法的**

- **合法（承重，必须留）**：`:107` 招式伤害 `13 + phase * 4` 与 `delay max(.55, .95 - phase*.08)`；
  `:111/:118/:121` 预警半径 `86 : 70`、冲刺宽 `54 : 44`、扇形 `230 + phase*25` / 张角 `.72π : .55π`；
  `:97` Boss 速度 `38 + phase*7`；`:124` 冷却；`:103` 接触伤害 `11 + phase*3`。**相位让战斗变难。**
- **非法（本片的缺陷）**：`:106` 把相位**加进招式下标**，于是**顺序**随血量改。

**实测（发货 `hud` 臂：`bossDamage 0.6` / 33 种子 / `NO_CADENCE` = 发货表；中位 2 次施放）**

1. 众数序列 `2:cone > 3:line`：classic **24/33**、evolution **28/33**。
2. **偏离的四局 `classic` 正是 DPS 不同的局**：seed 19/27/29 首次施放仍在相位 1
   （`hpFrac` 0.4027 / 0.4983 / 0.7461）⇒ 第一刀是 `蛮王冲锋`（槽 `(1+1-1)%3 = 1`）；
   seed 20 唯一一次出手已落在相位 3 ⇒ `3:circle`。**同一个 `skillIndex = 1`，两种不同招式。**
3. **反事实（决定性）**：把每次施放的相位强制为 1（即把表当纯 `skillIndex` 循环），
   形状被改变 **classic 58/61（95.08%）**、**evolution 59/59（100%）**
   ⇒ **相位项不是舍入细节，它规定了玩家看到的几乎所有招式。**

**相位项在防什么 —— 什么都不防**

`% 3` 无论有没有相位项都在 ⇒ **不防越界**。它唯一的效果是把顺序从 `skillIndex` 平移 `phase - 1` 格，
而 `phase ∈ {1,2,3}` 让平移量**每场都在变**。`skillIndex` 单独就已经保证**相邻两刀永不重招**
（`+1 % 3`）—— 那正是 `bossThreat.test.ts:249-250` 的注释所依赖的性质，**但那条注释把机制归因
