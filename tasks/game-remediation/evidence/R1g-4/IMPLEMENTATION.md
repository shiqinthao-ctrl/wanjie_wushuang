## 3. G7 的根因：不是门槛，是宝箱次数

融合要求**两个**父条目在某次宝箱**之前**都已进化，而 `TimedChests` **每次宝箱只给一次选择**：

1. 3 次宝箱（90 / 210 / 300s）⇒ 单局最多 3 个进化；
2. 最早能出现融合的是**第 3 次**宝箱，且要求第 1、2 次拿到的**恰好是一对父条目**；
3. 44 局逐局追踪（`growth-report.json` → `trace`）：**没有任何一次宝箱的候选里出现过融合**
   （`chestsOfferingFusion = 0`，断言已钉住）；
4. 但 **4 局在结束时确实凑齐了一对**——`first 1` / `first 25` / `focus 1` / `focus 25`
   都是 `E003 + E054 → F004`；只是**第二个父条目是在最后一次宝箱才拿到的**。

**⇒ 再加一次宝箱就能开出融合。** 建议下一片在 `paced` 档案里把 `chestAt` 从
`[90, 210, 300]` 扩到 4 次（例如 `[90, 165, 240, 300]`），**`legacy` 档案保持
`[90, 210, 300]` 逐字节不变**（`chests-oracle.json` 的对照因此不受影响）。

## 4. 本片发现的 3 处仪器缺陷

1. **宝箱选择会跳过融合。** 原写法 `Math.max(findIndex(evo), findIndex(fusion))`——
   `TimedChests` 把融合**排在进化前面**，所以进化总在更高索引，融合被系统性跳过。
   已改为「融合优先」。
2. **反事实重放的融合计数错。** 第 2 步的离线重放按**最终**进化集合数融合，把
   「永远不可能被提供」的融合也算进去了，因此预测「方案 A → 8/44 局有融合」。
   改成**按宝箱顺序**重放（每次宝箱先看融合是否已可用，再拿进化）后是 **0**。
   **这是第 2 步 `GROWTH.md` §5 的一个实质性修正**：方案 A 命中的是 G6，不是 G7。
3. **`bossBudget.test.ts` 从不开宝箱**（第 2 步发现，本片量化后果）——见 §5。

## 5. 后果：Boss 预算被打破（→ 下一片）

本片让 `apps/mobile-next` 的测试树**不绿**：`1344 passed / 2 failed`。两处失败都**由 `paced`
档案引起**，下面用两次受控实验把它钉死。

### 5.1 归因实验：把 `paced` 换回 `legacy`，两处失败同时消失

唯一开关是 `GameCore.ts:63`（`PACING.legacy` = 3/8/5，与改造前的硬编码值逐位相同），
所以「`rules = threat-v2` × `pacing = legacy`」就是改造前的状态。

| 测试文件 | `pacing = legacy`（改造前） | `pacing = paced`（现行） |
| --- | --- | --- |
| `bossBudget.test.ts` | **7/7 全绿** | 6/7（1 红） |
| `skillCadence.test.ts` | **6/6 全绿** | 5/6（1 红） |

`classic` 的三个 cell 在两次运行里**逐位相同**（`11/11`、`9/11`、`11/11`，TTK 61.6 / 65 / 60.9），
只有 `evolution` 的 cell 变化 —— 证明这是**受控的单变量实验**，不是 RNG 抖动。

### 5.2 胜负率那处红：**是仪器缺陷，不是 paced**

`bossBudget.test.ts` 的 66 局里含 22 局 `evolution` 局（占 1/3），而 paced 把觉醒从
Lv.8（74.9s）推到 Lv.19（253.0s）。把宝箱打开（= 浏览器行为，见 §4 第 3 条）：

| 仪器 | 胜负 | 判定 |
| --- | --- | --- |
| 关闭（= R1g-3 现状） | **57 / 66 = 86.4%** | ✗ 低于 `>= .9` |
| **开启（= 浏览器行为）** | **63 / 66 = 95.5%** | ✓ |

⇒ **胜负率那处红完全是仪器造成的**：把宝箱打开，胜率回到 95.5%，比改造前（61/66 = 92.4%）
还高。paced 并没有让游戏变得不可赢。

### 5.3 但打开宝箱会打破 G3 —— 仪器保真与重标定是一枚硬币

同一实验的 TTK（`first` cell）：

| cell | 关闭宝箱 | 开启宝箱 | G3 窗口 60–90s |
| --- | --- | --- | --- |
| classic 390×844 | 61.6s | **55.4s** | ✗ |
| evolution 390×844 | 64.9s | **50.1s** | ✗ |
| classic 1280×720 | 65.0s | **51.4s** | ✗ |
| evolution 1280×720 | 64.2s | **51.4s** | ✗ |

同时「手机与桌面同长」的 Boss 生成时血量中位差从 2.1%（687 vs 673）涨到 **17.8%**（594 vs 700）。

⇒ **在 `bossBudget` 里，不开宝箱则胜率不达标、开宝箱则 G3 与视口一致性不达标 —— 两个方向
互为代价。** 所以 **仪器保真与 `bossHp` 重标定必须同片落地**，正是第 2 步 §7.2 说的
「不要分片各自改」。

**为什么本片不修。** `bossHp` 需上调约 15–20% 才能把四个 cell 从 50–55s 拉回 60–90s，
但更长的战斗会压低最低血线（现 0.38–0.46，断言要求中位 > 0.3）与胜率（现 95.5%，要求 ≥ 90%），
而且视口一致性还要另调 `bossDamage` / `bossPhaseSpawnInterval`。这是**多旋钮**搜索，
且必须与 `threatV2.json` 的数值改动一起落地 —— 动平衡前须先 scope 出 TASK（`AGENTS.md`）。
所以本片：

- **回退了** `bossBudget.test.ts` 的 `claimChest` 修改，只留下一条 `KNOWN FIDELITY GAP` 注释；
- 把量化结果留在 `growthPacing.test.ts` 的 `chestGap`：**关闭 71.3s / 开启 49.0s**（同 11 种子）。

### 5.4 `skillCadence` 那处红：**是真实的尾部，不是仪器**

同一实验里，`evolution @390×844` 的 `unlock` 驱动即使**开着宝箱**仍然丢 seed 15
（`lost ["15:timeout"]`）。所以这处红**不能**靠修仪器消掉。

机制（逐帧诊断，seed 15）：`bossAt` = 270s，`bossAt` 时玩家 **Lv.18**、形态已选（Lv.10）、
**尚未觉醒**（觉醒门槛是 Lv.19），最终在 **360s 超时于 Lv.18**。改造前同一局在 Lv.11 @137s
就觉醒了，280.7s 通关（最低血线 0.899）。

⇒ **G5 的觉醒窗口（240–300s）与 R1g-3 的 Boss 生成时刻（270s）重叠。** 中位（253.0s）只比
Boss 早 17s；尾部（320.6s / 346.8s）则在 Boss 战中段才觉醒。这是**两条规格之间的结构性张力**，
不是调一个数能解决的 —— 见 §8.2。

## 8. 交接：R1g-5 规格

### 8.1 四件事（必须同片落地）

1. **修仪器**：`bossBudget.test.ts` 补 `claimChest`（保真度 —— 浏览器每次都点「宝箱 领取」）。
   预期：胜率 86.4% → **95.5%**，`bossBudget` 的胜负率红自动消失。
2. **重标定 `bossHp`**：仪器修好后四个 `first` cell 掉到 50–55s，需上调约 **15–20%**
   拉回 G3 的 60–90s。同时盯住两条附带断言：
   - 最低血线中位 > 0.3（现 0.383–0.456）；
   - 胜率 ≥ 90%（现 95.5%）。
3. **修视口一致性**：开宝箱后「手机与桌面同长」的血量中位差涨到 **17.8%**（594 vs 700）。
   先判断这是**真分歧**还是 **11 个种子太少**造成的分位噪声 —— 建议把该断言的种子集扩大
   （11 → 33），再决定是否动 `bossDamage` / `bossPhaseSpawnInterval`。
   **不要**在没有扩种子的情况下直接改数值。
4. **`skillCadence.test.ts` 的口径**：它的 winnability 断言是**单种子**（seed 15）判定，
   而本项目已确认「单种子 A/B 完全不可用」（`bossBudget.test.ts` 的 docstring）。
   改为**多种子取中位**。改完仍可能红 —— 那就是 §8.2 的设计问题，不要用放宽断言掩盖。

### 8.2 需要产品/设计决策的一件事（不是工程能定的）

**G5 的觉醒窗口（240–300s）与 R1g-3 的 Boss 生成时刻（270s）重叠。**
中位觉醒 253.0s 只比 Boss 早 **17s**；尾部（320.6s / 346.8s）在 Boss 战中段才觉醒。
后果：弱构筑（`unlock`）在 Boss 战开始时**尚未觉醒**，90s 内打不完 → `timeout`。

三个可选方向（互斥，需选一个）：

| 方向 | 做法 | 代价 |
| --- | --- | --- |
| A. 把 G5 提前 | 觉醒门槛 Lv.19 → **Lv.17**（约 215s），留 ~55s 余量 | 偏离 GDD §4 的 240–300s 目标 |
| B. 把 Boss 推后 | `bossAt` 270s → **330s** | 前 330s 全是杂兵段，节奏变长；R1g-3 的窗口要重算 |
| C. 接受尾部 | 只保证中位；弱构筑在 Boss 战里觉醒 | G5 与 G3 的张力长期存在，弱构筑胜率上限被压低 |

**建议 A**：它把张力从「重叠」变成「有 55s 余量」，且只动一个门槛等级，不碰 R1g-3 的窗口。
但这是 GDD 目标值的改动，需先 scope 出 TASK。

### 8.3 G7 的收口（与本片 §3 一致）

`paced` 档案的 `chestAt` 从 `[90, 210, 300]` 扩到 4 次（如 `[90, 165, 240, 300]`），
**`legacy` 档案保持 `[90, 210, 300]` 逐字节不变**。证据：4 局在结束时已凑齐一对父条目
（`E003 + E054`），只是第二个父条目落在最后一次宝箱。
