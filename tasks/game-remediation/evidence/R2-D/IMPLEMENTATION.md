## 0. 前提核实（Scope 0，命令产出）

`TASK.md` 写着「20 行、9 行两部件都在池里、4 个可达融合」，并要求**不要相信这三个数**。
第一个 `it` 把它们**数出来并钉住**：

| 量 | 值 | 依据 |
| --- | --- | --- |
| `evolution.json` 行数 | **20** | `Object.entries(evolutionTable).length` |
| 两部件都在 `activeSkills`(10) + `passiveSkills`(11) 的行 | **9** | `E003 E011 E013 E015 E021 E026 E027 E054 SE001` |
| 两父件都可达的融合 | **4** | `F001 F002 F004 F026` |

**TASK 的三个数字是对的** —— 本片没有推翻它们。但 Scope 0 还多问了一步：
**这三个数是「英雄无关」的吗？** 答案是**是**，而且是构造性的：

`evolutionBuild(hero)`（`RunEvolution:8`）= `starter(hero).active` + 其余全部 `activeSkills`，
被动同理。所以三个英雄的池**成员完全相同（10 主动 / 11 被动）**，差别只有两处：

| 英雄 | 起手主动（表序） | 起手被动 |
| --- | --- | --- |
| H001 | `A003` `A011` | `P026` |
| H010 | `A011` `A054` | `P026` |
| H012 | `A015` `S001` | `P033` |

`it('Scope 0 …')` 逐英雄断言 `reachable == 结构集`、`actives == 10`、`passives == 11`，
并断言三份 `active` 列表**不是同一个字符串**（成员相同、顺序不同）。
⇒ **「9 / 4」是池的性质，不是某一局的性质。** 要问「一局能拿到什么」，必须实测。

## 1. 仪器声明（与数字同一句话）

- **种子**：`1..200`，三英雄**同一组**，写进报告。
- **驱动**：`fusionReachability.test.ts` 的 rules-only 玩家（原样照抄）：390×844、`threat-v2`、
  `evolution` 旅程、每秒按 `skill`+`ultimate`（Boss 在场时每帧）、HUD 闪避提示、`f` 交互，
  升级/宝箱/遭遇/Boss 掉落全部走 `GameCore` 的公开方法。浏览器孪生体是 `tests/settlement.spec.ts`。
- **升级策略**：`options[0]`（自然玩家取前排）。
- **唯一一处转向，且明写**：**形态**取 `options[seed % options.length]`。原因是旅程路径
  （`ruleset === undefined`）的形态候选**不洗牌** —— `RunEvolution.special` 在 `!ruleset` 时
  `return options`，直接返回表序 ⇒ 取前排的玩家在每个英雄身上**只会见到同一个形态**，
  报告就只描述 11 个形态里的 1 个。按种子轮转让每个形态拿到 50–67 个种子，
  满足 `TASK.md` 的「≥33 每格」下限。其余选择一律不转向。
- **`validOptions()` 不被调用**：它用本局的 RNG 洗牌，从 harness 里调它会**扰动它正在测的那一局**。
  所以「可选数」由快照**重算**（`eligible()`），并用 `shown === min(3, eligible)` 在
  **每一次普通升级**上交叉验证 —— 这让这个推导**可被证伪**，而不是把生产规则复述一遍。

## 2. Scope 1：逐英雄（这是本片的重点）

| | H001 | H010 | H012 |
| --- | --- | --- | --- |
| 形态分布 | 4 × 50 | 67 / 67 / 66 | 4 × 50 |
| 可达进化中**实际达成** | **9 / 9** | **9 / 9** | **9 / 9** |
| 每局进化数 | 2.44 | 2.44 | **0.70** |
| 至少一次进化的局 | 200 / 200 | 200 / 200 | 105 / 200 |
| 达成融合 | `F001` `F004` | `F001` `F004` | **`F026`** |
| 有融合的局 | 17 / 200（8.5%） | 12 / 200（6.0%） | 5 / 200（2.5%） |
| 中位等级 | 20 | 19 | 19 |
| 结局 | 胜 106 / 败 94 | 胜 65 / 败 133 / 超时 2 | 胜 0 / 败 174 / 超时 26 |

**发现 1（本片最重要的一条）：结构可达与实达是两件事，而且实达是「按英雄切开的」。**

4 个结构可达融合**没有一个英雄能全拿到**：

- `F001`（`E001`+`E054`）与 `F004`（`E003`+`E054`）要 `A003`+`A054` —— H001 起手有 `A003`、
  H010 起手有 `A054`，两者各差一半，实测都拿得到；
- `F026`（`SE001`+`E015`）要 `A015`+`S001` —— **H012 的两个起手主动**，实测 H012 拿到 5 次；
- 反过来，**H012 一次也没拿到 `F001`/`F004`**，**H001/H010 一次也没拿到 `F026`**。

⇒ `TASK.md` 的猜想成立，但比它写的更强：不是「`F026` 在 H012 下天然可达、在 H001 下不可达」，
而是**可达融合集被英雄切开成两块互不相交的子集**。所以「`reachableFusions` = 4」这句话
**不能被读成「一局有 4 个融合可拿」**；任一英雄的上限是 2（H001/H010）或 1（H012）。
这是**设计事实**，不是 bug —— 但它意味着 G7 的 100% 契约在任何单英雄上都**不可能**由
「四个融合」达成。

## 3. Scope 2：分布与偏差

| 量 | H001 | H010 | H012 | 说明 |
| --- | --- | --- | --- | --- |
| 升级次数 | 3795 | 3540 | 3506 | 共 **10841** |
| 可选数中位 / 最大 | 19 / 21 | 19 / 21 | 19 / 21 | 池是 10 主动 + 11 被动 |
| 展示数中位 | 3 | 3 | 3 | `slice(0, 3)` |
| **单个候选的可见率** | **15.46%** | **15.36%** | **15.44%** | `shown / eligible` |
| **解锁占比** | **22.71%** | **22.54%** | **24.70%** | 这一手买的是**没有的**技能 |
| 拥有主动中位 | 4 | 4 | 4 | 上限 6 |
| 拥有被动中位 | 3 | 3 | 3 | 上限 6 |
| **槽满的局** | **0** | **0** | **0** | 600 局里**没有一局**填满六个主动槽 |
| 每局路线数 | 1.90 | 1.80 | 1.83 | 12 条路线 |
| 宝箱 / 其中进化候选 | 753 / 655 | 756 / 629 | 744 / 166 | |
| 宝箱 filler | 1587 | 1627 | 2061 | `upgrade`/`gear` |
| **无效候选** | **0** | **0** | **0** | 按**可达子集**判 |

**「无效候选为零」怎么判的**（不是「看起来对」）：`run()` 在**每一次**升级与宝箱上逐项检查 ——

- 主动/被动候选必须**在该英雄的池里**（`evolutionBuild(hero)`）；
- 形态候选必须是**该英雄自己的**形态（`formTable.filter(form.hero === hero)`）；
- 路线候选的**技能必须已拥有且 ≥ Lv.3**，且不能是**已经选过的**那条；
- `recovery` 兜底**在旅程局里一次都不许出现**（它是 `ruleset` 专属）；
- 宝箱的 `evo` 必须在**可达集**里、`fusion` 必须在**可达融合集**里；
- 普通升级必须满足 `shown === min(3, eligible)`。

600 局 / 10841 次升级 / 2253 次宝箱 ⇒ **违规 0 条**。

**发现 2：路线系统对每个英雄都是「一条被强制的路线」。**

`volley` 在 H001/H010 各 **200/200**、`hunter` 在 H012 **200/200**。原因不是随机：
`special()` 取的是 `skillRoutes` **表序里第一条「技能已达 Lv.3 且还没选过」**，
而**起手主动天然最先到 Lv.3**（H001 的 `A011`、H012 的 `S001`）。所以：

- 每个英雄的**第一条路线是起手技能的路线**，100% 固定；
- 12 条路线里，每局平均只走到 **1.8–1.9 条**（第二条要等另一个技能爬到 Lv.3）；
- **`A013`/`A026`/`G2_FROST` 的路线只在玩家主动买这些技能时才可能出现**，而买不买由下一节解释。

**发现 3：六槽上限从来没有约束过任何一局。**

`slotSaturated = 0`（600 局），拥有主动中位 **4**。机制在 `pickTally` 里：
起手两个主动各被点到 **800 次**（= 200 局 × 4 级，即 Lv.1→5 全部点满），
**点满两个起手要花 8 次升级**，而一局只有约 **17.5 次**普通升级。
⇒ 自然玩家的等级预算几乎全花在「把已经有的点满」上，**上限 6 是空的**。
「槽满」这个验收项在本片**测到的是 0**，不是「没有测」。

**发现 4：`coreSkillLevel` 在旅程局里多数是 0。**

`RunEvolution.coreSkill()` 按形态查 `chapterCoreSkills`：H001 的 4 个形态指向
`A003` / `A021` / `G2_FROST` / `G2_FROST`，H010 的 3 个指向 `A054` / `S001` / `A013`。
`A021`、`G2_FROST`、`A013` 都不是起手技 ⇒ **中位核心术式等级 0**（H001、H010）。
H012 是 5，因为它的 4 个形态里有 2 个指向起手技（`A015`、`S001`），那两条必然点满。
`GameCore:193` 把这个字段写进战报 ⇒ **战报上「核心术式 Lv.0」是真实的读数，不是缺失**。
它是**展示层的缺口**（本片不改），不是规则 bug。

## 4. Scope 3：G7 的裁定（`DECISIONS.md` D21）

本片只**测**、只**定价**，不改 `evolution.json`、`bonds`、候选池、宝箱表。

**D4 的问题陈述在本片上被重新量化**：

| 量 | 实测 |
| --- | --- |
| 有融合的局 | **34 / 600 = 5.67%**（H001 8.5% / H010 6.0% / H012 2.5%） |
| 宝箱总数 / 其中融合候选 | 2253 / **34**（占全部宝箱候选的 1.5%） |
| 每局宝箱 | 3.76 |
| 单个升级候选的可见率 | **15.4%** |
| 解锁型选择占比 | **23.3%** |

**两条路的定价**：

- **A —— 升级候选池向「已拥有 / 可配对」加权。**
  机制上只有**一种**写法能影响自然玩家：把某个候选**钉到第 0 位**
  （`validOptions` 现有两个先例：`owned` 的 unshift、`signature` 的 splice）。
  代价三条：① `progression.ts` 目前**不 import 融合表**（只用 `journeySkillNames`），
  加权要它认识 `fusions.json` ⇒ **新增一条 progression → 数据表 的依赖**；
  ② 钉到第 0 位会**改变每一局、每一个玩家**看到的候选集；
  ③ 它会把 `growthPacing` 的 G6/G7 行与 `manual-report.json` 的自然局行**全部重新基线化**
  （R1g-7 已经为一次类似改动重基过一次）。
  ⇒ **不是一个 UX 小改，是一次需要单独切片的全局改动。**
- **B —— 图鉴 / 升级界面标出配方。**
  纯展示：数据已经在 `fusions.json` + `evolutionCatalog` 里，`RunGuide.vue:17` 已经把
  `bonds` 用「`needs` + 逐 tag 条件 + `${count}/2` + `detail`」渲染过一遍，配方卡是同一种渲染。
  **无规则改动、无基线作废。** 依赖 **R3-P01（图鉴）**。

**裁定：B 交给 R3-P01，A 定价存档、本片不建。**

**理由（用本片的数字）**：缺口不是**供给**，是**信息**。
同一套规则下，**会看候选的玩家**（D4 的 `fusion` 策略）达成 **60.6%**，
**取前排的玩家**达成 **5.7%** —— 差 10 倍，而候选池是同一个。
所以「把配方摆到玩家眼前」是唯一一条**不改变任何规则**就能动这个数的杠杆；
A 改变的是全局行为，且它的收益只有在玩家**已经知道要选什么**时才兑现。
若将来某片要冲 100% 契约，**A 是唯一能改变「取前排玩家」的杠杆**，
但必须带着 G6/G7 与自然局行的**重新基线**一起做，不能藏在测量片里。

## 7. 本片踩的坑（已入技能）

**`undefined === 0` 是假。** 第一版 `unlock` 写成
`(state.skills[pick.id] ?? 生产里的原样表达式) === 0`，而**未拥有的技能在记录里是「不存在」
不是 0** ⇒ `undefined === 0` 为假 ⇒ 报告在 600 局上写着 **`unlocks: 0`、`unlockShare: 0`**。
它长得完全像一条「玩家从不解锁新技能」的结论，而且和 `slotSaturated: 0` 互相印证 ——
**两个错的读数互相印证比一个错读数更危险**。真值 22.7% / 22.5% / 24.7%。
**修法**：`?? 0` 之后再比较；**判据**：任何「某字段 == 0」的计数，先确认那个字段在
「没发生」时是 `0` 还是 `undefined`。这与 D20 的 `!(undefined > 0)` 是同一个陷阱的第二次出现。
