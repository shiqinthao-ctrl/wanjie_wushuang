**结论：行为与代码逐条吻合，文案无矛盾，零生产改动。** 这是十形态里的第五个，也是
**第一个「召唤型」形态**（kit 的伤害主要来自分身，而不是弹道或场），同时是
**第一个不留任何场的形态** —— 因此共享的 `fieldR > 0` 可达性读数在它身上**恒为 0**，
本片必须为它换一个读数（见 §1）。

（bulwark 5 + frostlord 7 + frostflame 7 + phoenix 5 + legion 7）。
读数冻结在 `evidence/R2-F05/legion-pressure.json`；
**`bulwark` / `frostlord` / `frostflame` / `phoenix` 四份旧报告经复核数值逐位未变**（见 §7）。

> ⚠ 本目录的 `legion-pressure.json` **每次运行都会被覆写**。正文里的绝对值读在
> `threat-v2` + `paced`、600 帧、rank 1/2 这一组参数上。

### 与 F01..F04 的前提差异

前四片的 kit 都能落在「场」或「弹道」上，所以共享骨架的 `fieldR > 0` 可达性断言一直够用。
`legion` **没有任何场**（技能与必杀都只 `summon`），`fieldR` 结构性为 0 ⇒
本片必须把可达性换成别的读数。**换成了 `summonsPeak > 0`，并且在 `Outcome` 里同时记
`summonKinds`**（见 §1）。这不是「更弱」的替代：场可以被放下却一次都不命中，
而召唤物**只因本 kit 自己的施放而存在**；再加一条 `dealtBy['H010_CLONE'] > 0`，
「召唤出来了」与「召唤物真的打到了」就都钉住了。

### 行为逐条

1. **普攻是「2 道 ±0.115 rad 的投刃，`pierce 1`，两阶相同」**：一次 `basic()` 后
   `projectiles.filter(id === 'H010_BASIC')` 长度 = **2**（两阶都是 2）；每道
   `dmg = atk × .8`、`pierce = 1`、`explode = 0`、速度 **440px/s**；航向 **∓0.115 rad**。
   **这个扇形没有「正前方」那一道**（`phoenix` 是奇数 3/5 道，所以有一道正好在瞄准线上）。
   后果是可量化的：正前方的目标离每条弹道线的垂距是 `d × sin(.115) = 0.11478·d`，
   而命中判据是 `enemy.r 10 + shot.r 7 = 17px` ⇒ **正前方只在 148px 以内打得到**。
   断言用一对靶子钉死这条边界：**120px 掉血、170px 不掉血**（同一次施放、同一个瞄准）。
2. **`pierce 1` = 每条弹道打 2 个**：把三个靶子摆在**上弹道自己那条射线上**
   （200 / 380 / 560px），下弹道同样摆三个；一次 `basic()` 后跑 56 帧
   （0.933s，**短于自动普攻的 ≥1s 间隔**）⇒ **上弹道恰好 2 个掉血、下弹道也恰好 2 个**，
   560px 那两个不掉，而**用来固定瞄准的 170px 正前方靶子一次都没被碰**。
3. **技能 = 2（觉醒 3）个环绕分身，5s（觉醒 7s），且不留场**：`action('skill')` 后
   `renderState().summons` 长度 = **2 / 3**，全部 `id === 'H010_CLONE'`、`guard === false`、
   `dmg = atk × .65`、`manual === false`，**站在离玩家恰好 68px 的环上**；
   首击错峰 `tick` = **0 / 0.12 / 0.24**（`summon` 的 `tick: .12 * i`）。
   **环绕是可证伪的行为主张**：把玩家挪 260/180px 后，每个分身到玩家的距离**仍是 68px**。
   同一时刻 `sim.fields` 长度 **0**。
4. **分身在 0.8s 节奏上自行开火**：`update` 在每次开火后把 `tick` 重置为 **`.8`**，
   而 `tick` 是**生产字段** ⇒ 节奏是**读出来的**，不是从弹道数量反推的。
   实测：第 1 帧 `tick = [0.8, 0.1033]`、第 8 帧 `[0.6833, 0.8]`，对应
   **第 1 帧 1 发、第 8 帧 2 发** `H010_CLONE` 弹道（伤害 `atk × .65`、速度 420px/s、`pierce 1`）；
   t=0.13s 时 `damageBy.H010_CLONE` 仍是 `undefined`，t=0.88s 时 `> 0`
   —— **「开火」与「命中」分开断言**，因为分身的弹道要飞 232px 才到靶子。
5. **必杀 = 4（觉醒 5）个额外分身 **加** 16 道火羽**：`player.ult = 100` → `action('ultimate')` 后
   `renderState().summons` 长度 = **4 / 5**（`id === 'H010_R_CLONE'`、`life = 7`、
   `dmg = atk`（**满攻击，不是 .65**））；同时 `projectiles.filter(id === 'H010_R')` = **16**，
   航向间隔 π/8、速度 340px/s、`dmg = atk × 2.4`、`pierce = 2`、`explode = 65`。
   行为验证：四个正方向 200px 的靶子**全部掉血**（正对第 0/4/8/12 道）；`sim.fields` 长度 **0**。
6. **觉醒动三处**：技能分身 2→3、技能分身 life 5→7、**必杀分身 4→5**；
   **必杀火羽 16 道两阶相同**（`:94` 完全不读 `v.rank`）。在**首领格**这一项有可测价值：
   **22807.65 → 28430.00（+24.65%）**。

## 5. 规则发现（都进队列，不在本切片改）

### 5.1 必杀**同时**是「召唤」和「弹道」——两条都执行

`:85` 与 `:94` 的关系不是「二选一」：

```ts
if (v.heroId === 'H012' || v.formId === 'legion') this.summon(`${v.heroId}_R_CLONE`, …);  // :85  ← 普通 if
if (v.formId === 'frostflame') { … }
else if (v.formId === 'windwarden') { … }
…
else if (v.heroId === 'H010') for (let i = 0; i < 16; i++) s.projectile(…);                 // :94  ← legion 也走这里
else { s.arc(260, …); s.field(id, p, 180, p.atk * .6, 4, true); }                           // :95
```

`:85` 是**独立的 `if`**，`:94` 是**另一条链**上的 `else if`，而 `legion` 的 `heroId` 就是 `H010`
⇒ 两条都命中。实测：必杀后**既有 4/5 个 `H010_R_CLONE`，又有 16 道 `H010_R`**。
这一条与 R2-F04 §5.1（`phoenix` 以为会走到 `:95` 的跟随火域、实际被 `:94` 抢位）
**是同一个 `else if` 链的两面**：一条链的相邻两行，既能**吞掉**不该走的默认分支，
也能**放行**看起来互斥的两件事。**读 `if`/`else if` 链时必须逐行确认前一条是 `if` 还是 `else if`。**

### 5.2 必杀在 10 秒窗口里**赚不到**，不给就测不到 kit 的一半

`hit` 只在**击杀**时充能：`player.ult += enemy.elite ? 8 : 1.4`（`CombatSimulation:240`），
**没有任何时间充能**。十秒窗口能摆出的敌人上限是敌群格的 12 只 ⇒ **最多 16.8 点**。
实测：不加干预时**八格 `ults` 全为 0**，而必杀贡献了敌群格 6067.98 里的 **5573.21（91.8%）**、
首领格 22807.65 里的 **14110.70（61.9%）**。
⇒ 一个「一半伤害在必杀上」的 kit，**不能用一个结构上到不了必杀的窗口去验证**。
仪器因此加了 **opt-in 的 `ult: true`**（t=0 给一次充能），浏览器机器人玩几分钟自然到得了。
**缺省 false ⇒ 前四片报告不受影响**（§7 有逐位复核）。这条与「弱驱动不是保守，是另一个玩家」
是同一类账：**窗口决定了你能看到哪一部分 kit**。

### 5.3 普攻有**正前方盲区**（2 道扇形的必然结果）

`fan(id, 2, …)` 的两道落在 `(i - .5) * .23` = **∓0.115 rad**，**没有一道在瞄准线上**。
正前方目标离每条弹道线的垂距 = `d × sin(.115) = 0.11478·d`，
命中判据 `enemy.r 10 + shot.r 7 = 17px` ⇒ **正前方只在 148px 以内打得到**。
实测三处互相印证：
- 170px 的正前方靶子**一次都没被碰**（§2 行为 1、行为 2 里的「固定瞄准用靶子」）；
- **远程格 `basicDealt = 0`**（线停在 190–300px，远超 148px）；
- **首领格 `basicDealt = 4019.14 ≠ 0`** —— 因为首领就站在 **90px**，在 148px 以内。

对比 `phoenix`：它是**奇数** 3/5 道，`i = (n-1)/2` 那一道正好在瞄准线上，所以没有这个盲区。
**这是「形态道数奇偶」直接决定的射程特性**，文案与任何测试都没记录过。
已作为一条队列项记下（改数值前必须先决定这是不是有意设计）。

### 5.4 远程格：kit 撤掉后整格归零

见 §3。这条与 F04 的远程格互为镜像，合起来说明：
**远程格读到的到底是「kit 够得着」还是「普攻够得着」，必须拆 `dealtBy` 才能回答。**
F04 的 `kitDealt` 在那一格等于 `basicDealt`；F05 的 `basicDealt` 恒为 0。

### 5.5 觉醒在**精英格**买不到任何东西

精英格两阶 `kitDealt` **逐位相同（1164.62）**，因为精英在 **t=0.05s** 就被第一个分身弹道打死
（`firstHitAt = [0.05]`），觉醒加的那一个分身来不及开火。
`summonsPeak` 仍然是 6 → 8 ⇒ **这一格只能从「峰值」看到觉醒，不能从「伤害」看到**。
断言把两件事都写下来（`kitDealt` 相等、`summonsPeak` 变大），
而不是悄悄跳过 rank 比较 —— 跳过会让下一个读者以为这里验过了。

### 5.6 已有的 `legion` 断言只钉了「> 0」，且把两件事混在一起

`evolutionCombat.test.ts:27` 是 `expect(render.summons.length).toBeGreaterThan(0)`，
它跑在**同一个测试体**里先 `basic()`、再 `action('skill')`、再 `player.ult = 100; action('ultimate')`。
所以它**同时**被技能和必杀满足 ⇒
**即使必杀一个分身都不召，这条断言依然为真**；它也没钉数量、id、`life`、节奏中的任何一项。
（Scope 0 要求说明「哪些主张已被覆盖、哪些没有」——这是「以为覆盖了、其实只覆盖了一半」的那一类；
与 R2-F04 §5.6 是同一类假覆盖。）

### 5.7 仪器文件头「and nothing else」是错的（已在本片对账）

`formPressure.test.ts` 文件头的「Adding a form」段原来写「加一个 `SPECS` 条目和两块 `describe`，
**and nothing else**」。本片是第一个需要**新读数**的形态（`legion` 没有场），
所以那句话对「kit 无法用现有字段读」的形态不成立。
已改成「这样的加法必须是**追加且 opt-in**，并必须让旧报告**去掉新键后逐字节不变**」，
并注明是 R2-F05 才发现的对账。
（同类：F04 对账了「one `describe` block」；R1g-11 撞到两处「断言与注释矛盾」。）

### 5.8 `legion` 不突进 ⇒ 没有体接触

首领格把玩家放在 `boss.x - 90`（R1g-10 起的固定站位：在预警范围之内、61px 体接触半径之外）。
`legion` 的技能是**召唤**而不是突进，玩家整局不动 ⇒
`takenBy['B001-contact']` **不存在**、八格 `taken` 只在远程格非零。
这正是 R2-F04 §5.4 的**对照组**：那条「突进把玩家送进 Boss 体内」的失效
**是突进类（`dragon`/`phoenix`/`reaper`）独有的，不是所有形态共有的**。

### 5.9 远程格 rank 2 的 `H010_R_CLONE` 通道为 **0**（非单调）

rank 1 该通道 **599.72**，rank 2 **完全没有这个键**；同格 `kitDealt` 反而
**2329.25 → 2119.35 下降 9.0%**（rank 2 的 `H010_CLONE` 从 389.82 涨到 779.63，补不回缺口）。
**实测如此，机制只是假设**：所有分身都瞄 `s.boss || s.nearest()` —— 那是**离玩家最近**的敌人
（`nearest()` 按到玩家的距离取最小），**不是离分身最近的**，所以 8 个分身会同时把弹道
压向同一个目标；多出来的那一个分身把它提前打死，后到的必杀分身弹道就找不到目标了
（`hit` 对已死目标直接 `return`）。
本片**只记录这个读数**，不把它写成断言（断言只要求 `H010_CLONE > 0`，八格都成立），
也**不据此改任何数值** —— 它是「召唤物共享瞄准」这条设计的一个可观测后果，归入队列。

## 6. 文案对账（Scope 5）

`evolutionCatalog.ts:18`：

- `detail: '投刃攻击；技能召出两名定时攻击的焰影。'`
  - 投刃攻击 ✅（普攻 = 2 道投刃）
  - 技能召出**两名**定时攻击的焰影 ✅（rank 1 恰好 2 个；0.8s 节奏自行开火；`life` 5s）
  - ⚠️ **未提必杀**（4/5 个焰影 + 16 道火羽）。
- `awakening: '三名焰影，持续时间延长。'`
  - 三名焰影 ✅（技能 2→3）
  - 持续时间延长 ✅（`life` 5→7）
  - ⚠️ 未提**必杀的分身也从 4 涨到 5**。

**结论：无矛盾，零改动。** 两处 ⚠️ 都是**不完整**而非**错误**，且**全系列同构**：

| 形态 | `detail` 描述的是 | 必杀在文案里出现了吗 |
|---|---|---|
| `bulwark` | 环形普攻 + 技能火域/护盾 | ❌ 未提（必杀是 260px 环 + 跟随火域） |
| `phoenix` | 扇形火羽 + 技能突进火径 | ❌ 未提（必杀是 16 道全周火羽） |
| `frostflame` | 霜环火刃 + 技能降霜留火域 | ❌ 未提（必杀是 260px 霜环 + 火焰爆） |
| `beastlord` | 穿透双刃 + 技能驻守近卫 | ❌ 未提（必杀是 6 个近卫 + 影环） |
| `legion` | 投刃 + 技能召焰影 | ❌ 未提（必杀是 4/5 焰影 + 16 道火羽） |

⇒ **「`detail` 只写普攻与技能、`awakening` 只写这两者的变化」是全系列的约定**，
十个形态**没有一个**在文案里描述过必杀。`legion` 的 `awakening` 是本系列**第一个**
「觉醒也改变必杀数量」的情形，所以它比其它形态更显眼，但**改它就得十个一起改**
（否则 `legion` 会变成唯一描述必杀的形态，反而不一致）。
已作为一条队列项记下（`QUEUE.md` 的 R2-F05 段），**本片不动文案**。
