## 3. 最深的发现：赢家 290 秒就走了，关卡是 420 秒

三处界碑 `opensAt: 90 / 180 / 270`，各 `dwell: 20` ⇒ **最早 290 秒三碑全持**，胜利条件满足，关卡结束。
**后 130 秒只有输家会看到。**

**这否定了 D34 的一半功劳。** 上一片给 `CH001-02` 加了一行 `at: 400, budget: .90`，理由写的是
「覆盖到 420，不留空场」—— **那一行对赢家完全无效**，因为赢家 290 秒就离开了。
D34 修的是**输家的空场**，而输家本来就快死了。

一条更锋利的说法：**我给一个「290 秒就能赢」的关卡补了 400 秒的怪。**

## 4. 为什么不重调

TASK 的 Scope 3 授权的是「打不赢时重调一次」。这里不是打不赢，是**不会输**：

- 改**波次表**只会让输家更早死，**不会让赢家更难** —— 赢家 290 秒就走了，表的后半段与他无关。
- 真正错位的是**关卡时钟与胜利条件**：420 秒的关卡，290 秒就能赢。要动的是
  `seals[].opensAt`（把第三处从 270 推到 340，290 → 360）或 `duration`（420 → 320），
  那是 D25 的设计，不是 D34 的表。

**所以本片零生产改动。** 交付是这张表、这条归因，和下一片的题。

## 7. 没有被验证的

- **只有一台机器人。** 33/33 是「这台机器人不会输」，不是「玩家不会输」。真人不会绕圈绕得那么准，
  也不会在血 < 55% 时一定选 recovery。**100% 是上界，不是估计。**
- **`CH001-01` 的 6 局超时没有被归因。** 它们结束在 360 秒、血量还是正的（40–279），说明
  **打不完 Boss**，不是被打死。这是另一个问题，本片只记录不解释。
- **`CH001-03` 的 16 局失败也没有被拆开**：几局是被 Boss 打死、几局是超时，报告里有 `endReason`
  但本片没有按它分组。
- **两份 `playSealStage` 是复制关系，不是 import。** `seals.test.ts:224` 的那个函数没有导出，
  本片在 `sealCalibration.test.ts` 里复制了一份。**漂移风险**：改了一边不会提醒另一边。
  唯一的防线是种子 15 的结果在两个文件里一致（`at 289.98`、三碑全持）。
