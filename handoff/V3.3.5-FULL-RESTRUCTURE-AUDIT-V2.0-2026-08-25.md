# 《万界无双》V3.3.5 全量改版第一轮审计与实施蓝图

日期：2026-08-25  
依据：《万界无双》Codex 完整大重构执行令 V2.0  
任务状态：第一轮只读架构/UI 审计完成，运行时改版尚未开始  
版本边界：继续使用 V3.3.5；不得创建或宣称 V3.3.6

## 1. 执行结论

本轮结论是“可以改版，但必须以表现层重构的方式逐模块推进”，不能重写战斗、存档或结算。

当前项目已经具备真实可玩的战斗内核、六名英雄、十二条剧情关卡、八名 Boss、剧情加六种非剧情模式、装备/符文/宠物/成长和完整结算能力。主要问题不是缺少底层玩法，而是玩家前台仍以“页面按钮集合”组织信息：主大厅偏产品展示，章节与模式分离，英雄/构筑/任务之间缺少统一简报，战斗信息层密度高，结算不能完整回答“完成了什么、为何失败、下一局做什么”。

因此，目标不是另造一套游戏，而是用新的任务型产品外壳重新编排已有能力：

~~~text
万界中枢
  -> 任务板
  -> 英雄/构筑简报
  -> 现有 startBattle 有效入口
  -> 现有战斗内核与任务状态
  -> 现有 Boss 战利品选择
  -> 现有单次结算链生成 lastResult
  -> 新结算报告只读 lastResult
  -> 返回万界中枢并提示下一任务
~~~

第一轮没有修改 index.html、assets/css/app.css、任何运行时 JavaScript、存档、路线、平衡或验收记录。下一轮只有在本能力图获得确认后，才能从 ui-shell 单模块开始。

### 3.1 当前导航

基础导航由 assets/js/config/game-data.js 的 go(id) 管理：

- 切换 .page.active。
- 同步 data-page 按钮和 aria-current。
- 更新 PAGE_TITLES。
- battle 页面触发 resizeArena()。
- 移动端通过 mobileNavPanel 收纳后五项。

assets/js/systems/game-modes.js 仍对 go 再包装一次，用于进入 modes 时刷新模式页。当前 continueFlow() 直接进入 heroes；选择英雄后进入 loadout。modes 和 world 均存在直接调用 startBattle() 的入口，尚不存在统一的“任务确认/构筑简报”状态。

### 3.2 当前页面流

~~~text
home
  -> continueFlow() -> heroes -> selectHero() -> loadout
  -> go('modes') -> 选择模式或快速开始
  -> startBattle() -> battle

world
  -> 选择章节/关卡/难度
  -> startBattle() -> battle

battle
  -> Boss 战利品/升级/事件/宝箱覆盖层
  -> finishRun()
  -> result

result
  -> go('home')
  -> startBattle() 再次挑战
~~~

这条流可以完成游戏，但玩家在“模式、关卡、英雄、构筑、目标、奖励”之间来回跳页，缺少一个明确的出战合同。

## 5. 战斗入口与结算链

### 5.1 战斗入口

基础 startBattle() 位于 assets/js/combat/engine.js，但当前真正生效的入口位于后加载的 assets/js/systems/game-modes.js。有效入口会：

1. 校验模式和剧情关卡是否解锁。
2. 展示当前模式、章节、英雄、奖励和遭遇信息。
3. 调用既有加载链。
4. 依次初始化英雄身份、技能形态、装备、符文/宠物、成长、模式和战斗 HUD。

新任务简报只能调用最终有效 startBattle()。禁止：

- 直接调用 engine.js 的基础入口。
- 复制一套初始化顺序。
- 新增 _vXXOldStartBattle 或再次包装 startBattle。
- 从任务板直接手写 run/player 初始化。

推荐边界是“任务简报只负责确认现有选择，发出一次 launch action；launch action 仍落到最终 startBattle()”。

### 5.2 Boss 战利品顺序

assets/js/systems/gear-affix-loot.js 的 v26ShowBossLoot() 暂停战斗并建立三选一。选择完成后才清空 run.v26PendingLoot 并恢复战斗。

首战剧情由 assets/js/systems/game-modes.js 的 v29FirstCampaignLootResolved() 判断：

- Boss 已击败。
- 战利品覆盖层已经展示。
- 待选战利品已经清空。
- 覆盖层已经关闭。

只有全部成立后才调用 finishRun(true, ...)。新 Boss UI 可以重新排版现有预警、阶段和掉落预览，但不得提前发奖、预写掉落或越过战利品选择。

### 5.3 单次结算

基础 finishRun() 位于 assets/js/ui/result.js，后续难度、交互、装备、符文/宠物、成长、模式、每日与稳定层逐步补充结果。最终 assets/js/core/stability-v30.js 使用 run.v30.finalizing 阻止一局重复结算。

新结算页必须遵循：

~~~text
现有 finishRun()
  -> 完成全部现有奖励/星级/模式/成长写入
  -> 生成并补充 lastResult
  -> 现有 renderResult()/新报告渲染器只读 lastResult
  -> 用户选择返回中枢或再次挑战
~~~

禁止从新结算 UI 再写金币、星级、装备、模式成绩或成长；禁止第二次调用 finishRun()；禁止用 run 临时状态重算 lastResult 已经确定的奖励。

5. CSS 可在实施中按模块拆分，但不得引入预处理器、框架或远程字体/素材依赖。

## 9. 目标数据流

### 9.1 中枢到任务板

~~~text
save + WW.config
  -> deriveNexusViewModel()
  -> 当前任务/英雄/奖励/成长摘要
  -> 玩家点击“查看任务”
  -> ui-shell 进入 mission-board
~~~

nexus-hub 不直接修改任务和构筑，也不直接 startBattle()。

### 9.2 任务选择

~~~text
WW.config.mode + WW.config.stage + 现有解锁函数
  -> 任务卡：主目标/阶段目标/风险/时长/奖励/推荐英雄
  -> v29SelectMode(id)
  -> selectWorldChapter(id) 或现有 selectedStage 写入路径
  -> persist()
  -> hero-build-briefing
~~~

任务板不得复制解锁逻辑，也不得在展示层自行判定一条新路线。

### 9.3 出战简报

~~~text
save.mode + save.selectedStage + save.hero + save.build
  + 装备/符文/宠物/成长派生摘要
  -> 任务合同与构筑协同说明
  -> 玩家确认
  -> 有效 startBattle() 一次
~~~

简报的“推荐”只解释已有机制，不自动添加隐藏属性，不改变正式平衡。

### 9.4 战斗信息层

~~~text
run/player/run.v29/现有 Boss 状态
  -> 生命与危险
  -> 技能与冷却
  -> Boss 阶段/预警
  -> 当前任务/下一阶段/奖励
  -> 当前构筑
  -> 折叠日志
~~~

桌面默认保护中心和下中部战场；移动端继续使用现有全屏摇杆和动作区。日志、长说明、世界档案不得常驻遮挡战斗。

### 9.5 战利品与结算

~~~text
Boss 击败
  -> v26ShowBossLoot()
  -> 玩家完成选择
  -> 现有 finishRun()
  -> lastResult
  -> combat-information 结算报告
  -> 返回 nexus-hub
  -> 根据现有解锁和星级派生下一任务
~~~

结算报告不得写奖励。返回中枢后“下一任务”必须重新从当前 save/配置派生，不能使用结算页缓存冒充权威状态。

## 10. 分模块实施路线

| 顺序 | 模块 | 单模块目标 | 必须保持 | 验收重点 |
|---:|---|---|---|---|
| 1 | ui-shell | 建立游戏化 shell、主导航和流程页层级 | 页面 ID、go 行为、battle 响应式、ordered scripts | 桌面/移动导航、焦点、Esc、战斗不被遮挡 |
| 2 | nexus-hub | 将 home 改为万界中枢 | 现有选择/进度只读、无直接发奖 | 当前任务和唯一下一步在首屏清楚 |
| 3 | mission-board | 合并 modes/world 的任务理解 | 七种模式、十二关、解锁、星级不变 | 目标/风险/时长/奖励/推荐英雄均可读 |
| 4 | hero-build-briefing | 建立任务上下文中的英雄/构筑确认 | 六英雄、技能/装备/符文/宠物、有效 startBattle | 玩家知道为何选、差什么、如何开战 |
| 5 | combat-information | 重排 HUD、升级、Boss、战利品和结算信息 | engine、Boss AI、pickLevel、loot、finishRun、lastResult | 中心战场清晰、信息优先级、单次结算 |
| 6 | narrative-archives | 接入非阻塞剧情卡和档案 | 无分支、无新存档字段、不遮挡战斗 | 每章/英雄/Boss 关联正确，短句可跳过 |
| 7 | cross-platform-regression | 关闭脚本、浏览器、真人和设备证据 | Schema30 和所有冻结契约 | 五门禁、桌面、390x844、真人矩阵分别报告 |

每个模块执行固定节奏：

~~~text
模块 SPEC/验收条件
  -> 只改该模块约五个文件
  -> check + smoke + audit + context + archive:verify
  -> 桌面与 390x844 浏览器检查
  -> 更新 STATE
  -> 可独立回滚
  -> 再进入下一个模块
~~~

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| startBattle 被多层历史逻辑覆盖 | 绕过初始化、加载两次或进入不可玩状态 | 新 UI 永远调用最终入口一次；禁止包装和复制初始化 |
| finishRun/renderResult 包装链很深 | 重复奖励、重复星级、结算行重复 | 新报告只读 lastResult；保持 v30 finalizing；加入单次结算回归 |
| renderTop/go 仍有包装债务 | 新 shell 与旧导航互相覆盖 | 在原所有者合并明确调用点，不新建别名 |
| 任务板复制模式/关卡数据 | 展示与真实规则漂移 | 所有任务卡以 ID 从 WW.config 和现有 helper 派生 |
| 统一 modes/world 时误改路线 | 解锁、星级、双 Boss 回归 | 保留选择字段和现有解锁 helper；运行 route/audit |
| 新 HUD 挤压 Canvas | 桌面像后台、手机遮挡战斗 | DOM 信息分层、日志折叠；验证桌面和 390x844 可视范围 |
| 剧情要求诱发新存档字段 | Schema30 变化 | 首轮使用静态/派生内容；需要持久化即停止报告 |
| 结算报告重算奖励 | 金币/装备/星级重复 | 只显示 lastResult；不在 UI 中写 reward |
| 非 Git checkout 难以模块回滚 | 改动混杂、无法按提交恢复 | 每模块开始前建立变更清单、SHA-256 和 task-scoped 文件快照；只恢复本模块明确文件 |
| 真人验收仍为空 | 无法证明传统页游操作和手机体验 | 不把自动化当真人；继续保留 pending 并单独完成 5x3 路线矩阵 |

当前 GLOBAL_RUNTIME_AUDIT 显示高风险覆盖链包括 v20Boot 10 层、finishRun 9 层、renderResult/startBattle/updateRun 各 8 层。全量改版应利用这次 UI 边界收敛展示调用点，但不得借机重写整个战斗循环。

## 12. 回滚边界

本项目当前不是 Git checkout，因此“每模块单独提交”尚不能按 Git commit 执行。实施期采用以下可恢复边界：

1. 每个模块开始前记录允许修改的约五个文件和 SHA-256。
2. 在 handoff/rollback/<module-id>/<timestamp>/ 保存这些文件的任务前快照和 manifest；禁止使用 archive/。
3. 模块失败时只恢复 manifest 中的文件，不覆盖其他任务或用户改动。
4. 存档、playtest 证据和 docs/reference 不进入 UI 模块回滚写入范围。
5. 每模块五门禁和浏览器证据通过后再关闭快照。
6. 如后续由产品负责人建立 Git，再改用 capability-id 分支/提交；本轮不初始化仓库。
