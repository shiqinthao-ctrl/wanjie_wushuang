**给技术成员的关键提醒**（本会话踩过的坑，能省几小时）：

1. **整局结局量是混沌的**：刷怪半径 524.2 → **524（0.2px）** 就让 Boss 生成 HP 从 478 变 710。
   **单种子 A/B 不可用，n=11 也是分位噪声**；平衡数字至少 **33 种子**。
2. **任何胜率/份额数字必须带仪器声明**（按键策略 + 是否按 `f` + 视口 + 种子集）。
   同一个 classic cell 在四种都站得住的仪器下读 24/28/30/31，跨度 **21pp**。
3. **harness 必须与浏览器机器人同构**：`status` 变 `'chest'` 需先调 `claimChest(index)`；
   `interact()`（`f` 键）是同类缺口的第四例。改造前差 2.8s TTK，改造后差 **22.3s**。
   形态场景另有两个同构缺口：**形态 kit 永不被自动施放**、**宠物会污染首命中**。
4. **能用生产字段就别用 harness 近似**：本片第一版在测试内缩放 `castCd`，
   对相位切换帧多算 `(k−1)·dt ≈ 0.22s`；在「一局只有 2 次施放」时这 0.22s 让血线中位差 **5pp**。
5. **前缀筛选要排除同前缀的兄弟键**：`'B001-contact'.startsWith('B001-')` 为真，
   第一版把体接触也乘了 14.31 ⇒ 施放/局 **0**、Boss 承伤/局 **573**。
6. **报告是滚动工件**：改完生产再跑一次就会覆写旧切片的数据。**目录名 = 数字被读在哪棵树上，
   报告里的 `slice` 字段 = 谁拥有这个问题**；旧目录留指向说明（**并且要真的执行 `ls` 复核**）。
   零生产改动的切片**不要**重指输出目录。
7. **聚合中位数会掩盖方向相反的 cell**：R1g-11 的 pooled 0.264 是绿的，
   分路线 classic 0.280 / evolution 0.147 才暴露了问题。**先拆路线再下结论。**
8. **断言要和自己的注释对账**：R1g-11 修了三处「断言与注释互相矛盾」
   （`growthPacing` 的行集、`manualDamage` 的 pressSensitivity 与 D2 份额）。
9. **会写文件的 harness 必须把赋值放在断言之前**：R1g-12 第一次跑 `manualDamage` 时守卫先红，
   `manual-report.json` 回来是 `rows: []`。
10. **归因划分必须完备，且「不相交」要真的验证过**：R1g-8 把两个 miss 机制写成不相交并断言
    `a + b === misses`，它们其实**按构造就重叠**。
11. **遥测记的是它自己的定义，不是你关心的量**：R2-F01 第一版把「远程线有没有开火」读成
    `damageTakenBy`，而 `hurt` **只记 HP 损失**、护盾吸收在 `incomingHit` 里提前 `return`
    ⇒ 血条没掉就一路读 0。**先读被调用函数的写入条件，再决定读哪个字段。**
    （R2-F02 撞到的是同一个陷阱的**反面**：`frostlord` 无盾，该格必须读 `takenBy`。）
12. **一个「什么都没发生」的格必须配反事实**：R2-F01 的敌群格 `absorbed + taken = 0` 看起来像
    kit 的功劳，关掉技能后发现**普攻也一击清场** —— 原归因被证伪。
13. **「打死它就不减速它」这类次序差异要用断言钉住**：R2-F02 第一版霜环测试直接红
    （`chilledUntil` 是 `undefined`），真因是**霜环把假人打死了**；修法是**把次序差异本身写成测试**。
14. **形态 harness 的 `SPECS` 表要保证「加一个形态不动已有形态」**：R2-F02/F03 都把旧形态的
    8 格数字**逐位比对**作为泛化的回归证据。**加新形态时先跑一遍旧形态并 diff 报告。**
15. **按一次技能键可能是两件事**：journey 局里 `CombatSimulation.action('skill')` 除了形态 kit，
    还会跑 R1g-7 的 `releaseManual()`，**额外释放 `progression.manualSkill()`**（×6 攻击、键名带 `_E`）。
    `manualSkill()` 取 `build.active` 里**等级最高的已拥有主动技** ⇒ **拥有的技能一变，搭车那一招就变**。
    不拥有技能的形态不会触发（F01/F02 因此从没见过它）。**要断言「只有一个变量在动」，先枚举这个
    动作会碰到的每一个共享状态**（拥有的技能、`manualSkill()` 的解析、`cool`、`manualCast`、宠物、刷怪）。
16. **多通道的增益类效果要同时断言「该动的动了」和「不该动的没动」**：R2-F03 的羁绊实测
    火通道 **×1.300000**，而**霜通道用 `toBe` 逐位相同** —— 只给前者时，一个「其实乘了全部通道」
    的实现也会绿。同一批里还测了**静止 vs 跟随**：行为断言是**移动玩家后读坐标**，不是读调用参数。
17. **单一开关的判别量选错了，会把正结果读成负结果**：R2-F04 的敌群格撤掉技能后
    **承伤 0 → 84.06、血线 1.000 → 0.836**，但**击杀两臂都是 12/12**（扇形普攻只是慢，10 秒内照样清空）。
    若沿用 F01 的 `control.killed < control.of` 判据，这一格会被判成「不具判别力」。
    **先问「这个 kit 的代价记在哪个字段上」**（承伤 / 血线 / 时间 / 击杀），再选判据。
18. **`kitDealt` 这类聚合字段在负结果格里会骗人**：R2-F04 的远程格 `kitDealt` 两臂**逐位相同**，
    拆开 `dealtBy` 才发现里面**只有 `H010_BASIC`** —— 这一格量的是**普攻射程**，kit 一分伤害没出。
    **凡写「这个格量的是 X」之前，先把聚合拆成 `dealtBy` 的逐源份额看一眼**；
    负结果要写成负结果，并写明它实际量的是什么（R2-F01 的敌群格、R2-F02 的清减速对照同此）。
19. **`if` 与 `else if` 要逐行确认前一条是哪种**：同一个链的相邻两行既能**吞掉**（R2-F04 的
    `phoenix` 被 `:94` 的 `else if (heroId === 'H010')` 抢位，永远到不了 `:95` 的跟随火域），
    也能**放行**（R2-F05 的 `legion` 因为 `:85` 是**独立 `if`**，而**同时**拿到 4/5 个分身 **和** 16 道火羽）。
    **`if` 是并行、`else if` 是互斥**；一个 `if` 后面跟一串 `else if` 是最容易把两件事读成一件的形状。
20. **报告 schema 变了时，回归证据要换形式**：`formPressure.test.ts` 是**跨形态共享**的仪器，
    加读数（`Outcome` 加键）会让所有旧报告的**字节**变化 ⇒ 直接比 md5 得到**假红**，
    而 `evidence/` 全是 untracked ⇒ `git diff` 也返回空。**修法：去掉新键后重建 md5**，
    再与**旧切片自己 `IMPLEMENTATION.md` 里记下的 md5** 逐位比。前提是新键**追加且 opt-in**、
    写入是**确定性**的 `JSON.stringify(report, null, 2)`。
21. **窗口本身决定了你能看到 kit 的哪一部分**：R2-F05 的必杀**只在击杀时充能**（无时间充能），
    10 秒窗口最多赚 16.8 点 ⇒ **八格 `ults` 全为 0**，而必杀占了那个 kit 91.8% 的伤害。
    **修法**：给 `RunOpts` 加一个**缺省关闭的 `ult: true`**（既测到全貌、又让旧读数逐位不变），
    **不要**去改生产充能速率。这与「弱驱动不是保守，是另一个玩家」是同一类账。
22. **「场景快照」和「持续交换」不是同一件事，窗口对后者是采样率而不是预算**：R2-F-INST 之前
    所有场景都跑 600 帧（10s）。首领格的**主体有自己的时刻表**（首跳 24.33s）⇒ 10 秒**一帧都没看到**；
    实测把敌群/远程/精英三格也拉到 5400 帧，`elite` 十片**答案不变**、`horde` 九片不变，但
    **`ranged` 六片会变**（`bulwark` 承伤 0 → 731.70、`frostlord`/`beastlord` 会**死**）——
    它量的是**持续交换**，所以它的 `taken` 是**采样**不是总量。
    **做法**：窗口**按场景**覆写（`run()` 的 `frames` 是全局的，改它会连带移动另外三格），
    窗口**从配置读**而不是手挑（`BOSS_FRAMES = (duration − bossAt) × 60`），
    并把「旧窗口是负结果」**留成断言**（同一臂在 600 帧下仍读 `bossCasts = 0`）。

## 7. 已积累的教训（给所有角色）

### 7a. R2-S01..12 的四条（**验收 / 比值类切片**）

1. **「承诺是相对量」时，基线必须**在同一上下文里现测**，不能从常量抄。** 十二条 `detail` 里有
   六条写的是「原来的 / 普通的 65%」—— 那个「原来」是一个**生产分支**（未选路），不是常数。
   本片把它跑一遍再取比值，才发现 `A011` 的基线**随 `m.evo` 改变身份**（1 发 → 3 发）。
   **抄常量会让断言在基线变化时保持绿。**
2. **一个 `detail` 可以「单发正确、总量反转」。** `volley` 的「单发 65%」在进化后仍然成立，
   而三条里两条的总量**低于不选路**。**验承诺要同时报「单位」与「总量」**：只验前者会把一个
   负收益的选项报成合格。
3. **「字段有读者」要数一遍，不能假定。** `skillModifier` 的 `count++` 在五个路线技能里
   **只有一个读者**（`S001`）；`A013` 自己算 `2 + P023 + bond` ⇒ `E013` 的第四项加成**静默丢失**。
   **给一个旋钮加字段，要 `grep` 它的消费者**；`m.dmg` / `m.range` 都生效，唯独 `m.count` 不生效，
   所以读数看起来「进化有效」。
4. **优先级也是边界，要断言。** Lv.19 的觉醒**抢占**路线选项（`special(19)` 只返回 `['awaken']`）——
   写验收时先问「这一档还有谁在抢同一个 `special()` 返回值」，否则会把「按顺序晚一档」写成「丢失」。

### 7b. R2-F-BOSS-COVERAGE 的五条（**覆盖 / 规格 / 仪器形状类切片**）

1. **「加一格」的规格要跟着「那一格演什么」一起写。** 队列的候选 B 是 *一个 `EN001`* ——
   但实测它**在 0.98–2.88s 内死亡**（场上 98.154 HP，一个 90s 按 15 次技能的 kit 不吃这一套）
   ⇒ 该格只能演出**≤5.3%** 的共存窗，而它存在的全部理由就是演出发货状态。**一个没有「单体寿命」
   参数的格规格，是一张没写完的图纸。** 落地前先测 body 活多久，再从实测出发写规格。

2. **「谁在场上」要按帧数，不按存在性。** 四格 × 十形态 = 40 格跑完，`framesBoth = 0` 全部成立 ——
   但同一几何**去掉该格自己的剔除**后 ≥94% 的帧同时有 Boss 与小怪。**「这一格有没有 X」
   是 `framesBoth` 这种**帧计数**，不是「场景里出现过 X」的布尔**。一个只在第 0 帧出现的量，
   和全程出现的量，在存在性判断下同值。

3. **缺口的**符号**要量，不能只量大小。** 一个身体在场让 `bossHpLost` 从 **+16.7% 到 −14.7%** ——
   八套**变高**、`phoenix` **变低 15%**。**只报「移动了约 15%」会丢掉「方向取决于 kit」这个事实**，
   而方向才是判断「该不该补这一格」的依据（`phoenix` 被抢走的是它自己的份额）。**跨 rank 复测**
   （7/10 比值逐位相同）才把它从「一次噪声」升成「结构」。

4. **`scenarios` 与 `NAMES` 是两份独立的名单。** 加一格要同时改两处，而**引用它们的是 62 条
   `of cells` 循环**。**本片不落地第五格**：把账单（`R2-F-INST:3018` 的 `WINDOWS`、
   两个名表、62 条循环、十份报告 schema 变、10 组控制臂）逐项写在证据里，比落地一个
   **演出 2% 窗**的格更值 —— **「可见」的仪器（帧计数断言 + 滚动报告）花 0 账单就够让缺口沉默不了。**

5. **账本「从源码派生滚动集」的形状是**约定**，不是任意写法。** `byte-ledger.mjs` 扫的是
   `writeFileSync(resolve(<dir>, '<name>'))`：**别名 import**（`{ writeFileSync: write }`）、
   **预绑定全路径 const**（`const P = resolve(...,'x.json')` 后 `write(P)`）、**三参 `resolve`**
   （`resolve(ROOT,'DIR','x.json')`）—— 三者**都不会被认成写者**，于是新报告被当成**冻结**
   ⇒ 将来一次合法重写会以 **MOVED(frozen) 报红**。**修法照抄本文件既有形状**（`const dir = resolve(EVIDENCE_ROOT, 'R2-F-XXX')` 然后 `writeFileSync(resolve(dir, 'x.json'))`）。
   另：扫描器**连注释一起读** ⇒ **注释里写出那段调用形状会凭空造出一个假报告名**（本片先后出现 `<name>` 与 `name.json` 两个幽灵入账）。**改完必须 `ledger:coverage` 数一遍名表**，别只看总数。

### 7c. R2-F-HORDE-LEDGER 的四条（**覆盖 / 生成器类切片**）

1. **「我核对过了」要问清核的是清单还是树。** 队列说逐字节账漏掉了目录下的 JSON —— 前提**半真**：
   `cap10-md5.txt` 本身**早就列全了**那 11 行（被点名的那四份是**散文**里漏的）。
   真正的问题是**每片只重算那 248 行，没有一片重走那棵树** ⇒ `evidence tree: 261 json | ledger: 248 lines`，
   **13 份从未进账**（6 滚动 + 7 冻结），沉默了两片。**一个漏掉的项不会报错，它只会沉默** ——
   所以「核对该目录下全部 X」这类断言，**被核对的对象必须是命令枚举出来的**，不是手抄的。
   **修法不是改数字，是换掉产生它的方式。**

2. **滚动 vs 冻结必须由源码派生，不能靠 mtime。** 全量套件会把每个滚动报告重写一遍
   （实测 11 份里 10 份的 mtime 都是「今天 19:2x」）⇒ **mtime 完全洗白**，唯一可靠判据是
   `grep writeFileSync(resolve(<CONST>, '<name>'))`。**D17 当时**派生结果 = **26 份滚动**（16 处直接写
   + `formPressure` 的表驱动 `spec.evidence`/`spec.report` 10 份），其余 235 冻结（**当前值 = 27 份 / 235 冻结**，见 §5）。
   **分类是断言，不是注释**：`byteLedger.test.ts` 独立重算这套分类，并加了「守卫的守卫」
   （滚动集必须非空且含两份具体报告），否则一个派生失败会让整类变成空集而**静默通过**。

3. **schema 长大的 md5 有两个用法，混用会在两个方向都错。** **相等性**检查（「这文件改动前后数值是否相同」）
   用「**去掉新键 + `sort_keys` 重建**」—— 这是 SUFFIX 记的 `1f4bfd3c…` 能被逐位复现的唯一办法
   （直接 `md5` 明文得到的是另一个值，会误判成「文件变了」）。**覆盖率**账本（「树里每一份都在账上」）
   用**明文直接 md5** —— 因为它的用途是「路径 → 内容指纹」，没有跨版本比对的语义。
   **两处用反都不会报错，只会给出错误结论。**

4. **覆盖声明要与数字同句，并且由命令产出。** `R2-F-CAP` 的 `248` 这句散文**没有任何命令支撑**，
   存活了十天没被发现 —— 因为**全库没有任何测试或脚本读它**。修法有三层，缺一层就会回退：
   **① 生成器**（`byte-ledger.mjs` 走树产出账，`--write`/`--verify`/`--coverage` 三模式）；
   **② 门**（`byteLedger.test.ts` 进 `npm test`，负例已验：删一行 ⇒ 2 红打印确切路径，
   改冻结文件字节 ⇒ 1 红点名冻结漂移）；**③ 守卫的守卫**（测试**独立重算**而不是 `import` 那个工具，
   否则生成器坏掉时测试会跟着一起坏）。**「这个数是谁写的、谁能改它、谁会在它错时报警」三个问题都要有答案。**

### 7d. R2-F-HORDE-BAND 的四条（**离散量 / 控制臂 / 自伤超时类切片**）

1. **「读数是一个连续量」是这个项目里最贵的默认假设。** 敌群环的 `taken` 看起来像伤害总量，
   实际上是**命中次数 × 单次接触伤害**：带上 320 个样本**全部**落在
   `q = 11.52 * (1 - 14/(14+60)) = 9.34054054054054` 的整数倍上，`q` **逐位**等于
   `enemyDamage.EN001` 经 threat-v2 软上限（`combatMath.ts:146`）。**先问「这个量的最小增量是多少」，
   再问它的值** —— 若最小增量是 1（一个计数），那么「挑一个更好的数值」根本不可表达，
   只能交付**那张表**。**离散量上的读数不给你中间档。**

2. **一个量在扫描床上「恒定」是**必须被测量**的断言，不是可以继承的前提。** 队列假定控制臂在
   半径带上是常量，实测它**不是**：`reaper` 的干净集是 `DDCCCDCC` —— **120 与 240 脏、其余六档干净**，
   而两处脏档读**同样的 3 次接触** ⇒ 那不是距离阈值，是**竞态**（哪一帧正好有身体站在玩家身上）。
   **非连续的结果集 = 测的是别的东西**：距离给出区间，竞态给出点集。**一个非连续的集合是
   「这不是距离」的证明，不是「数据脏」的证明。**

3. **「既有仪器覆盖它」要先按臂数一遍，再按轴数一遍。** 队列说「带上没有对应物可以重推 43 条断言」——
   **一半是假的**：kit 臂**早就有**一条完整的带（`radiusSweep()` `:3195`，`:3307` 已经断言了
   「只有出货环 `clean=10` 且 `blind=7` ⇒ `[120]`」，也就是本片独立重算的那条）。
   真正缺的只有**控制臂**（`kit: false`）。**「我要重推的东西有没有对照」要分臂问** ——
   一条扫描床可能只覆盖了它名字里一半的臂。**本片独立重算的结论在仓库里早已存在**，
   这正是「先数一遍」能省下的整片工作。

4. **写「重块要显式超时」这条教训的切片，自己也踩了它。** 本片第四个 `it` 调 `band()` = **320 次
   `run()`**（十形态 × 八档 × 两阶 × 两臂），没写显式超时 ⇒ 全量下 `Test timed out in 5000ms`，
   而**单独跑 5.4s 绿**（工作 2.7s）⇒ 又一条**并行争抢**。**修法是两条，不是一条**：
   **① 记忆化**（`cached ??= build()`，320 次只算一次而不是四块各算一次）
   **② 显式超时**（`300_000`）。只加超时会在块数增长时重新淹掉；只记忆化会在单块变重时重新淹掉。
   **整文件从 29.17s 降到 21.40s** 说明**记忆化本身是那半条正解**。

### 7e. R2-F-BOSSPHASE 的四条（**规则渗漏 / 仪器卫生类切片**）

1. **一个旋钮渗进正交维度 = 顺序成了另一个变量的函数。** `:70` 的相位是**难度**旋钮（伤害、预警、
   速度、冷却都按它缩放，合法），`FirstBoss.ts:106` 把它**加进了招式下标** ⇒ 顺序随**血量**走 ⇒ 随
   **DPS** 走。**判据不是「它有没有用」，而是「它作用在哪个维度」**：把 `phase` 从索引里拿掉，
   「相邻两刀永不重招」**依然成立**（靠 `+1 % 3`）⇒ **相位项在那里没有防守对象**。凡是「同一个输入
   在不同时刻解析出不同输出」的映射，先问**那个把两者耦合起来的加法**在防什么。
2. **读回的字段要先确认它是什么。** `castLog` 记的是 `event.shape`（**形状键** `'cone'`），
   **不是**招式名（`'旋风断军'`）。第一版把两者混用，反事实算出 **61/61**（一个看起来很有力、
   实际是假的读数）。**修法不是改数，是拆出 `shapeOf`（返回键）与 `moveOf`（返回名）**：名用于
   表与第一刀断言，键用于与 `castLog` 比较。**任何「拿生产字段和期望值比」的地方，先把那个字段
   打印出来看一眼。**
3. **反事实要钉实测值，不要钉阈值。** 断言写的是 `[61, 58]` 与 `[59, 59]`（**跑出来的**），不是
   `moved > 0.9 * total`。**阈值只证明「有变化」，实测值证明「变化是多少」** —— 后者在规则被改动时
   会立刻指出移动了哪一格，前者只会说「还是红的」。**与之配套**：凡是要被行号引用的文件，
   新仪器**一律追加到 EOF**，并**断言新常量 == 旧构造**（共享字面量只证明两处写的一样）。
4. **「重块」的判据不是「它慢」，而是「它的墙钟依赖邻居」。** `formPressure.test.ts:3294` 单独跑
   **3.11s 绿**，在 43 文件 / 11 worker 的全量里**超掉默认 5s** ⇒ 一条**只报一次、复跑即绿**的红。
   **本文件同时有 24 个 `describe`，只有它一个塞了三位数 `run()`（270 次）**，而隔壁 `R2-F-BOSS-ADDS`
   早就写了 `}, 300_000);`。**同一个坑 `R2-F-G4ROWS` 在 `bossThreat.test.ts` 已经踩过一次** ⇒
   凡新写重块，**第一件事是抄本文件已有的超时惯例**。（入账为 **#6x**。）

### 7f. R2-F-KITKEY 的三条（**同形两义 / 守卫盲区类切片**）

**「两个东西共用一个字符串」要用「谁减掉谁」来判，不是用「名字像不像」。** 队列说的是
「`G2_FROST_E` 同时是签名场和释放键」。本片把它变成一条**可判定的结构断言**：
`chapterCoreSkills[form] + '_E' ∈ SPECS[form].kit` —— 枚举十个形态，**恰好一个**成立。
而且关键在于：`frostflame` 的 core 也是 `G2_FROST`，但它的 kit 用 `G5_*`
⇒ **同一个释放键不在它的 kit 里** ⇒ 过滤器能抓到它。**「撞车」不是「有共同的字符串」，
是「那个字符串落在了会被减掉的那一半里」。**

**「守卫是盲的」要指出它盲成什么，不是只说它盲。** 释放**没有丢**：`dealtBy` 的键集
**完全不变**，释放**并进了签名场自己的键**（152.92 → 1136.01，**7.43×**）。
区分「丢了」和「合并了」是全部 —— 丢了的键会红，合并了的只让数字变大。
**排查一条守卫时，先问它把什么减掉了，再问被减掉的那一份里有没有它本该看的东西。**

**「靠构造回避」若只写在散文里，等于没有断言。** 两套 harness 都在避开这个碰撞，而
`formPressure` 那条**唯一**把机制讲清楚的注释（`:1041-1052`）**没有任何断言**。
**散文里的回避是下一次编辑的陷阱** —— 把回避写成断言（`{}`、`{A011:1}`、
`{A011:1,G2_FROST:1}`、`{G2_FROST:1}`、**`{A011:1,G2_FROST:3}`** 五个装配各断言一次），
比再写一段注释有用得多。

### 7g. R2-F-GDD-G8 的三条（**设计裁定 / 口径类切片**）

**「两个读数不同」要问到「是不是子集」。** 队列说「GDD 的断言与 harness 不是同一读数」—— 到此为止
只知道「不一样」。本片把它推到**严格子集**：`H001_E + H001_R`（12,098,521.36）**完全包含在**
`manualSkill + manualUltimate`（33,139,229.20）里，差量 21,040,707.85。**子集关系比「不同」强得多**，
因为它直接点名了**哪一半被漏掉**：漏掉的正是生产自己的 `manual` 旗标判为 `true` 的那一半
（19,654,845.33），也就是**这个指标存在的理由**（R1g-7 落地的手动释放 `A003_E` = 13,447,659）。
**遇到「两个读数不一致」，下一步永远是问「谁包含谁」**，而不是「哪个更保守」。

**一个键名可能有两个发射点 —— 先枚举发射点再解释它。** `H001_E` 同时由
`CombatSimulation:292`（classic 路线）和 `EvolutionCombat:79`（形态 switch 的**最后一个 `else`**，
只在英雄**尚未进化**时触发）发出，**两条路径互斥但共用一个键名**。按路线拆开数：
`H001_E` 有 **74.8%**、`H001_R` 有 **64.7%** 来自进化路线。**解释一个遥测键之前先 `grep` 它有几个
发射点**；只有一个发射点的键才能用「它属于哪条路径」来解释。

**判「哪个口径才对」，用「两个读数是否朝同一方向动」—— 反向意味着测的是别的东西。**
最直觉的裁定是「字面口径更保守，所以更安全」。实测否掉了它：在唯一有进化/未进化混合的 cell
（`evolution/unlock`，33 局）上，`r(进化数, gddShare)` = **−0.3172** 而
`r(进化数, manualCoreShare)` = **+0.3447** —— 进化一次把真·手动释放**翻了一倍**（92,961 → 186,370）、
把桶读数抬 **+11.2pp**，而字面读数**掉 2.5pp**。**一个随玩家变强而下降的「贡献」读数，
测的不是贡献**；它不是更保守，它是另一个读数。**裁定要按意图，不按数值能不能过** ——
本片同时把**保守界**（release-only = 0.22174，未达 35%）记进账，因为「哪个口径」这件事
**不能在两种读法之间来回挑**。

### 7h. R2-F-BOSS-ADDS 的三条（**几何判定 / 覆盖缺口类切片**）

**「没有格包含它」可能是断言，不是遗漏。** 队列写「首领格不撒任何小怪」，听起来像仪器缺了一格。
实测：`scenarios.boss`（`:371-380`）**主动 `return []`**，而 `R2-F-INST:3040` 把
`nothing but the Boss lands here` 写成**十形态共用断言** ⇒ 候选「往首领格塞小怪」**必然打红 ×10**，
**不是「补一格」而是「改一条验收」**。**在动任何 `scenarios.*` 之前，先把整套 harness 里针对那个
场景的断言 `grep` 一遍** —— 一个「看起来只是数据」的构造，很可能已经被另一片钉住了。

**「几何理由」要写成可判定的不等式，并逐格对账。** 队列的说法是「偏离最近目标」，无法证伪。
本片把它化成 **`d < standoff` 且 `standoff + min(180, d) > r + 42`**（`bossR = 42` 是**测量**出来的），
然后**逐格对账**：46 格里模型解释 **46/46**（40 可分离、6 不可）。**对账全中才算结论**；
对不上的那几格才是真正要看的地方。顺带一个反直觉点：**挡路的是站位 `standoff` 而不是半径** ——
出货 90px 下 `d = 1..89` 全枚举后 **rank 2 的可分离集合是空的**，rank 1 也只在 `d ∈ (72, 90)` 才可分离。

**离散量上的增益是常数，「找中间档」是白费。** ① 买到的伤害恒为 **+831.28（rank 1）/ +1219.21（rank 2）**，
= **跳数 × 单跳伤害**（+15 / +22 跳 × 55.42）⇒ **一格要么全盲要么全开**。当改动作用在
「跳数 / 环上命中数 / 分身数」这类**离散**量上时，先扫整个区间确认增益是不是常数；
是常数就**别去调中间值**，直接问「这个常数占目标预算的多少」—— 本片是 **0.18% / 0.27%**，
所以结论是「可验证但不值得落地」。

### 7i. R2-F-TOUGH-HORDE 的四条（**测量 / 仪器成本类切片**）

**队列里的「互斥」是先验，不是测量。** TASK 写「敌群格同时要求无伤清线与可见觉醒，对持续场二者互斥」，
并把范围说成「八个形态」。实测**两处都不成立**：`hpMin === 1` 只被断言 **7 处**（F04..F10），
而**「clean ⟺ blind」不是规律** —— 40 格里 **12 个反例、两个方向都有**（`clean` 但可分的 4 个里就有
`void`，它**也是**持续场），敌群列本身 **10/10 clean、3 个可分**，而且**敌群格还不是最弱的格**
（`elite` 9/10 盲 > `ranged` 8/10 > `horde` 7/10）。**凡 TASK 用「不可能 / 互斥 / 永远」下结论的地方，
都要先把那个集合数一遍、再对每个成员跑一遍** —— 本片若照着前提去「修互斥」，会去改一个不存在的规律。

**一个读数可以对参数非单调，所以「挑一个好值」不是设计。** 半径带实测 `clean` 是
`[true,true,false,true,false,true,true,true]`（180 与 240 变脏）—— 互斥**可破**，
但**只在两个孤立档位上可破**。**当「调整一个常量」看起来能解决问题时，先扫那个常量的整个区间**：
单调的修复可以钉一个数，非单调的只能**连同那张表一起交付**，否则下一个人换个数值就复现缺陷。

**行号引用会随插入位移。** `manualDamage.test.ts` 用**行号**引用 `formPressure.test.ts` 的四处
（`:195` / `:1009-1047` / `:2572` / `:2895`）⇒ 在文件中间加代码会**静默**改变那些引用的含义。
**在会被行号引用的文件里加仪器，一律追加到文件末尾**，并用一条**断言**把「新常量 == 旧构造」钉住
（本片：新 `HORDE` 与 `scenarios.horde` 走生产路径逐具比对），而不是共享同一个字面量 ——
共享字面量只证明「两处写的一样」，不证明「构造没变」。

**逐字节账要写成可执行清单，不能手抄。** 「本片零生产改动」的最强证明是「报告逐位不变」，
而 `R1g-12/` 目录里有**六份**滚动报告，早先两片只核了**四份** ⇒ 一份不符被漏了整整两片
（`R1g-12/manual-report.json`）。**凡「核对该目录下全部 X」，都要用一条命令列出 X**；
漏掉的项不会报错，只会沉默。

### 7j. R2-F-CIRCLE 的三条（**覆盖缺口 / 几何裁定类切片**）

**「几何理由」可能把两个不同的距离当成一个。** 队列写「首领格站位 90px、红圈 `r = 70` ⇒ `90 > 70` ⇒ 永远打不中」。
但红圈的圆心是**玩家自己**（`FirstBoss.ts:111`），判定读的是「玩家到**圆心**的距离」= **0**，不是「到 **Boss** 的距离」= 90。
实测 41 个红圈、`distAtCast` 全为 0，而站位实测 59.1–84.4px **横跨** `r = 70`。
**凡「A > B 所以不会发生」的几何论证，先确认 A 与 B 是从同一个点量的** —— 这次两个量来自两个不同的原点，
所以那个不等式对红圈的判定**完全没有约束力**。

**「到达」≠「命中」。** `.75×` 下 `browser` 命中 14/12 次，而 `hud` **命中 0 但到达 8/6 次** —— 它躲开了。
第一版把两者混为一谈，`hud` 就报了红；那个红是**发现**，不是 bug。
**一个测量报红时，先问它测的是「事件发生」还是「事件生效」**；这两件事在「会躲」的臂上必然分离。

**「没观测到」的原因可能是节奏，不是结构。** 「结构上不可测」这个结论在**同一棵树、同一个节奏**上被证伪：
`browser` 臂（不读预警的臂）在发货节奏下已经落了 2 次红圈，因为**哪一招落在哪个槽取决于施放时的相位**，
而相位取决于玩家自己的 DPS（R2-F-BOSSPHASE）。**在宣布某物不可测之前，先把所有已有的臂都跑一遍** ——
尤其那些「不读线索」的臂，它们的行为与「读线索」的臂不同，而差别恰好在这里决定可见性。

**过滤会掩盖覆盖缺口。** `perShape.filter(shape => shape.hits > 0)` 让零命中的形状**静默消失**，
于是 `cheapestMove` / `heaviestMove` 只从过滤后的集合取。发货 `hud` 读数只有 **line 5** 有命中
⇒ 「有的招看得见、有的看不见」这个**分散度主张塌缩成一个数**，而报告仍然报「过」。
**凡「在集合上取极值或统计」之前先 filter 的地方，都要问「被 filter 掉的是什么」** —— 以及
`g4: phase1.length ? … : null` 这类**三元返回 `null`** 的分支，它报的是「没测到」还是「测到了且不合格」。

### 7k. R2-F-CADENCE 的四条（**节奏 / 杠杆裁定类切片**）

**「两个读数各自正确，基准不同」比「谁错了」更常见。** TASK 明写「两次施放都在相位 1」，实测**为假** ——
但**不是错，是基准不同**：那句话对 `formPressure` 的首领格成立（那里 Boss 背 **452,115.7 HP** 的进化预算，
只有 `phoenix` r2 越过 70%），而**发货关卡** Boss 预算 ≈ **166,553**、玩家在 270s 已练满 ⇒ **第一次施放前
就越过 70%/35%** ⇒ 两次施放落在**相位 2/3**。**同一个问题在两棵树上答案不同时，先标基准再下结论；
「TASK 写错了」是最后一种可能，不是第一种。**

**「A 就是 B」的等号要被测量，不是被假设。** TASK 的前提里藏着「**施放数 = 闪避机会数**」这个等号 ——
它只有在「每一次施放都是一个玩家真的能做的决定」时才成立。本片新增 **opt-in `castLog`** 把它量出来：
`blockedByCooldown`（施放时闪避键还灰着）与 `blockedByOverlap`（上一招预警还没结算）在**所有四个倍率上都是 0**。
**凡是「X 就是 Y」的句子，都要找到一个能把 X 和 Y 分开的读数，并证明它们在当前树上相等** ——
否则那个等号只是排版。

**「pin every X」这种全称断言要逐项核对 X 的清单。** `bossBudget.test.ts:202` 的注释写着
「pin every viewport-derived gameplay distance」，钉了 `spawnRadius`/`chargeRange`/`bossDamage`/`bossHp`/
`bossPhaseSpawnInterval` —— **就是没有 `bossCastCooldown` / `bossSkillDamage`** ⇒ 全套件里**没有任何断言**。
一个**为 0 的覆盖**比没有更糟：它让下一个人以为「这条规则被钉住了」。**凡注释里出现「every / all」的断言，
都要把清单逐项数一遍**（与 R2-F10「『已有断言』可能假覆盖」同源）。

**一个杠杆可以同时改两个验收，而且方向相反 —— 判别量必须按策略拆开报。** 缩短冷却对**会躲的玩家**
（`hud` 臂）**几乎免费**（G2/G3 全绿，施放 2→3→4，多出来的施放落不到身上），对**不躲的玩家**
（`browser` 臂）**从「拿不到 G2」升级成「会死」**（`cadence only m=.5` ⇒ evolution `hpMin` 0、战死 21/33）。
**先算出余量再选杠杆**：G4 的 `requiredMultiple / shippedSkillDamage` = 14.31 / 14.31 = **1.000** ⇒
**任何按比例缩招式的候选（`constant aggregate`）都破 G4，而只缩冷却的候选（`cadence only`）不破。**
余量为 1 的验收上，唯一的出路是**换场地（拉长窗口 / 解耦招式）而不是换数值**。

### 7l. R2-F-SUFFIX 的三条（**分类器 / 断言类切片**）

**「TASK.md 里写的待测前提」也要当假设测过。** 本片 Scope 1 明写「前提要检验的是：**一次自动施放会不会被
算成手动技能**」—— 实测**为假**：形态 kit **从来不被自动施放**（`action('skill')` 只由玩家输入到达），
而自动循环的 id 取自 `build.active`，**没有一个以 `_E` 结尾**。所以「一个字符串两种意思」是真的，
但它**没有**污染 G8 —— 真正的缺陷在别处（下一条）。**照前提去修会修错地方**：如果只按 Scope 1 的
措辞去「排除 kit id」，就会得到一个零差异的改动，同时把 §3 那条 2.74× 的假绿留在原地。

**「注释声称的读数」和「代码实际算的读数」要分开量。** `MANUAL_CORE` 的注释写着「The GDD's own §11.1
test reads only these two **keys**」，而代码是**两个桶** —— 注释描述的是 GDD，代码不是。**凡注释里出现
「这就是 X 的读数」的句子，都要把 X 的原话找出来跑一遍。** 本片照 GDD `:919` 的原话跑出 **0.1365**，
而字段报的是 **0.3739**；`expect(core).toBeLessThanOrEqual(headline)` 这类守卫因为
`MANUAL_CORE ⊂ MANUAL` 而**恒真**，所以**过**是假的。这是 R2-F10「『已有断言』可能假覆盖」的
第二种形态：**不是断言太弱，是断言测的不是注释声称的那个量。**

**「分类器只看得见键」的时候，信息可能在写入时就丢了。** `_E` 的两种意思里，`G2_FROST_E` 这一种
（霜君签名场 **与** `G2_FROST` 的释放键）**从键字符串本身无法分辨** —— 所以要靠**构造**回避
（`formPressure` 保留 `A011`；`manualDamage` 只跑到 `dragon`）。**凡是「靠构造回避」的陷阱，
都要在某个地方留下断言**（本片加了 `truth['G2_FROST_E'].auto === 0`），否则它会在下一个人手里静默复活。
另：**「修分类器还是修生产」的判据是「信息有没有在写入时丢失」** —— 没丢就修读者（0 报告改动），
丢了才动生产。

### 7m. R2-F-SHADOW 的三条（**测量 / 修法裁定类切片**）

**「队列里写的理由」也要当前提核实。** 本片的三条修法里，① 被队列写成「技能改 `heroAim()`
（偏离最近目标，不再同心）」—— 而 `heroAim()` 与 `nearestFrom` 在**四个压力场景里逐位相同**，
唯一分离的配置没有任何格包含。**如果照着队列的理由直接落地 ①，就会交付一个「声称修好了、
但一个字节都没动」的改动。** 这是 R1g-5 / R1g-6 那类失效的第四次，而这次是**队列本身**写的理由。

**「有效」不等于「修好了」。** ③ 在「把技能涡旋送进 `damageBy`」这条上是有效的，但它的**净效果
是负的**（觉醒 ×0.8903、玩家挨 18.68）。**凡「X 出现了」的句子，都要再问一句「那么整体是变好了
还是变差了」，并且用同一份账本回答。** 这与 R2-F10 的「凡『觉醒让 X 上升』都要先拆 `dealtBy`」
是同一类，只是这次反向。

**反相关比单一读数更有信息量。** 本片的关键不是「`hpMin = 1`」也不是「两阶相同」，而是
**两者同生同灭**（六个取值无一例外）。**当两个读数在扫掠下同步翻转时，它们多半是同一个事实的
两个面** —— 这时修其中一面必然破另一面，出路是**换场地**而不是换数值。

### 7n. R2-B01..08 的四条（**验收 / 单开关控制类切片**）

1. **「没有验收」要按条数一遍，不能按印象。** 队列说八条都没有，实测**六条早就有**，两条还相当
   完整。**差别的形状是「存在性 vs 系数」**：`damageBy.X > 0` / `undefined` 这种断言在**系数被改
   掉时保持绿**，所以它证明「有」，不证明「是多少」。补的时候只补缺的那一半，别重写既有的。
2. **一个空对象让「清冷却」变成空操作。** `cool` 初始是 `{}`（`CombatSimulation:79`），
   `for (const id of Object.keys(sim.cool))` 在全新 sim 上**遍历零项**；自动施法循环随后读到
   `undefined`，而 `!(undefined > 0)` 为**真** ⇒ **第一帧把所有已拥有技能放一遍**。症状是「多出
   一个涡旋」「两个假人同时被 135px 的霜环冻住」—— 看起来像被测代码错，其实是夹具没生效。
   **修法**：按 `Object.keys(sim.progression.snapshot().skills)` 置大数。
3. **对照臂的源 id 必须与生产同元素。** 用 `CTRL` 这种自造 id 做对照，`sourceElement` 会把它判成
   **physical**，而生产是 **fire**，元素本身就在 `damageMultiplier` 里 ⇒ 假差异 **1.67×**。
   **同一个量、同一条管线、同一个元素**，只让被测系数变，才是单开关控制。
4. **`updateOuter` 不推进 `sim.time`** ⇒ 用时间戳测间隔会得到全 0（不是「间隔为零」）。**改按帧**：
   召唤物的 `tick` 在每次攻击时**复位到常量**，复位间隔 = 间隔本身，而「间隔是常量」正是
   「不自我叠加」的判据。

### 7o. R3-E01..07a 的三条（**第一次改出货档的切片**）

1. **首轮报出的红是下限，不是全量。** 同一个 `it` 里前面的断言红了，后面的**根本不会跑**。本片
   首轮报 13 条，补完再复跑又露出 2 条（`growthPacing` 的「带融合选项的宝箱」、`bossThreat` 的
   `kept[0] === cheapestMove`）。**红的总数要按「复跑到全绿」数**；`+N` 对不上时先问「是不是还有
   没跑到的」，不要先怀疑探针。
2. **一条恒等式在一侧为空时不是「更难满足」，而是「不成立」。** 空 `kept` 上
   `kept[0] === cheapestMove` 拿到 `undefined` vs `0` —— 它红了，但红的**理由不对**（不是读数错，
   是没有读数）。**改成「有 survivor 就比、没有就断言空过滤器自己的产物是 0」**：后者有主语，
   前者没有。守着一条没有主语的恒等式，只会让下一个人以为数据脏了。
3. **改了池就要先推「谁读池」，再用实测对账。** `createEnemy` 是唯一读出生池的地方 ⇒ 「读敌人
   构成」= 「这次运行让刷怪器活着」。这条推出的名单是 16 份，实测也是 16 份，而**没动的 67 份
   里包含十个压力格** —— 它们逐帧 `cull` 掉刷怪器的产物。**先推后测**，两者对上才敢说「价格
   就是这些」。

### 7p. R3-M01 的三条（**验收空真 / 守卫可达性类切片**）

1. **空真的断言与真断言长得一样。** 「无隐形阻挡」成立，因为**全库没有任何碰撞体** —— 它不是被验证的
   性质，是**没有防守对象**。判据：把断言换成**强形式**（走过全部六个物件的**每一步步长完全相同**），
   只有强形式会在有人加进第一个碰撞体时变红。**先问「这句话的防守对象存在吗」，再问它对不对。**
2. **「缺一个守卫」要先问「有没有可达路径」。** 敌人移动一直没有 `clampPoint`，而它**从来没出过问题** ——
   因为后退方向永远指向内侧，**几何在替 clamp 干活**。`charge`（瞄**穿过**玩家）是**第一条**给它造出
   路径的机制，实测冲刺后 `x = -30`：一个身体在地图外、照常发弹、照常结算接触，而玩家钳在 18 ⇒ 再也
   够不到它。**新机制会点亮旧缺口** ⇒ 加机制时把它经过的每一条既有守卫数一遍。
3. **clamp 的是「谁」要说清。** 火线原来钳的是**中心**（世界内 80 px），而它要防的是**自己的身体**
   （36 px 宽）。中心钳 80 + 玩家钳 18 ⇒ 沿墙 **44 px 永久免伤区**，201 个 draw 实测最近距离恒 **62**。
   **钳制的余量决定玩法**，不只是防越界。另：**混沌序列上的 `max` 要钉上界不要钉值** —— D23 钉 `>= 1`，
   本片就回到 0；改成 `<= 1` 后两次读数都在内，而它正是 D3 需要的那个量。

### 7q. R3-M02 的三条（**开门 / 类型撒谎类切片**）

1. **类型系统也会替数据撒谎。** `stage: structuredClone(chapterStages[0])` 让 `stage` 的类型**等于第一行**：
   `boss` 非空、`seals` 空元组、`duration` 字面量 `360`。三个关卡的**联合信息被抹成一行**，而编译器
   一个字的怨言都没有。换成 `ChapterStageId = (typeof chapterStages)[number]['id']` 后 `vue-tsc` 精确
   点名**恰好两处** `stage.boss.spawnAt`，探针实测 `TypeError: Cannot read properties of null`。
   **判据：一个字段的类型来自「第一行」而不是「所有行」，那它就是一条假注释。**
2. **一扇打不开的门会挡住门后的崩溃 —— 门和崩溃是同一个 bug 的两面。** `CH001-02` 有三道显式锁
   （`prepare.ts` 的两处 + `contracts.test.ts` 把拒绝钉成断言），第四道锁**在类型里**。开门不是「放开
   一行校验」，是**同时**修掉三个首帧崩溃 + 让胜利成为可能（`updateObjective()` 只认 `defeatedAt`，
   `boss: null` 的关卡**只能超时或阵亡**）。**先数「门后有几处会炸」，再决定开不开。**
3. **扫描必须固定走位策略，否则量的是机器人。** 同一个界碑半径 84 px，站定死于 109.1 s、绕 0.55R 死于
   136 s、绕到圈边守到 2/3 —— 「能不能守住」由**怎么动**决定。所以半径扫描的每一档都用**同一条轨迹**
   （绕 0.85R + 闪避 + 奥义 + 低血优先恢复），否则表里的差是策略的差。另：**要机器人活七分钟才能证明的，
   是战场不是时限** —— 超时臂改成 `sim.time = duration - FRAME` 后一行就够。

### 7r. R3-E01..07c 的三条（**定义类切片 / 夹具选层**）

1. **「带 X 的行」这个问法可能不成立。** `elite` 不是一行数据，是 `spawnRules.ts` 的一串倍率 ——
   出生池六行**每一行**都可能被 roll 成精英。所以「多少行带 elite」的答案是**零行**，而正确的问题是
   「谁在运行时把 `elite` 置真」。**先问「这个字段存在哪一层」，再数行。** 同一个字段在两个层
   （数据行 / 运行时布尔）里叫同一个名字时，数出来的数会差一个量级。
2. **一个「不可达」的数可以单独否掉一个方案。** 时钟第二词缀要 `time > 960`，而三关时长
   360/420/480 —— **全部到不了**。这不是「少一个档位」，是**这个机制在有名字的关卡里不存在**。
   所以「两个普通精英」这个选项在写第一行代码之前就该被否掉。**扫一遍候选方案里每个依赖的
   阈值，先问它在目标场景里能不能满足。**
3. **夹具选错层，量到的是夹具。** 三条红全是驱动错：① 用 `GameCore` 构造关着的关卡会被
   `OPEN_STAGES` 拒（`CombatSimulation` 才是不看策略的那层）；② 把 `sim.time` 跳到 150 s 会让
   120 s 的检查**补刷**，于是「波精英不计」的断言被自己的检查污染（换到 `eliteAt: []` 的关卡才干净）；
   ③ `spawn()` 在 `updateObjective()` 里调、不在 `updateAI` 里，用 `beginFrame` 驱动永远等不到首领。
   **红的时候先问「我的驱动有没有把这个机制跑起来」，再问「读数对不对」。**

### 7s. R3-M03 的五条（**标定 / 浮点 / 写死的长度 / 过期绿 / 命令在哪**）

1. **「太难」这个读数必须先过一道控制臂：仪器能不能通关出货关卡。** 第一版机器人报 `CH001-03`
   打不完（141/223/372 s 阵亡），但**同一台机器人在出货的 `CH001-01` 上也死**（227/230/303 s）。
   一个连出货关卡都打不过的机器人，没有资格判定新关卡太难 —— 那次读数是**仪器**的读数。
   修好走位后同一关卡 **3/3 胜**，而换一种走位（守一角）**1/3 胜**。**判据**：任何「这个关卡不行」
   的结论，都要附一句「同一台仪器在同一批种子上通关了哪个已经上线的关卡」。
2. **搬进数据的数，要么是系数，要么就等着浮点翻脸。** `.95 - phase * .08` 的结果**不等于**字面量
   `0.87`。把三档「预算好」存进 JSON，等于把每一发预警的 `life` 改到最后一位，而
   `combat-math-oracle.json` 是逐字节的。**存 `base`/`perPhase`，保留算式**，出货路径才真的不变。
3. **一个 id 可能被仪器写死它的长度。** `'B001'` 不只是标签：它是 `damageTakenBy` 的键前缀，
   而 `bossThreat.test.ts` 用 `source.startsWith('B001')` + **`slice(5)`** 拆招式名 ——
   id 一变长，伤害就被静默归进 `lostToHorde`，而**分区看起来仍然完备**。改任何被当作键的常量前，
   先 `grep` 它的**切片**与**前缀**用法，不只 `grep` 它的值。
   附带一条：`firstStage.rule.bossId === 'B001'` **零读者** —— 「默认值」早就写在数据里，
   代码只是不看。**要加一个兜底常量之前，先找有没有一个没人读的字段已经是它。**
4. **「首轮全绿」也可能是过期绿。** 全量要 28 分钟，**采集发生在启动那一刻**，期间改测试文件不会被
   重新读。本片首轮全量报 `altar.test.ts (12 tests)`，而单跑报 13 —— 根因不是 vitest 吞了一个 `it`，
   而是那次全量 `01:00:19` 启动、文件 mtime `01:00:33`（守一角的对照臂是采集之后写进去的）。
   判据不是「它绿了」，而是**「它的 mtime 早于采集时刻」**：跑全量前对这片改过的文件跑一次
   `ls -l --time-style=full-iso`。**首轮报出的红是下限，绿也可能是下限。**
5. **「跑一下那个命令」之前先确认命令在哪。** `ledger:write` 不在 `apps/mobile-next/package.json`，
   它在**仓库根**（`node tasks/game-remediation/byte-ledger.mjs --write`），在子包里跑得到的是
   `Missing script`。手写脚本算出的 271 行与官方脚本逐项一致（新增 1、删除 0、漂移 2 且两份都是
   滚动），**但手写脚本能算对，不代表它就是那条命令** —— 证据页上写的命令必须是真能跑的那条。

### 7t. R3-P02 的五条（**读字段 / 同一数字两种态度 / 夹具合法性**）

1. **`re.findall(r"(\w+): …")` 会漏掉 shorthand，而漏掉的结果长得像「字段没写」。**
   本片第一次数「声明的字段 vs 写入的字段」，得到「18 声明 / 15 写入，缺 `runId`、`stars`」——
   **那是正则的错**：这两个是 `{ runId, ruleset: …, stars, … }` 里的**裸标识符**。按逗号切分、
   裸标识符也算写入后是 **17 == 17**。**判据**：任何「某字段没人写」的结论，先确认解析器认不认 shorthand。
2. **同一个数字可以在两处有两种态度，而且两处都对。** `20` 在写入处是 `slice(0, 20)`（**静默丢最旧**），
   在校验处是 `> 20 → 抛`（**拒收整份存档**）。页面因此能假设 `<= 20`，**不能**假设 `=== 20`。
   **一个上限要在两处实现时，先问它们是不是同一个意思** —— 截断与拒收是两种策略，不是同一个的备份。
3. **校验允许的范围可以比写入的宽，宽出来的部分是假格子。** `stars` 写入是 `victory ? 1 : 0`，
   校验是 `number(..., 3, true)`。按校验画三格星，**每次胜利都会显示 1/3** —— 一个玩家没做错却看着像
   没打好的读数。**画实际值，不画声明范围**；范围宽出来的格子没有数据，画上去就是造数据。
4. **一个断言把整个字面量钉死，就成了摩擦。** `codex.test.ts` 逐字钉了
   `page = ref<'home' | 'battle' | 'settings' | 'saves' | 'codex'>`，于是**加一个页面要改一个无关文件**。
   改成 `page = ref<[^>]*'codex'[^>]*>`：钉**自己那一段**，不钉别人的邻居。**断言的范围应该等于它声称的
   那个事实的范围** —— 多钉一个成员，多的不是保险，是下次的噪音。
5. **夹具里的数字也要合法，否则红的是夹具不是产品。** 中位数用例拿了 `time: 401`，而 `CH001-01`
   的时限是 **360** ⇒ `validateChapterFinal` 直接拒收（`精品首章数据无效：时间`）。
   更贵的一次是同一条测试里：失败局**沿用了胜利局的 `time: 310`**，却断言 `06:00`（实际 `05:10`）——
   就算改对数字，那条「失败行和胜利行字段一样」的测试**也什么都没证明**，因为两行的钟本来就一样。
   **「A 与 B 有同样的形状」这种断言，必须让 A 与 B 在别的维度上真的不同。**

### 7u. R3-P03 的五条（**一个杠杆几个发射点 / 乘数缺省 1 / 回执**）

1. **「一个杠杆只有一个读点」是断言，不是印象。** 我在裁定里写了「六个杠杆各自一个读点，所以
   『一个护符只做一件事』是结构保证」，然后第一次跑测试 `MC_CYCLE` 就红了：`expected 6 to be 5.1`。
   `p.skillCd` 有**三个**写入点 —— `CombatSimulation`（遗留分支）、`chapter/DragonCombat.ts`（龙形术式）、
   `core/EvolutionCombat.ts`（征途）。`H001` 在章节线的术式**走龙形**，所以我改的那一行**根本不在它的路径上**。
   **判据不是「我改了」，是「所有发射点都经过我改的那一行」** ⇒ 修法是把冷却收成 `skillCooldown()`
   一个函数、三个发射点都调用它。**只测 `charmScale()` 的返回值会绿，而玩家装上护符什么都不会发生。**
2. **「乘数缺省 1」比「在准备期预先算好」更安全。** 前者让「没装备」与「这段代码不存在」在读数上
   不可区分（`x * 1` 对任何有限双精度逐字节相等），后者会把效果烘进 `player`，于是同一个杠杆就有了
   第二个生效位置。**预言机的保护应该来自结构（两条测试的 `chapter` 都是 `undefined`），不是来自小心。**
3. **`transactOnce` 的操作号必须带 revision。** 不带的话，「装备 A → 卸下 → 再装 A」的第三次会命中
   第一次的**回执**，返回 `applied: false` 且**什么都没写**，而界面显示「已装备」——
   **幂等与「重新做一遍」是两件事**，revision 正好把它们分开。
4. **数据里存绝对值会漂移。** 一枚把「4.5 秒」抄进自己行里的护符，在有人把闪避冷却改成 4 秒之后
   会**一边失效一边宣称 4.5**。只存 `lever` + `factor`，基数留在读点，改基数会流过每一枚碰它的护符。
   代价是页面上只能写「×0.8」，绝对值写在证据页 —— 那是对的，证据页才有仪器声明。
5. **「一个护符只做一件事」是靠选读点保证的，不是靠自律。** `MC_MOVE` 乘 `player.speed` 会同时放大
   闪避位移（`min(90, speed * .34, 视口 * .16)` 读同一个量）⇒ 一枚护符悄悄做两件事。挂在移动那一行上，
   闪避距离**逐位不变**，这条可以用「两局各闪一次、比较位移完全相等」断言。

### 7v. R3-P04 的五条（**零读者字段 / 文档比代码错 / 三档塌成一档 / 结构类型断依赖**）

1. **一个「零生产读者」的字段，不能问它「有没有被滥用」。** `chapters.stars` / `clears` 只被写、只被校验，
   没有任何 UI 读它们 ⇒ 「重打会不会刷出永久优势」这个问题的答案**不在那个字段里**，在**消费端**：
   `prepareChapterRun` 从 progress 只取一样东西（装备的护符），`player` 的五个数逐字来自常量表。
   **判据要写成「只改进度字段，输出逐字段相等」**，而不是「我搜了，没人用」—— 后者在有人接上时不会红。
2. **注释和文档会比代码错得更久。** 队列写着「`App.vue` 只有四页」，实测七个；GDD 写着「通关 1 /
   无伤 2 / ≥55% 3」，而数据是 `clear: 2 / mastery: 3`。**两条都不影响任何一行代码**，但下一个人会从
   它们开始数。**发现文档与代码不一致时，写进证据页而不是悄悄绕过** —— 它本身是下一切片的前提。
3. **三档评级可以「每档都对」而整体是错的。** `无伤` 蕴含 `≥55%`，所以 `hp===maxHp ? 2 : hp/maxHp>.55 ? 3 : 1`
   会让**打得更好的局显示更差**。每个分支单独看都正确，没有一条测试会红。**判据不是「每档都实现了」，
   是「档位之间单调」** ⇒ 拿数据里自洽的两档（`clear` / `mastery`），把散文记为错。
4. **用结构类型断掉依赖方向。** 挑战表只声明它敢读的三个字段（`ChallengeFacts`），`ChapterFinalRun`
   结构上满足它 ⇒ 数据表不认识结算类型，`import` 是单向的。**「只读三个字段」再用 `Proxy` 数一遍**：
   多读一个 `time`/`hp`/`stars` 就红 —— 这样「挑战不会因为关卡被重调而改变含义」是结构保证。
5. **奖励必须是「一次只能戴一个」的东西。** 队列说「无永久数值碾压」，护符满足它不是因为乘数小，
   而是因为**同时只能生效一枚**、且解锁是**首次达成的一次性**（`earnedCharms` 过滤已拥有）。
   **判据要写成三条独立的断言**：不碰 `gold`/`mastery`/`accountXp`/`level`、不新增存档字段、
   重复打同一关产出为零。**一条「我保证不发数值」的注释，一条测试都不会红。**

### 7w. R3-U01..05 的五条（**改了实现没改句子 / 空态不可达 / 两类失败同形 / 存闭包 / scoped 断点**）

1. **改了实现、没改那句给玩家看的话 —— 而且两次都是同一个提交里。** `ReportsPanel` 说「胜利记 1 星」
   而 D31 已改成 0..3；`ChapterResult` 说「效果将在战备版本开放」而 D30 已接入。**测试全绿，因为没有
   一条断言读那句话。** 判据不是「文案有没有更新」，是「页面上有没有一句承诺，其真值来自别处」——
   页面**复述**别的模块的规则就必然漂。修法不是改字，是**插值**（`chapterStars.clear`）或**陈述已发生的事实**。
   断言要写两条：旧句子不再出现 **+** 新句子从数据取；只钉前者，「换个说法再说一遍同样的错」还是绿的。
2. **「空态」要先问它能不能到达。** `SaveRepository.initialize()` 在没有存档时**创建一个** ⇒
   `slots` 永远非空 ⇒ `SavePanel` 的空 `v-for` 是**空真**。空真断言与真断言长得一样，
   所以不要给它写文案，去**钉住所有者行**（`existing[0] || makeSlot(...)` 那两行）。哪天有人改成
   「没有就返回空」，那条先红 —— 那时才需要句子。
3. **同一个 API 的两种失败可以长得完全一样，而正确的按钮相反。** `transactOnce`：`receipt` 命中 ⇒
   再调同 id 安全（重试是对的）；`revision` 不符 ⇒ **重试永远失败**（该给「回大厅」）。
   只有 `BattleView` 分了这两类，`CharmsPanel` 把两类显示成同一句话 ⇒ 玩家反复点一个不可能成功的按钮。
   **判据不是「有没有错误提示」，是「提示指向的那个动作能不能成功」。**
4. **重试要重跑**那个**操作，所以存闭包，不存按钮名。** `SavePanel` 的 `failed` 存的是失败的那个
   `() => Promise<void>`，`importFile` 捕获的 `File` 还在，玩家不用重新选文件。存「上一次点了什么」
   会在参数变化时重做另一件事 —— 而界面上看不出区别。
5. **`scoped` 只作用于本模板，所以断点必须写在组件自己里。** 往 `style.css` 加 `.reports{...}`
   到不了 `ReportsPanel` 的 scoped 样式作用域。断言也要跟着分：有 `<style scoped>` 的页面检查
   组件文件本身，`SavePanel`（无 `<style>`）检查 `saves.css`，`settings`（无组件）检查 `style.css`
   的 640 块 —— **同一句「有断点」，三个不同的文件位置，写错一个就漏一页。**

### 7x. R3-U06 的五条（**一行绑定 / 门禁读不读 / 三格什么时候才成立 / 图鉴看运气 / 清空的顺序**）

1. **「可构造 ≠ 可玩」可能只是一行。** 六个片（D27–D32）在一条没有入口的路径上写代码，原因就是
   `App.vue` 那行 `<BattleView>` 少了 `:chapter`。**判据不是「功能有没有实现」，是「有没有一条从
   玩家手指到它的路径」**；而路径的缺口常常比功能小两个数量级。
2. **复用一道门禁之前，先问「这道门拦的字段，这条路径读不读」。** `previewBlocker` 有八条，
   章节线只读其中一条 —— 而那条 `prepareChapterRun` 自己就保证了。复用的后果是造出一个
   **假限制**（`mode: 'endless'` 的存档打不了章节关），而那个字段章节线根本不读。
   替代品不是「再写八条」，是**试跑一次真正的调用**：它执行的就是开战那一刻要执行的那一行，不会漂。
3. **「画三格」是布局假设，不是显示选择。** D29 拒绝画三格，因为写入端只发 0/1（三格显示 1/3 像没打好）；
   D31 把区间填满之后，三格才是评级。**同一个布局在两次裁定里答案相反，因为数据变了** ——
   所以「这个布局对不对」不能脱离「这个字段现在能取哪些值」回答。格子数也从 `chapterStars.mastery` 取。
4. **「打完就有内容」要按页面逐个看写入条件。** 战报/挑战/护符是 `settleChapterRun` 无条件写的；
   图鉴写在 `if (run.formId)` 里 —— 不进化的一局 `formId === null`，图鉴仍然空。
   **差别是结构性的**（图鉴记的是可选分支见没见过），不是运气；页面上的「未见」是诚实的。
5. **退出时先翻页、再清状态。** `BattleView` 是 `v-if` + 挂载时分叉，所以 `chapterOptions` 不清会让
   **下一局静默变成章节局**；而清的**顺序**也重要 —— 先清再翻页会把 `chapter: undefined` 递给一个
   还活着的组件。断言写成「两句的先后」，不是「两句都在」。
